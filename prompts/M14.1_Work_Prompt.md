# OpenFEP M14.1 Work Prompt

## Milestone

M14.1: Background Self-Continuity And Persistent Idle Loop

## Goal

Lift Path B's idle reflection out of the Streamlit rerun cage. Today Hu Tao can
only "think" when the user clicks something or the chat page rerenders. M14.1
gives the MVP runtime a real, budget-bounded heartbeat so that:

- the conscious idle reflector (M14.0) can keep ticking while the user is silent
or while the browser is closed,
- `self_cognition`, `open_items`, and bounded memory consolidation can evolve
between user turns through the same named-owner contract,
- a persistent **operational self** baseline (`self_continuity`) survives across
sessions and resists low-confidence drift,
- proactive outreach can be **prepared offline** and delivered through the
existing M13.3 path when the UI is next available, instead of being lost on
page close.

This milestone explicitly retires the M13.3-era guardrail wording
"no background autonomy". That phrase was a placeholder for "we did not yet
have a safe lifecycle". M14.1 builds the safe lifecycle and replaces the
wording with honest engineering language.

The target behavior:

```text
opt-in (background self-continuity) + budgets (tokens/day, wallclock/day)
-> background runner (in-process daemon when UI open, or CLI process)
-> heartbeat tick (interval >= MIN_TICK_SECONDS)
-> M13.4 structural pre-filter
-> M14.0 conscious idle reflector (mode = "idle_introspection")
-> self_continuity review (drift / pinning / baseline update)
-> patches via named owners (M8.9 contract)
-> outreach proposals queued (cross-session safe)
-> on UI render: drain queue through M13.3 delivery assessor
```

## Architecture Position

M14.1 stays Path B and stays MVP-local. It must obey `CLAUDE.md`:

```text
background runner
-> MVPStateStore (file-locked, single owner per persona+session)
-> shares the same modules used by user turns:
   M13.4 m13_idle structural pre-filter
   M14.0 conscious idle reflector
   M14.0 named-owner validators
   M13.3 outreach pipeline (delivery only)
-> conversation_log.jsonl (audit)
-> queued_outreach.jsonl (new, persistent across UI sessions)
```

The conscious loop remains the orchestrator. The runner does **not** introduce
a second agent, a second prompt persona, or a second cognition stack. It is
purely a scheduler around already-tested M13/M14 modules.

## Dependencies

Hard:

- M8.9 state-ownership contract and `MemoryWriteIntent`
- M13.0 / M13.1 / M13.2 drive state
- M13.3 outreach pipeline (`maybe_propose_proactive_turn`,
`run_proactive_turn`, delivery assessor)
- M13.4 idle tick + structural pre-filter
- M14.0 conscious idle reflector + named-owner validators

Soft (read-only):

- M11.0, M12.0, M12.1, M12.2 outputs

M14.1 must not cross-write into M11 or M12.x ledgers. It must not reimplement
any conscious-loop content; it only schedules calls into M14.0.

## Non-Goals

- Do not claim subjective consciousness, real loneliness, real craving, real
pleasure, or "true self". The runner produces an **operational** self
baseline. All audit text, prompts, UI labels, and code comments use that
framing.
- Do not introduce a second LLM persona or a second cognition stack.
- Do not run unbounded LLM calls. Token-per-day, wallclock-per-day, and
minimum-tick-interval budgets are mandatory.
- Do not bypass `user_opt_in`. Background self-continuity is an explicit,
separate opt-in on top of M13.3 / M13.4 opt-ins.
- Do not let the runner produce user-visible text by itself. Outreach text is
only generated when the M13.3 delivery assessor approves a queued proposal.
- Do not write to M11 or M12.* ledgers from the runner.
- Do not extend Path A (`conversation_loop.py`) or M10
(`exploration.py`) for this milestone.
- Do not let the runner mutate `self_basic_facts.json`.
- Do not require Streamlit to be running. The runner must be able to operate as
a standalone CLI process attached to the same MVPStateStore.

### 2. Background Runner

Add a new module:

```text
segmentum/dialogue/runtime/m14_1_self_runner.py
```

It must expose two interchangeable backends behind a single interface:

```text
class BackgroundSelfRunner:
    def start(self) -> None
    def stop(self, *, drain_wait_seconds: float = 2.0) -> None
    def status(self) -> dict
```

Backends:

- **Inline daemon backend** — a single daemon `threading.Thread` started from
the Streamlit app on opt-in. Stops when the Streamlit process exits or opt-in
is cleared. Must never block Streamlit reruns.
- **CLI backend** — `python -m segmentum.dialogue.runtime.m14_1_self_runner --persona <id> --session <id>`. Reads the same MVPStateStore the UI uses.
Single instance per (persona, session) enforced via a lock file
(`runner.lock` in the session root) with PID + start timestamp.

Both backends share:

- the same tick loop (no logic forks),
- the same audit events (different `runner_kind` tag),
- the same budget enforcement,
- graceful shutdown on `SIGTERM`, `SIGINT`, opt-in flip, or stop call.

The tick loop:

```text
sleep until next tick boundary
acquire MVPStateStore lock
state = store.load()
if budgets exceeded: emit BackgroundBudgetReachedEvent and skip LLM
else:
    invoke M13.4 maybe_run_idle_introspection
    invoke M14.0 reflector when structural pre-filter passes
    run self_continuity review (see §4)
    persist patches via M14.0 owners
    enqueue outreach proposal in queued_outreach.jsonl when applicable
release lock
```

Tick interval is configurable; default `tick_interval_seconds = 90`, minimum
`MIN_TICK_SECONDS = 30`.

### 3. Persistent Budgets

Replace and extend the M13.3 / M13.4 session counters with persistent budgets
under `m13_drive_state.initiative.background_continuity`:

```text
m13_drive_state:
  initiative:
    background_continuity:
      enabled
      user_opt_in
      runner_kind          # "inline" | "cli" | "none"
      tick_interval_seconds
      tokens_used_today
      tokens_budget_per_day
      wallclock_used_today_seconds
      wallclock_budget_per_day_seconds
      ticks_today
      max_ticks_per_day
      llm_calls_today
      llm_calls_budget_per_day
      day_anchor            # ISO date used to reset daily counters
      last_tick_at
      last_budget_block_reason

      # lifetime counters (never reset; useful for the 内心活动 panel)
      idle_ticks_lifetime
      self_reviews_lifetime
      llm_calls_lifetime
      tokens_used_lifetime
```

Defaults must be conservative:

```text
enabled                          = false
user_opt_in                      = false
tick_interval_seconds            = 90
tokens_budget_per_day            = 30_000
wallclock_budget_per_day_seconds = 600
max_ticks_per_day                = 400
llm_calls_budget_per_day         = 80
```

Every LLM round-trip (conscious idle reflector, self-review, delivery
assessor, queue drain) must increment `llm_calls_today` /
`llm_calls_lifetime` and add the response tokens to `tokens_used_today` /
`tokens_used_lifetime`. Successful idle ticks increment
`idle_ticks_lifetime`; successful self-review ticks increment
`self_reviews_lifetime`. These counters are read-only diagnostics; reaching
`llm_calls_budget_per_day` raises `BackgroundBudgetReachedEvent` with
`reason="llm_calls_budget_exhausted"` and skips the LLM call for the rest of
the day.

Daily rollover must happen at the first tick after `day_anchor` changes
(local date) and must be auditable (`BackgroundDailyRolloverEvent`).

Session-scoped counters from M13.3 / M13.4 stay as-is; M14.1 adds the daily
layer on top. "Continuous loop" means **not gated by session caps**, but still
hard-bounded by the daily budgets above.

### 4. Self-Continuity State

Add a new owned section under `self_cognition.json`
(or new file `self_continuity.json` — pick one and document the choice in the
implementation note; do not split across both):

```text
self_continuity:
  baseline_summary
  baseline_stable_values
  baseline_known_limits
  baseline_updated_at
  drift_window:                  # capped FIFO, e.g. last 20 entries
    - { patch_id, at, magnitude, direction, kept_into_baseline }
  identity_tension_history:      # capped FIFO
    - { tension, opened_at, resolved_at|null, resolution_kind }
  stable_value_candidates:       # rolling counts before promotion
    - { value, count, last_seen_at }
  last_self_review_at
  self_review_count_today
```

Promotion rules (deterministic; not LLM hints):

- A `stable_value_candidate` is promoted to `baseline_stable_values` after
appearing in `K_STABLE_PROMOTION` consecutive self-review ticks
(`K_STABLE_PROMOTION = 3`).
- A drift entry that persists for `K_DRIFT_KNOWN_LIMIT` reviews (`= 4`)
and is not absorbed into the baseline must be added to
`baseline_known_limits` with `source = "self_continuity_drift"`.
- Patches with `confidence < MIN_BASELINE_UPDATE_CONFIDENCE = 0.7` may enter
`drift_window` but must not modify the baseline directly.

Self-review tick (run inside M14.0 reflector, not as a separate prompt):

- Every `K_SELF_REVIEW_TICKS = 6` idle ticks, the conscious idle prompt
receives an extra compact block `self_continuity_snapshot` (baseline +
drift_window summary).
- The reflector may propose at most one baseline update per self-review tick;
validators must enforce the `0.7` confidence floor and require evidence_refs
retrieved this tick.

No new LLM persona. The reflector keeps the M14.0 schema; this is one extra
prompt section plus deterministic post-processing.

### 5. Cross-Session Outreach Queue

When the runner is active and an idle plan produces
`outreach_recommendation.should_outreach=true`, do **not** synthesize text from
the runner. Instead, persist a queue entry:

```text
queued_outreach.jsonl (append-only, capped):
  {
    proposal_id,
    created_at,
    expires_at,
    trigger,                  # "reflection_outreach" | ...
    ordinary_language_intent, # clamped
    evidence_refs,
    drive_snapshot_compact,
    status: "pending" | "delivered" | "expired" | "suppressed"
  }
```

Constraints:

- `expires_at = created_at + DEFAULT_QUEUED_OUTREACH_TTL_SECONDS = 24 * 3600`
  (so that an idea generated late at night can still be delivered the next
  day; tunable via the sidebar within `[1h, 72h]`).
- Queue length cap: `MAX_QUEUED_OUTREACH = 8`; older pending entries are
  expired with `QueuedOutreachExpiredEvent`.
- The queue lives in the persona+session root; it is **not** shared across
personas.

Drain rule (UI side):

- On each Streamlit render with `user_opt_in=true` and no pending user message,
drain at most one queue entry through the existing M13.3 path:
  - call `maybe_propose_proactive_turn` with `locked_proposal=<queue entry>`
  - on approval: `run_proactive_turn`
  - on suppression: keep the entry pending if reason is transient
  (`cooldown_active`, `user_active`); mark `suppressed` for hard reasons
  (`safety_risk`, `session_limit_reached`).

Crucial invariant: there is no second generation path. The runner never
produces user-visible text; only M13.3 does.

### 6. Concurrency, Locking, Lifecycle

- All MVPStateStore writes during a tick happen inside a file lock
(`session_root/store.lock`) with a fair timeout (suggest 5s).
- Only one runner per (persona, session). The lock file `runner.lock` records
PID, host, runner_kind, started_at. Second runner attempts emit
`BackgroundRunnerCollisionEvent` and exit.
- The inline daemon backend must register a Streamlit-side
`on_session_end` hook (or equivalent) to stop the runner on browser
disconnect. If the hook is unavailable, the runner stops after
`INLINE_RUNNER_IDLE_DEATH_SECONDS = 1800` of no Streamlit pings.
- All audit events must include `runner_kind`,
`engineering_proxy_label = "mvp_local_background_self_continuity"`, and the
`runner.lock` PID.

### 9. Language Discipline (Engineering Layer Only)

This section narrows an inherited rule. It does **not** invent a new ban and
it explicitly does **not** apply to Hu Tao's in-character chat replies.

**Where the rule comes from.**

```text
prompts/M13.3_Work_Prompt.md, Non-Goals:
  "Do not claim the persona 'woke up' or 'felt lonely' unless the user has
   explicitly opted into fictional roleplay wording and the message remains
   clearly within persona style."
  Proactive-text generation constraint: "no claim of subjective need".

prompts/M14.0_Work_Prompt.md, Non-Goals:
  "Do not claim subjective 'loneliness', 'addiction', 'boredom feeling', or
   'I needed to reach out'. Use plain operational language."
  Acceptance: "No subjective-need wording appears in any reflector output,
   prompt, or outreach intent."
```

M14.1 inherits the same constraint and applies it to the new background
runner. The intent is to prevent the **engineering layer** from presenting
itself as having subjective experience, not to censor the persona's voice.

**Scope — what this section covers.**

```text
- audit event types, `reason` and `skip_reason` strings, enum values
- runner / reflector / owner module code comments and docstrings
- sidebar labels, help text, status strings, diagnostics labels
- M14.0 reflector JSON fields and engineering-side prompt sections
  (e.g. self_continuity_snapshot block)
- the system-side `ordinary_language_intent` text that is fed back into the
  thinking prompt as engineering guidance
- documentation under prompts/ and CLAUDE.md
```

**Scope — what this section does NOT cover.**

```text
- Hu Tao's persona reply text generated by the thinking module under persona
  style and the M9 reply_contract
- in-character chat that the user reads in the chat tab
- delivered M13.3 outreach text after it has passed the delivery assessor
- roleplay vocabulary inside that delivered text, including "我想你了" /
  "想你" / "我有点小情绪" — these are character voice, not system claims
```

The persona is free to say "想你" because that is the character speaking. The
ban is only on the **system** (audit row, sidebar label, code comment,
reflector JSON, engineering intent text) describing itself or the persona as
literally having that subjective state as ground truth.

**Forbidden in engineering-layer text only.** Phrases or fields that present
the runner / reflector / system as subjective:

```text
"she is awake" / "the runner is awake"
"consciousness module" / "self-awareness module"
"true self" / "free agent"
"I needed to reach out" (as system reason or intent)
"reason=she_misses_user" or similar audit reasons that read as feelings
audit reasons phrased as first-person emotional need
```

Note that "she misses the user" is **only** forbidden as a system claim
(e.g. an audit `reason`, a sidebar label, or an engineering intent string).
The persona reply "我想你了" is fully allowed and out of scope here.

**Allowed engineering vocabulary.**

```text
"background self-continuity"
"operational self baseline"
"persistent idle loop"
"drift window"
"stable-value pinning"
"runner produced N idle ticks today"
"outreach proposal queued, pending delivery assessor"
```

**Lint.** A small static check (`tests/lint_no_subjective_language.py` or
equivalent) scans only the engineering-layer surfaces above. Specifically:

```text
must scan:
  segmentum/dialogue/runtime/m14_1_self_runner.py
  segmentum/dialogue/runtime/m14_idle_owners.py
  segmentum/dialogue/runtime/m14_idle_reflector.py
      (engineering-side strings only; persona-facing reply contract excluded)
  segmentum/dialogue/runtime/m13_initiative.py (initiative module text)
  segmentum/dialogue/runtime/app.py sidebar/help/diagnostics strings
  new audit-event type constants
  prompts/M14.1_Work_Prompt.md
  CLAUDE.md

must NOT scan:
  persona thinking prompt reply instructions and persona style sections
  M13.3 delivered chat messages
  M9 reply_contract templates
  user-facing chat history rendered in the chat tab
```

The forbidden phrase list is short and additive across milestones. It is a
denylist of system-level subjective claims, not a vocabulary denylist for the
character Hu Tao.

## Acceptance Criteria

M14.1 is complete when:

1. Background self-continuity is an explicit, separately-toggled opt-in,
  layered on top of M13.3 and M13.4 opt-ins, and disabled by default.
2. A heartbeat runner — inline daemon and CLI process backends — can tick the
  M14.0 conscious idle reflector and self_continuity review independently of
   Streamlit reruns, while honoring per-day token, wallclock, and tick budgets.
3. `self_continuity` state evolves through deterministic promotion / drift /
  known-limit rules plus M14.0 conscious patches, with the M14.0 named-owner
   validators enforcing evidence_refs and confidence floors.
4. Outreach proposals produced while the UI is closed are persisted in
  `queued_outreach.jsonl`, survive process restarts, and are delivered (or
   safely discarded) only through the existing M13.3 pipeline.
5. M11.0, M12.0, M12.1, M12.2 ledgers are not written by the runner.
6. The phrase `no background autonomy` (and equivalent placeholders) is removed
   from code, sidebar text, and M13.3 / M13.4 prompts, replaced by
   engineering-honest language.
7. No system-level subjective claims appear in any **engineering-layer** text
   (runner output, audit event, sidebar label, code comment, reflector JSON,
   ordinary_language_intent, commit message). The lint test enforces this
   scope only; persona-style replies and roleplay vocabulary in delivered chat
   are explicitly out of scope.
8. Path A and M10 are not extended; no new dependencies on
  `conversation_loop.py` or `exploration.py`.
9. All listed suggested tests pass with deterministic LLM stubs.
