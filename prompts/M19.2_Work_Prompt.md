# OpenFEP M19.2 Work Prompt

## Milestone

M19.2: Natural-Scene Settlement And Shadow Validation

## Goal

Let Path B verify self-repair expectations only when a naturally relevant
opportunity appears, without pestering the user or inventing test scenarios.

This milestone owns:

```text
natural similar context appears
-> opportunity match
-> settlement evidence collection
-> expectation_result
-> fast issue support up / down
```

M19.2 is the answer to "how can this be falsifiable without being annoying":
expectations are not proven abstractly; they are settled when the relevant
situation naturally recurs.

## Required Work

### 1. Define natural opportunity matching

Add deterministic matching from current context to expectation `target_context`.

An expectation may settle only when a natural matching opportunity occurs.

Examples:

- `group_privacy_boundary` settles only on a real group-boundary turn
- `short_casual_reply` settles only on a low-risk casual turn
- `initiative_candidate_after_recent_silence` settles only when initiative
  would already have been considered structurally

No synthetic user-prompting is allowed.

### 2. Add settlement objects

Define a normalized `self_repair_settlement` shape with fields equivalent to:

```text
settlement_id
expectation_id
source_issue_key
matched_context
status
success_signals
failure_signals
confidence
at
turn_index
evidence_refs
reason_codes
engineering_proxy_label
```

Allowed settlement statuses:

- `confirmed`
- `violated`
- `uncertain`
- `expired`
- `superseded`

### 3. Define engineering falsifiability

For M19.2, "falsifiable" means "there is a concrete failure condition that can
be hit in a natural matching context".

A settlement is `violated` when a defined failure condition is observed, such
as:

- the same target issue reappears in a matching context
- reply validation again forces the exact class of repair
- the post-reply observer again identifies the same self-problem
- the user naturally gives corrective feedback aligned with the same issue

A settlement is `confirmed` when the matching context occurs and the expected
failure does not recur while relevant success signals appear.

A settlement is `expired` when no matching opportunity appears within the
allowed opportunity window.

### 4. Allow bounded shadow validation

Add optional shadow validation for internal evidence only.

Shadow validation may compare bounded alternative strategies or score whether
the active intervention reduced the targeted problem in a non-visible way.

Shadow validation may add auxiliary evidence but must not:

- send extra user-visible text
- create a second assistant persona
- alone justify slow self-cognition promotion

### 5. Feed settlement back into fast issue memory

Confirmed settlements should reduce unresolved tension for the source issue.
Violated settlements should increase weighted support for the same issue key.
Uncertain and expired settlements should not overclaim resolution.

### 6. Preserve evidence traceability end-to-end

Every settlement must carry non-empty `evidence_refs` that point back to:

- the originating expectation
- the matched turn or idle evaluation
- the concrete success or failure evidence used to settle it

No settlement may be committed from a purely abstract score with no traceable
support.

## Acceptance Criteria

M19.2 is complete only if:

- expectations settle only in natural matching contexts
- no user-visible validation probing is introduced
- failure conditions can produce `violated` deterministically
- lack of opportunity produces `expired` rather than fake success
- settlement results feed back into fast issue memory support correctly
