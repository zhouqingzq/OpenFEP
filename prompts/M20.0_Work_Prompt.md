# OpenFEP M20.0 Work Prompt

## Milestone

M20.0: ActiveCommitment Meta-Contract, Registry, And Observable Vocabulary

## Goal

Freeze the cross-cutting meta-contract that lets every Path B commitment flow
through the same shape, the same owner, and the same observation vocabulary —
without yet building any settler, promotion, or repair runtime. M20.0 is a
schema-only milestone.

```text
M17 prediction_proposals
M19 self_response_expectation / self_repair_expectation
M19.3 calibrated_tendencies / repair_priors
M11 UserPredictionLedger
M9.0 memory_dynamics.control_guidance
M15.0 episode ledger entries
M13.3 outreach intents
M18.x addressee graph
                                       |
                                       v
                +-------------------------------------+
                |        ActiveCommitment (M20.0)     |
                +-------------------------------------+
                                       |
                                       v
        schema        -> CommitmentRegistry -> Observable vocabulary
        (frozen)         (owner map, v1)         (bounded enum v1, with
                                                  settler-type hint)
```

M20.0 does not replace M17/M19/M19.3/M11/M9/M15/M13/M18 implementations. It only
adds a meta-layer that:

- names what a "commitment" is on Path B,
- maps each existing commitment type to a single owner in
  `CommitmentRegistry`,
- freezes the first version of the `Observable` vocabulary that all later
  settlers must speak.

It explicitly does **not**:

- implement settlers (deterministic / llm_judge / hybrid) — that is M20.1,
- implement graded correction or promotion logic — that is M20.2,
- refactor M17/M19 self_response_expectation rows to use `ActiveCommitment`
  as the storage shape — that is an adapter concern, owned by later milestones,
- unify Path A or M10 (out of scope per CLAUDE.md).

## Why M20.0 Exists

Three pre-M20 paths each grew a "commit / observe / repair" loop independently:

```text
M17  prediction lock  -> settlement  -> precision EMA  -> memory gate
M19  self-expectation -> mismatch    -> repair expectation -> traction
M9   memory_dynamics  -> guidance    -> recall seeds  -> (no settler)
M11  user model       -> proposal    -> judgment      -> (legacy)
M15  episode ledger   -> entry       -> consolidation -> (M15.1)
M13  drive state      -> pull        -> settle proxy  -> (M13.2)
M18  addressee graph  -> target      -> policy        -> (M18.5)
```

Every loop had to answer the same five questions:

1. What is being committed to, in a single bounded shape?
2. Who owns the row? (Path B requires named owners, `source`, `reason`,
   `confidence`, audit event.)
3. What does "settled" mean here — deterministic, LLM-judge, or hybrid?
4. How does it promote or revoke, and on what timescale?
5. What evidence anchors are required?

Before M20.0, each loop answered these with its own private vocabulary:

- M17 invented `prediction_type` enum and `evidence_basis` reason categories.
- M19 invented `target_context` enum, `mismatch_type` enum, and
  `engineering_proxy_label`.
- M9.0 invented `repair_bias`, `conflict_level`, `assertion_strength` floats.
- M13.2 invented `prediction_error_proxy` scalar.
- M15.0 invented episode-ledger shape.
- M11 legacy had `confidence_band` strings.

These vocabularies drift. M17.12 already complains that Path B has "two
half-loops". M19.3 will collide with M17.5-M17.10 over what "promoted" means.
M15.2 meta-control will not know which row to inspect.

M20.0 freezes the *vocabulary of commitment* itself, so that later milestones
can converge without rewriting history.

## Architecture Position

M20.0 is MVP-local and lives as a sibling meta-layer to the existing
conscious-loop / memory-dynamics / M13 stacks:

```text
conscious-loop JSON
   |  M19 self_response_expectation_proposals
   |  M11 prediction_proposals
   |  pending_expectations / open_items
   v
+-----------------------------------------------------+
|  ActiveCommitmentAdapter (M20.0 v1, no settler)     |
|  - validates ActiveCommitment shape                |
|  - resolves owner via CommitmentRegistry            |
|  - emits ActiveCommitmentCreated audit event        |
|  - hands off to owner write path                    |
+-----------------------------------------------------+
   |
   v
owner.write(state, commitment)        # named owner, source, reason, evidence
```

M20.0 owns:

- the `ActiveCommitment` schema (frozen),
- the `CommitmentRegistry` (owner map, frozen),
- the `Observable` vocabulary v1 (frozen),
- the `CommitmentPhase` enum (frozen).

M20.0 does **not** own:

- any settler implementation (M20.1),
- any promotion or revocation rule (M20.2),
- any `M19 self_response_expectation` shape change (M19.0/19.1 already landed;
  adapter work is a separate later milestone),
- any rewrite of `pending_expectations` / `open_items` storage — only the
  ActiveCommitment *shape* needs to be expressible.

## Non-Goals

- Do not implement any settler. M20.0 must not contain code that decides
  whether an `Observable` value is `confirmed` / `violated` / `uncertain` /
  `ambiguous`. That is M20.1.
- Do not implement promotion, demotion, downgrade, or revocation. M20.0 must
  not contain a `commitment_promotion` rule, a `repair_priors` write, a
  `calibrated_tendencies` write, or any pull/traction update.
- Do not rewrite `self_response_expectation` or `self_repair_expectation` to
  use `ActiveCommitment` as their storage shape. M19.0/19.1 land is the
  source of truth; later adapter work can map, not migrate, them.
- Do not unify `pending_expectations` and `open_items` with
  `ActiveCommitment`. The active conscious-loop JSON contract is separate.
- Do not introduce new top-level state buckets. M20.0 may add a small
  `commitment_registry_index` audit-only artifact, but must not create
  `active_commitment_state` that owns rows.
- Do not touch Path A, M10, `conversation_loop.py`, or `SelfThoughtProducer`.
- Do not let the LLM emit final committed state for an `Observable`. The
  vocabulary defines what an `Observable` is; the LLM may propose observable
  values, but commitment confidence remains in the existing confidence
  surfaces (M17 numeric confidence, M19 self-expectation confidence, etc.).
- Do not let `Observable` become a free-text field. The vocabulary is a
  bounded enum v1; adding a new value is a registry change, not an LLM call.

## Required Work

### 1. Freeze `ActiveCommitment` schema

Define a frozen, immutable-by-convention `ActiveCommitment` dataclass or
Pydantic model. Fields:

```text
commit_id: str                       # deterministic: sha1 of (owner_id,
                                      #   source_kind, source_ref, layer,
                                      #   observable, created_turn)
owner_id: str                        # must be a key in CommitmentRegistry
source_kind: str                     # "policy" | "state" | "episodic"
source_ref: str                      # stable id of the source row that
                                      #   produced this commitment
layer: str                           # "A_long_term_prior" |
                                      #   "B_per_turn_commitment" |
                                      #   "C_observation"
observable: str                      # must be a key in Observable v1
observable_payload: dict             # bounded structured payload for the
                                      #   observable, schema-per-observable
                                      #   (defined in Observable v1, see §3)
target: dict                         # bounded target spec, e.g.
                                      #   {"target_context": "short_casual_reply"}
due_at: dict | None                  # {"kind": "next_turn"} |
                                      #   {"kind": "natural_context",
                                      #    "context_match": "..."} |
                                      #   {"kind": "iso", "iso": "..."} |
                                      #   None  # no due
priority: float                      # [0.0, 1.0], clamped
confidence: float                    # [0.0, 1.0], source-owned
evidence_refs: list[str]             # non-empty; see §5
created_turn: int
created_at: str                      # ISO 8601
reason_codes: list[str]              # bounded enum, see §6
engineering_proxy_label: str         # bounded enum, see §7
```

Rules:

- `commit_id` MUST be deterministic. Given the same owner/source/layer/
  observable/created_turn, the same `commit_id` is produced. The proposal
  LLM may not choose it.
- `owner_id` MUST be a key in `CommitmentRegistry` (§2). Unknown owners are
  rejected at adapter admission.
- `source_kind` MUST be one of the three frozen values.
- `layer` MUST be one of the three frozen values.
- `observable` MUST be a key in `Observable` v1 (§3). Unknown observables are
  rejected.
- `evidence_refs` MUST be non-empty. Empty refs are rejected.
- `confidence` and `priority` are clamped to `[0.0, 1.0]` and not
  re-interpreted by the adapter.

### 3. Freeze `Observable` vocabulary v1

bounded payload schema and a settler-type hint. Settler-type hints are

### 4. Freeze `CommitmentPhase` enum

```text
CommitmentPhase:
  - "created"        # ActiveCommitment has been admitted
  - "settled"        # an Observable has produced a settled value
  - "promoted"       # the owner accepted the commitment into a long-term
                     # bucket (M20.2 logic, not implemented in M20.0)
  - "revoked"        # the owner rejected the commitment (M20.2 logic, not
                     # implemented in M20.0)
  - "expired"        # due_at passed without settlement (M20.2 logic, not
                     # implemented in M20.0)
```

M20.0 freezes the enum and emits `created` audit events. It does not emit
`settled` / `promoted` / `revoked` / `expired` events; that is M20.1+.

### 5. Make evidence anchoring mandatory

`evidence_refs` MUST be non-empty. Allowed value kinds (M20.0 v1):

- an existing M17 `prediction_id`,
- an existing M19.0 `self_response_expectation.expectation_id`,
- an existing M19.1 `self_repair_expectation.expectation_id`,
- a M19.0 `mismatch_id`,
- a M11 legacy `prediction_proposal_id` (read-only),
- a M15.0 `episode_id`,
- a M13.2 `settlement_id`,
- a conscious-loop `expectation_id` (existing pending/open item),
- a turn-local handle of the form `turn_<n>_<slot>` if no durable id exists
  yet (bounded local reference; not allowed for promoted or revoked phases).

The adapter must reject ActiveCommitments whose `evidence_refs` is empty or
whose refs cannot be parsed into one of the allowed kinds.

### 8. Add the `ActiveCommitmentAdapter` admission path

Implement a thin adapter in `mvp_loop.py` (or a small sibling module) that:

- accepts a proposed `ActiveCommitment` from a bounded producer (a conscious
  loop, an idle reflector, or a M19.0/19.1 self-expectation wrapper),
- validates the schema, registry, observable, and evidence_refs per §1–§7,
- derives `commit_id` deterministically,
- emits an `ActiveCommitmentCreated` audit event with the full validated
  commitment row (no payload truncation, no `reason` paraphrasing),
- hands the validated row to the owner's existing write path, which already
  owns the storage bucket.

The adapter must NOT:

- settle, promote, revoke, or expire the commitment,
- compute priority or confidence from raw text,
- invent new observables, owners, or reason codes,
- store the commitment outside the owner's storage bucket.

Producer wiring in M20.0:

- The adapter accepts proposals from exactly two sources in M20.0:
  - existing M19.0 `self_response_expectation_proposals` (mapped to
    `observable = "expectation_outcome_match"` on a later settle attempt),
  - a small new bounded `active_commitment_proposals` field added to
    `normalize_conscious_turn_plan` (empty by default; future milestones
    populate it).
- No other source may produce an `ActiveCommitment` in M20.0. Future
  milestones (M17.5+, M19.4+, M20.1+) add bounded producer fields, each
  through a separate work prompt.

### 9. Emit the audit event

{

  "turn_index": 42,
  "commit_id": "<deterministic sha1>",
  "owner_id": "<from registry>",
  "source_kind": "policy|state|episodic",
  "source_ref": "<stable id>",
  "layer": "A_long_term_prior|B_per_turn_commitment|C_observation",

with a bounded `reason_code` (`unknown_owner`, `unknown_observable`,
`empty_evidence_refs`, `invalid_layer_source_kind`, `unknown_reason_code`,
`unknown_engineering_proxy_label`, `invalid_payload_shape`).

## Acceptance Criteria

M20.0 is complete only if:

1. `ActiveCommitment` schema, `CommitmentRegistry` v1, `Observable` v1,
   `CommitmentPhase`, `reason_codes` v1, and `engineering_proxy_label` v1
   are all frozen as immutable-by-convention in code.
2. The adapter admits commitments, derives `commit_id` deterministically,
   and emits `ActiveCommitmentCreated` and `ActiveCommitmentRejected`
   audit events. No other event kinds are emitted by the adapter.
3. The adapter has no settler, no promotion, no revocation, and no
   expiration code path. M20.1 / M20.2 acceptance work cannot run on
   top of M20.0 because no settlers exist; this is intentional.
4. Existing M17/M19/M11/M9/M15/M13/M18 producers are not refactored to
   use `ActiveCommitment` as their storage shape. They MAY call into
   the adapter as a *parallel* producer (M19.0 self-expectation does
   this in §8) without changing their on-disk shape.
5. The conscious-loop JSON contract gains one bounded field,
   `active_commitment_proposals`, that is empty by default and may be
   populated by future milestones.
6. `evidence_refs` is enforced non-empty at admission.
7. `commitment_registry_index` diagnostic counters are exposed in the
   existing diagnose/UI observability surface.
8. All new tests pass; settler/promotion/revocation tests for M20.1/M20.2
   are explicitly absent (red), and the absence is documented in the
   test file headers.
9. Path A and M10 remain untouched.
10. `prompts/README.md` M20.0 entry exists and lists the freeze boundary.

## Verification Standard

The milestone is only accepted if a recorded Path B test turn can show:

```text
ActiveCommitmentCreated.timestamp < owner_write_event.timestamp
owner_write_event references commit_id from the created event
owner_id is in CommitmentRegistry v1
observable is in Observable v1
evidence_refs is non-empty
```

with no settlement / promotion / revocation event in the trace (because
M20.0 does not emit them). This proves the meta-contract binds but does
not yet bind the loop. M20.1 then proves the first settler, M20.2 proves
the first promotion, against the same trace format.

## Engineering Phenomenology Boundary

M20.0 is a schema milestone. No new visible behavior is expected. The
user must not see any change in chat output, idle ticks, or proactive
delivery as a result of M20.0 landing.

M20.0 may create the engineering preconditions for "every commitment
flows through the same shape" but it must not claim a unified
commitment loop has been achieved. M20.1 and M20.2 own that claim.
