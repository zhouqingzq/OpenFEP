# OpenFEP M17.1 Work Prompt

## Milestone

M17.1: Prediction Settlement And Deterministic Error

## Goal

Close the T1 half of the prediction loop:

```text
next user observation arrives
-> fetch pending predictions whose verification window includes this turn
-> settlement assessor classifies each prediction by prediction_id
-> deterministic code computes prediction_error from committed_confidence
-> append settlement/error rows and M15 episode addenda
```

This milestone replaces post-hoc surprise proxies for user predictions with a
replayable measurement:

```text
confirmed: -log(committed_confidence)
violated:  -log(1 - committed_confidence)
unclear:   no information / no error update
expired:   no information unless explicitly configured as timeout audit
```

The only LLM step is bounded classification. It must not output a surprise
score, memory score, or final error value.

## Architecture Position

```text
M16 runner receives next user turn
  -> MVPDialogueRuntime.run_turn
     -> load pending UserPredictionLedger rows from prior turns
     -> settlement assessor emits outcome by prediction_id
     -> deterministic error calculator appends judgment/error events
     -> M15 episode ledger receives addendum for affected prior episode
     -> current turn may then create fresh M17.0 predictions
```

M17.1 builds on:

- M17.0 prediction lock ordering
- M13.2 `normalize_user_reaction_assessment` and pending-settlement style
- M15.0 episode ledger append-only addenda

M17.1 must keep semantic ownership separate from M13.2:

```text
M13.2 settlement -> user reaction to a prior assistant action
M17.1 settlement -> observed outcome of a prior user-model prediction
```

M17.1 may reuse small deterministic helper patterns from M13.2, such as bounded
reason-code normalization or confidence clamping, but it must not reuse the
M13.2 reaction taxonomy, prompt, state rows, or reward-settlement owner.

## Dependencies

Hard:

- M17.0 numeric `committed_confidence`
- M13.2 bounded assessor patterns and reason code limits
- M15.0 episode ledger append-only addenda

Soft:

- M13.6 memory-backed expected-free-energy events, read-only as evidence context
- M14.7 gate events, read-only as future memory update linkage

## Non-Goals

- Do not update type precision EMA in M17.1.
- Do not change MemoryGate scoring in M17.1.
- Do not run offline ablations.
- Do not force binary outcomes when evidence is weak.
- Do not use keyword or regex rules over raw user text for semantic settlement.
- Do not let the settlement LLM output `prediction_error`, `surprise`, or write
  scores.
- Do not rewrite original prediction rows; append settlement rows/addenda.
- Do not route new M17 locked predictions through legacy M11
  `prediction_judgments`. That path may remain only for backward-compatible M11
  fixtures until explicitly retired.
- Do not store M17 measured prediction error under unqualified M13 names such as
  `prediction_error_proxy`.
- Do not touch Path A or M10.

## Required Work

### 1. Add settlement schema by prediction_id

Define a normalized settlement record:

```text
PredictionSettlement:
  settlement_id
  prediction_id
  source_prediction_turn
  settled_at_turn
  outcome: confirmed|violated|unclear|expired
  settlement_confidence: float
  evidence_span: str
  evidence_refs: list[str]
  reason_codes: list[str]
  should_update: bool
  assessor_kind: llm_bounded|expiration|deterministic_no_info
```

`outcome` is the M17 settlement outcome. It is allowed to include `expired`.
`validation_status` is the compatibility ledger status. If the existing ledger
status enum is not expanded, map:

```text
confirmed -> confirmed
violated  -> violated
unclear   -> uncertain
expired   -> uncertain with settlement_outcome="expired"
```

Do not allow an unsupported `expired` ledger status to silently fall back to
`pending`.

Rules:

- `confirmed` and `violated` require `settlement_confidence >= 0.55`.
- `confirmed` and `violated` require either an `evidence_span` or evidence refs.
- Weak or missing evidence becomes `unclear`.
- `unclear` must not update precision, memory gate, or prediction-error totals.
- Expired predictions are appended with settlement outcome `expired` or
  `unclear` and reason `ttl_expired_without_evidence`; the compatibility ledger
  status must follow the mapping above.

### 2. Add deterministic error calculator

Add a helper, preferably in a new module:

```text
segmentum/dialogue/runtime/m17_prediction_error.py
```

Required functions:

```text
prediction_error_from_outcome(committed_confidence, outcome) -> float | None
prediction_brier_from_outcome(committed_confidence, outcome) -> float | None
normalize_prediction_outcome(raw) -> confirmed|violated|unclear|expired
```

Definition:

```python
if outcome == "confirmed":
    error = -log(max(conf, eps))
if outcome == "violated":
    error = -log(max(1.0 - conf, eps))
if outcome in {"unclear", "expired"}:
    error = None
```

Also compute a Brier component for later calibration:

```text
confirmed -> (1 - conf)^2
violated  -> (0 - conf)^2
```

### 3. Connect settlement assessor to pending predictions

Add an adjacent M17 assessor wrapper so it receives compact pending prediction
summaries:

```json
{
  "prediction_id": "pred:...",
  "prediction_type": "preference_prediction",
  "claim": "User will prefer implementation-level guidance.",
  "committed_confidence": 0.72,
  "created_at_turn": 42,
  "expires_after_turns": 2
}
```

Expected bounded output:

```json
{
  "prediction_id": "pred:...",
  "outcome": "confirmed",
  "settlement_confidence": 0.81,
  "evidence_span": "user asks for module paths and verify standards",
  "reason_codes": ["continued_same_design_topic", "implementation_detail_requested"]
}
```

The wrapper must reject:

- unknown prediction ids,
- duplicate settlement for the same prediction in the same turn,
- unsupported outcomes,
- overlong evidence spans,
- reason code lists beyond the existing M13.2 cap.

The wrapper may call shared normalization helpers, but its prompt, input schema,
output schema, telemetry event type, and state owner must be M17-specific. A
user saying "thanks" may be M13 uptake without confirming any M17 prediction;
the two assessments must be able to disagree without either being treated as an
error.

### 4. Append ledger events

For each settled pending prediction, append a judgment entry to
`UserPredictionLedger`:

```text
event_kind = "judgment"
validation_status = compatible status mapped from outcome
observed_outcome_summary = compact settlement summary
settlement_outcome = outcome
m17_prediction_error = deterministic error or null
m17_brier_score = deterministic brier or null
settlement_confidence = normalized settlement confidence
settlement_id = ...
```

Keep the original pending row intact.

If the implementation keeps legacy `prediction_error` or `brier_score` field
names for compatibility, it must also write the explicit M17-prefixed aliases
above and document that they are distinct from M13 reward
`prediction_error_proxy` and M15 `expectation_prediction_error_proxy`.

### 5. Emit episode ledger addenda

When a prediction tied to a prior turn settles, append an M15 episode addendum:

```json
{
  "type": "PredictionSettlementAddendum",
  "episode_id": "...",
  "source_episode_id": "...",
  "prediction_id": "pred:...",
  "prediction_type": "preference_prediction",
  "outcome": "confirmed",
  "committed_confidence": 0.72,
  "m17_prediction_error": 0.328504,
  "m17_brier_score": 0.0784,
  "evidence_refs": ["..."],
  "reason_codes": ["..."],
  "engineering_proxy_label": "mvp_local_prediction_error"
}
```

If no matching episode exists, write a ledger-level audit event and continue.
Missing episode linkage must not block prediction settlement.

M17.1 must establish a stable linkage strategy from locked prediction rows to
the episode that created them. Prefer writing `source_episode_id` or an explicit
`prediction_id -> episode_id` mapping when the T0 response episode is committed.
Replay coverage in M17.3 depends on this mapping; missing linkage should be
audited with a reason code, not silently ignored.

M17.4 bundle assembly also depends on compact structured linkability. New M17.1
rows and addenda must preserve whatever explicit keys are already known from
this bounded set:

```text
prediction_id
source_episode_id
episode_id
evidence_refs
reason_codes
```

They do not all have to be present on every row, but an implementation must not
drop an already-known structured link and then expect M17.3/M17.4 to recover it
from natural-language text.

### 6. Replace local user-prediction proxy where safe

Where M15.0 currently reads `expectation_prediction_error_proxy`, add a separate
field for the new measured value:

```text
measured_user_prediction_error
measured_user_prediction_brier
settled_prediction_count
```

Do not delete the existing proxy in M17.1. Mark it as legacy/advisory in comments
or report text until M17.2/M17.3 proves replacement quality.

Naming rule:

```text
M13 reward delta error       -> prediction_error_proxy
M15 legacy expectation proxy -> expectation_prediction_error_proxy
M17 measured user prediction -> measured_user_prediction_error / m17_prediction_error
```

Do not feed M17 measured values into M13 rollback thresholds or reward baseline
logic.

## Acceptance Criteria

M17.1 is complete when:

1. Pending predictions from prior turns can be settled by `prediction_id`.
2. Settlement outputs are only `confirmed`, `violated`, `unclear`, or `expired`.
3. Deterministic error is a pure function of committed confidence and outcome.
4. Re-running the same settlement input produces byte-stable error values.
5. M15 episode addenda include measured prediction error where linkage exists.
6. `unclear` and default expiration do not pollute calibration data.
7. M17 settlement uses an M17-specific wrapper and does not mutate M13.2 reward
   settlement state.
8. Legacy M11 `prediction_judgments` cannot double-settle new M17 locked rows.
9. `expired` is either a valid explicit ledger status or a separate settlement
   outcome mapped to compatible `uncertain`; it must never become `pending`.
10. Known structured link fields needed by replay and bundle assembly are
    preserved on addenda or audited as missing, never silently discarded.
11. Existing M13.2 reward settlement tests still pass.
12. Path A and M10 remain untouched.

## Verification Standard

Use a fixture with one prediction at `committed_confidence=0.90`.

Expected:

```text
confirmed -> prediction_error ~= 0.1053605
violated  -> prediction_error ~= 2.3025851
unclear   -> prediction_error is None
```

The same fixture must produce the same ledger addendum on replay except for
explicitly allowed generated ids/timestamps.
