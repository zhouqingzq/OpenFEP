# OpenFEP M17.6 Work Prompt

## Milestone

M17.6: Verification-To-Memory Credit Assignment

## Goal

Make later verification outcomes change memory quality rather than only changing
action bias or write thresholds.

Target contract:

```text
retrieved memory or path helps form a prediction
  -> later evidence confirms / violates / leaves it unresolved
  -> deterministic credit assignment updates memory quality
  -> future retrieval, retention, and forgetting reflect that history
```

This milestone is the first real closure of the loop:

```text
prediction
  -> evidence
  -> measured outcome
  -> memory credit revision
```

Without this step, verification remains mostly advisory. M17.6 makes it
causal for memory dynamics.

## Architecture Position

```text
decision retrieval / memory context
  -> prediction ledger + verification loop
  -> MemoryCreditSignal
  -> memory entry / episode / path update
  -> later retrieval and retention policy
```

Recommended owner split:

```text
PredictionLedgerOwner      -> prediction settlement facts
VerificationLoopOwner      -> evidence support / contradiction facts
MemoryCreditOwner          -> converts facts into memory-quality updates
MemoryStore / LongTermMemory -> apply updates, persist audit
```

Recommended landing points:

```text
segmentum/prediction_ledger.py
segmentum/verification.py
segmentum/memory.py
segmentum/memory_store.py
segmentum/agent.py
```

If a helper module is added, prefer:

```text
segmentum/memory_credit.py
```

## Dependencies

Hard:

- M17.5 canonical FE surrogate terminology
- Existing prediction ledger and verification loop
- Existing retrieval audit / memory context linkage

Soft:

- Existing replay and sleep consolidation surfaces
- Existing `reusable_cognitive_paths` or future path objects

Compatibility-sensitive:

- Existing memory retrieval ranking inputs
- Existing retention or forgetting heuristics
- Existing verification artifacts that do not yet preserve memory linkage

## Non-Goals

- Do not convert memory quality into unconstrained learned weights.
- Do not let the LLM assign memory credit.
- Do not rewrite content during this milestone; quality update comes first,
  structural reconstruction later in M17.7.
- Do not replace retrieval scoring wholesale yet.
- Do not present the credit signal as a true free-energy measurement. It is the
  M17.5 surrogate applied to memory; audit and docs must keep that label.
- Do not touch Path A or M10.

## Required Work

### 1. Define a deterministic memory-credit signal contract

Add a bounded contract such as:

```text
MemoryCreditSignal:
  linked_prediction_id
  linked_memory_ids
  linked_path_ids
  outcome: confirmed|violated|partial|unclear|expired
  support_score
  contradiction_score
  prediction_error_delta
  free_energy_delta
  confidence_weight
  source_module
```

Rules:

- `confirmed` should strengthen predictive reuse value.
- `violated` should increase corrective pressure or contradiction burden.
- `unclear` or `expired` may affect confidence slowly, but must not pretend to
  be evidence of success or failure.
- The same signal must not update a memory twice for the same settled
  prediction.
- `partial` must have an explicit bounded meaning, for example mixed support
  with incomplete contradiction, rather than being an implementation escape
  hatch.
- The signal must be computable from structured verification facts, not from a
  prompt-only narrative explanation.

### 2. Preserve explicit retrieval-to-prediction linkage

When a decision uses retrieved memories, the runtime must preserve compact
linkage sufficient for later credit assignment:

```text
prediction_id -> retrieved memory ids
prediction_id -> bundle ids, if any
prediction_id -> path ids, when available
```

Natural-language reconstruction alone is not enough. Later verification must be
able to say which memory/path was actually on the hook.

Minimum linkage requirements:

- prediction settlement must name the memory ids that materially participated
- skipped or auxiliary retrieved memories must be distinguishable from
  committed-on-the-hook memories
- if bundles or path summaries later exist, they must still retain member-level
  accountability

### 3. Define bounded quality dimensions and update rules

Credit assignment should update bounded quality fields, for example:

```text
predictive_reliability
retention_pressure
future_path_utility
error_avoidance_gain
contradiction_burden
verification_history
```

Requirements:

- These may live in `compression_metadata` or first-class fields, but they must
  have one owner.
- `support_count` alone is not enough; the system must distinguish repeated
  confirmation from repeated reuse without confirmation.
- Violation should not simply negate all prior value; updates should be bounded
  and history-aware.
- The update rule must specify which fields move on:

```text
confirmed
violated
partial
unclear
expired
```

- The implementation must define how `prediction_error_delta` and
  `free_energy_delta` influence credit magnitude without making one extremely
  noisy observation dominate the whole history.
- Credit magnitude must be precision-weighted using the M17.5
  `precision_weighted_prediction_error` / `free_energy_delta` components, not the
  raw error alone. The intended meaning is that a memory's quality approximates
  the degree of precision-weighted free-energy reduction it produced when reused:
  a confident memory that materially lowered the surrogate earns more credit than
  one whose reuse left the surrogate unchanged. Low-precision (high-ambiguity)
  outcomes must move quality less. Do not invent a second error scale here.

### 4. Feed credit into retrieval and retention owners

At least two downstream consumers must change:

```text
retrieval ranking or accessibility
retention / forgetting / promotion pressure
```

Examples of allowed behavior:

- memories repeatedly linked to confirmed predictions become easier to retrieve
- contradicted memories accumulate contradiction burden and become less likely
  to dominate future recall
- stable confirmed paths become more eligible for consolidation

Rules:

- Retrieval may read compact quality summaries, but it must not become an
  uncontrolled blend of all credit history.
- Retention and forgetting policy must distinguish repeated confirmed utility
  from repeated mere exposure.
- First shipped version must affect at least one online retrieval surface and
  one persistence surface.

### 5. Add audit events and idempotence protection

Required events or equivalent structured payloads:

```text
MemoryCreditAssignedEvent
MemoryCreditSkippedEvent
```

Minimum fields:

```text
prediction_id
memory_ids
path_ids
outcome
support_score
contradiction_score
applied_deltas
skip_reason
```

Also require a settlement guard such as:

```text
credit_application_key = (prediction_id, memory_id or path_id, settlement_version)
```

so duplicate settlement, replay, or late-arriving evidence cannot silently
double-apply the same update.

### 6. Add replay-safe determinism and negative controls

Credit assignment must be deterministic from the same settled prediction and
verification evidence. This is required so later replay harnesses can measure
its effects.

M17.6 must include negative controls proving:

- unlinked memories do not receive accidental credit
- expired or unclear outcomes do not masquerade as confirmation
- a retrieved memory that did not materially support the committed prediction is
  not updated as if it had

## Acceptance Criteria

M17.6 is complete when:

1. Settled predictions and verification outcomes can produce explicit memory
   credit signals.
2. Retrieval-time memory ids are durably linked to later settled predictions.
3. At least one bounded memory-quality dimension changes on confirmation and on
   violation.
4. Those quality changes affect at least two downstream consumers: retrieval
   and retention/forgetting.
5. Duplicate settlement events do not double-apply the same credit update.
6. Audit payloads can explain why a memory gained, lost, or skipped credit.
7. The implementation remains deterministic and replay-safe.
8. Path A and M10 remain untouched.

## Verification Standard

Use one fixture where:

```text
two retrieved memories support the same prediction
later verification confirms the prediction
only one memory was marked materially committed in the runtime linkage
```

Expected:

```text
the committed memory gains predictive_reliability or equivalent utility credit
the merely retrieved-but-unused memory does not receive the same credit
MemoryCreditAssignedEvent names the linked prediction_id and applied deltas
```

Use a second fixture where:

```text
a previously trusted memory helps form a prediction
later verification contradicts the prediction
```

Expected:

```text
contradiction_burden increases
future retrieval accessibility is reduced or bounded
the same settlement replayed twice does not double-apply the update
```
