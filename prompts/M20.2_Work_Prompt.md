# OpenFEP M20.2 Work Prompt

## Milestone

M20.2: Graded Correction, Revocation, And Slow Promotion Runtime

## Goal

Close the unified-commitment loop by reading `owner.observability[commit_id]`
(M20.1), choosing a graded correction based on `magnitude` and
`outcome`, and routing the correction through the existing owner write
paths (M19.1 traction, M19.3 slow promotion, M9.0 control_guidance,
M15.0 episode aggregation, M11/M17 prediction precision EMA) — without
inventing a new long-term state bucket and without duplicating any
existing owner's mutation logic.

```text
M20.1 owner.observability[commit_id] = SettledValue
   |
   v
+-----------------------------------------------------+
|   GradedCorrectionRuntime (M20.2)                  |
|   - read observability                             |
|   - map (outcome, magnitude, evidence_refs) to     |
|     a GradedCorrection level                       |
|   - route to the existing owner write path         |
|   - emit ActiveCommitmentPromoted / Revoked /      |
|     CorrectionMicroadjusted / CorrectionDeferred   |
+-----------------------------------------------------+
        |
        v
owner write path (M19.1, M19.3, M9.0, M15.0, M11/M17, etc.)
   does its existing work and emits its existing audit events
```

M20.2 owns the **what to do** question. It does **not** own the storage
shape of any owner. Every correction lands on an existing write path.

## Why M20.2 Exists

M19.1 already updates M13 traction when a self-repair expectation is
`confirmed` / `violated`. M19.3 already promotes repeated repair
patterns into `self_cognition.calibrated_tendencies`. M9.0 already
shifts `repair_bias` and `conflict_level`. M17.4 already updates type
precision EMA. M15.1 already consolidates episodes.

Each of these was a small, private, prompt-shaped write. They share the
same question — *given a settled expectation, how strongly should we
update which owner?* — but they answer it independently. M20.2 is the
runtime that asks the question once, maps to a graded level, and routes
to the right existing owner write path.

M20.2 is **not** a new write path. It is a dispatcher with magnitude
thresholds, owner-routing rules, and audit events. The actual mutation
is owned by the existing owner; M20.2 only chooses the level.

## Architecture Position

M20.2 is MVP-local and lives as a sibling runtime to M20.0's
`ActiveCommitmentAdapter` and M20.1's `SettlementScheduler`:

```text
M20.0 admission -> M20.1 settlement -> owner.observability[commit_id]
                                              |
                                              v
                            GradedCorrectionRuntime (M20.2)
                                              |
                +-----------+-----------+-----+-----+----------+
                |           |           |     |     |          |
            microadjust   next_turn  same_turn slow  revoke    expire
                |           |           |     |     |          |
                v           v           v     v     v          v
        M9.0 control_   M13.0        M19.1  M19.3 existing    NoSettlementMade
        guidance       pull_nudge   trac.  slow     owner
        microadjust                  (existing) (existing) revoke path
```

The dispatcher uses M20.0's frozen `owner_id` to pick the owner. Each
owner has a frozen `graded_action_set` that says which correction
levels it accepts. The dispatcher never invents new owner behaviors.

## Non-Goals

- Do not introduce any new long-term state bucket. M20.2 writes only to
  existing owner storage, through existing owner write paths.
- Do not re-implement M19.1 traction logic, M19.3 promotion logic,
  M9.0 control_guidance logic, M17.4 precision EMA logic, or M15.1
  episode aggregation logic. M20.2 routes to them; it does not
  duplicate them.
- Do not let the dispatcher change a settled outcome. M20.1 settled
  values are immutable from M20.2's perspective. If the dispatcher
  disagrees, it emits `Revoked` and routes to the owner's existing
  revocation path; it does not edit the `SettledValue`.
- Do not let microadjust float values become unbounded. M20.2 emits
  bounded `magnitude_after` and `magnitude_before` audit fields; it does
  not store float history.
- Do not let the dispatcher promote a `silent` settler outcome. A
  `silent` settler did not produce a `SettledValue`, so there is no
  `commit_id` for the dispatcher to read. M20.2 only processes
  commitments that have a non-`silent` `SettledValue`.
- Do not let the dispatcher revoke a `pending` or `active` commitment
  whose `SettledValue` was `confirmed`. Revocation is reserved for
  `violated` outcomes, `ambiguous` outcomes with `magnitude >= 0.5`, or
  contradictions from a later settlement.
- Do not let the dispatcher override a M19.3 slow-promotion lock. If
  M19.3 has marked the source expectation `promoted`, M20.2 emits
  `CorrectionDeferred` with `reason_code = "m19_3_already_promoted"`
  and does not re-promote.
- Do not let the dispatcher run on the same turn as settlement. M20.2
  processes `owner.observability[commit_id]` only on T1+1 turns (one
  turn after the settlement turn).
- Do not let the dispatcher write to a `source_kind = "policy"`
  commitment's `observable_payload`. Policy commitments are
  observation-only; their corrections are read-only too.
- Do not touch Path A, M10, `conversation_loop.py`, or
  `SelfThoughtProducer`.

## Required Work

### 1. Freeze the `GradedCorrection` enum

```text
GradedCorrection:
  - "microadjust"        # smallest effect: nudge a float or scalar
                          # within a bounded band
  - "next_turn"          # effect on the next eligible turn only;
                          # pull_nudge into M13.0 / M13.2
  - "same_turn"          # effect on the current turn's reply
                          # guidance; advisory only, must not hard-
                          # force visible text
  - "slow_promote"       # M19.3 slow layer promotion
  - "revoke"             # existing owner revocation path
  - "expire"             # no correction; emit audit-only event
```

Rules:

- M20.2 freezes the enum. Adding a new correction level is a vocabulary
  version bump.
- The dispatcher maps `(outcome, magnitude, evidence_refs)` to one of
  the six levels via frozen rules (§3).
- "slow_promote" routes to M19.3's existing slow promotion path. M20.2
  does not implement slow promotion; it only routes.
- "revoke" routes to the existing owner revocation path. M20.2 does not
  implement revocation; it only routes.

### 2. Freeze the magnitude-to-level thresholds v1

```text
magnitude in [0.0, 0.1)  ->  "expire"  (essentially no signal)
magnitude in [0.1, 0.3)  ->  "microadjust"
magnitude in [0.3, 0.6)  ->  "next_turn"
magnitude in [0.6, 0.85) ->  "same_turn"
magnitude in [0.85, 1.0] ->  "slow_promote"
```

Special cases (frozen, override the table above):

- `outcome = "violated"` AND `magnitude >= 0.85` -> `"revoke"` (the
  dispatcher tries to revoke the existing owner state, not promote it).
- `outcome = "ambiguous"` -> `"expire"` (ambiguity is not enough signal
  to act; we carry forward as `observations_tail` only).
- `outcome = "uncertain"` -> `"microadjust"` only if
  `magnitude >= 0.5`, else `"expire"`.
- `source_kind = "policy"` -> `"expire"` for any outcome. Policy
  commitments are observation-only by M20.0's freeze; corrections to
  them are not allowed.
- M19.3-already-promoted shortcut: if the source expectation_id is
  already in `self_cognition.calibrated_tendencies` (read-only check),
  downgrade `slow_promote` to `CorrectionDeferred` audit event with
  `reason_code = "m19_3_already_promoted"`.

Rules:

- The thresholds are frozen. A change is a vocabulary version bump.
- A `commit_id` whose outcome is `silent` (no `SettledValue`) is never
  dispatched; M20.2 ignores it.
- The dispatcher enforces the source_kind = "policy" rule by reading
  the `ActiveCommitment.source_kind` field, not by re-interpreting
  `observable_payload`.

### 3. Freeze the per-owner `graded_action_set` v1

Extend each row of `CommitmentRegistry` v1 with a `graded_action_set`
declaration:

```text
owner_id: "policy_state"
  graded_action_set: []      # M20.2 cannot correct policy_state
  notes: "policy_state is read-only from M20.2; corrections are
          observation-only"

owner_id: "m13_drive_state"
  graded_action_set: ["microadjust", "next_turn", "same_turn"]
  notes: "M13.0 traction accepts float and pull updates"

owner_id: "m15_episode_ledger"
  graded_action_set: ["microadjust", "next_turn"]
  notes: "M15.1 episode consolidation accepts episode aggregation"

owner_id: "mismatch_memory_fast"
  graded_action_set: ["microadjust", "next_turn", "revoke"]
  notes: "M19.0 fast layer accepts weighted support updates and
          revocation"

owner_id: "self_repair_expectation"
  graded_action_set: ["next_turn", "same_turn", "slow_promote",
                       "revoke"]
  notes: "M19.1 mid layer accepts traction update, slow_promote
          routes to M19.3, revoke routes to M19.1 revocation path"

owner_id: "self_cognition_calibrated_tendencies"
  graded_action_set: ["slow_promote", "revoke"]
  notes: "M19.3 slow layer is the destination of slow_promote; it
          also accepts revocation"

owner_id: "user_prediction_ledger"
  graded_action_set: ["microadjust", "next_turn"]
  notes: "M17.4 type precision EMA accepts precision updates"

owner_id: "memory_dynamics_control_guidance"
  graded_action_set: ["microadjust", "next_turn", "same_turn"]
  notes: "M9.0 control guidance accepts bounded float shifts"

owner_id: "outreach_intent_registry"
  graded_action_set: ["next_turn", "same_turn", "revoke"]
  notes: "M13.3 / M14.x outreach intent accepts timing and revocation
          updates"

owner_id: "group_addressee_graph"
  graded_action_set: ["microadjust", "next_turn"]
  notes: "M18.2 addressee graph accepts bounded policy updates"
```

Rules:

- A correction level not in the owner's `graded_action_set` is rejected
  with `CorrectionRejected` and `reason_code =
  "action_set_violation"`.
- A `slow_promote` correction sent to an owner whose
  `graded_action_set` does not include `slow_promote` is rejected with
  `reason_code = "slow_promote_not_supported"`. The dispatcher does
  not "try anyway" through a different owner.

### 4. Implement the dispatcher

The dispatcher is a small, deterministic function:

```text
dispatch(commitment, settled_value, owner_state_snapshot) ->
    GradedCorrectionDecision:
        correction_level: GradedCorrection
        reason_code: str
        routed_owner_id: str
        evidence_refs: list[str]   # subset of commitment's
                                  # evidence_refs
        magnitude_before: float   # if applicable
        magnitude_after: float    # if applicable (clamped to
                                  # [0.0, 1.0])
        at: str                   # ISO 8601
        turn_index: int
        engineering_proxy_label: str
```

The dispatcher must:

- read `commitment` (immutable from M20.0),
- read `settled_value` (immutable from M20.1),
- read `owner_state_snapshot` (read-only; one read per dispatch),
- map `(outcome, magnitude, source_kind, owner_id, owner_state)`
  through §2 and §3 to a `GradedCorrection`,
- emit a decision.

The dispatcher does NOT:

- mutate any state,
- call any LLM,
- re-interpret `observable_payload`,
- read raw user text or prompt text.

### 5. Route to existing owner write paths

Each `GradedCorrection` value routes to an existing owner write path
that already exists in the codebase. M20.2 only adds the routing glue
and the audit envelope.

Routing v1:

```text
microadjust
  -> if owner_id == "m13_drive_state":
       M13DriveEvaluator.apply_microadjust_traction(...)
  -> if owner_id == "m15_episode_ledger":
       M15EpisodeLedger.apply_microadjust_aggregation(...)
  -> if owner_id == "mismatch_memory_fast":
       M19FastMismatch.apply_microadjust_support(...)
  -> if owner_id == "user_prediction_ledger":
       M17PrecisionEMA.apply_microadjust_precision(...)
  -> if owner_id == "memory_dynamics_control_guidance":
       M9ControlGuidance.apply_microadjust_float(...)
  -> if owner_id == "group_addressee_graph":
       M18AddresseeGraph.apply_microadjust_policy(...)
  -> (no other owner accepts microadjust in v1)

next_turn
  -> routes to owner's existing next-turn update function
  -> for m13_drive_state: M13DriveEvaluator.apply_next_turn_pull
  -> for m15_episode_ledger: M15EpisodeLedger.apply_next_turn_seed
  -> for mismatch_memory_fast:
       M19FastMismatch.apply_next_turn_recurrence
  -> for self_repair_expectation:
       M19RepairExpectation.apply_next_turn_traction
  -> for user_prediction_ledger:
       M17PrecisionEMA.apply_next_turn_precision
  -> for memory_dynamics_control_guidance:
       M9ControlGuidance.apply_next_turn_band
  -> for outreach_intent_registry:
       M13OutreachIntent.apply_next_turn_timing
  -> for group_addressee_graph:
       M18AddresseeGraph.apply_next_turn_target

same_turn
  -> routes to owner's existing same-turn update function
  -> for m13_drive_state:
       M13DriveEvaluator.apply_same_turn_pull_nudge
       (advisory only, no hard-forced text)
  -> for self_repair_expectation:
       M19RepairExpectation.apply_same_turn_repair_guidance
       (advisory only)
  -> for memory_dynamics_control_guidance:
       M9ControlGuidance.apply_same_turn_assertion_strength
       (advisory only)
  -> for outreach_intent_registry:
       M13OutreachIntent.apply_same_turn_cancel
       (advisory; can suppress this turn's outreach)
  -> (no other owner accepts same_turn in v1)

slow_promote
  -> routes to M19.3 slow promotion path:
       M19_3SlowPromotion.apply_promotion(...)
  -> uses existing M19.3 audit events; M20.2 does not invent new
     promotion events
  -> emits CorrectionDeferred with reason_code
     "m19_3_already_promoted" if M19.3 has already promoted

revoke
  -> routes to existing owner revocation path:
       for mismatch_memory_fast:
         M19FastMismatch.apply_revocation(...)
       for self_repair_expectation:
         M19RepairExpectation.apply_revocation(...)
       for self_cognition_calibrated_tendencies:
         M19_3SlowPromotion.apply_revocation(...)
       for outreach_intent_registry:
         M13OutreachIntent.apply_revocation(...)
  -> (no other owner accepts revoke in v1)

expire
  -> no routing
  -> emits CorrectionDeferred audit event with reason_code
     "magnitude_below_threshold" or "policy_source_no_correction"
     or "ambiguous_outcome"
```

Rules:

- Each routing function is a thin wrapper around the existing owner
  write path. M20.2 does not duplicate the write logic.
- A routing function MUST emit the existing owner audit events plus a
  new `GradedCorrectionRouted` event with the `correction_level` and
  the `routed_owner_id`.
- A routing function MUST NOT emit any state the existing owner
  doesn't already know how to emit.

### 7. Bound same_turn guidance so it cannot hard-force text

M20.2's `same_turn` level emits advisory guidance only. The existing
owner write path must be wrapped in a `is_advisory` flag at the call
site so that:

- `m13_drive_state.apply_same_turn_pull_nudge` does not hard-set the
  reply action; it only nudges the priority within the existing reply
  candidate set,
- `self_repair_expectation.apply_same_turn_repair_guidance` only
  modifies `control_guidance` floats, never `reply_text`,
- `memory_dynamics_control_guidance.apply_same_turn_assertion_strength`
  only modifies the `assertion_strength` scalar, never the reply text,
- `outreach_intent_registry.apply_same_turn_cancel` may suppress
  this turn's outreach but does not modify the reply.

If a `same_turn` routing function attempts to write to a non-advisory
field, the existing owner write path MUST refuse and M20.2 must emit
`CorrectionRejected` with `reason_code = "same_turn_not_advisory"`.

This rule exists because M20.2 is the first time the unified
commitment loop has a same-turn path; without the advisory cap, the
loop would short-circuit the conscious loop.

### 8. Honor the M19.3 slow-promotion lock

M19.3 already manages slow promotion. M20.2's `slow_promote` is a
**router** to M19.3, not a parallel promoter. M20.2 must:

- read M19.3's existing `promotion_lock` map (read-only),
- refuse to dispatch `slow_promote` for any `commit_id` whose
  `source_expectation_id` is already in `promotion_lock` (M19.3 owns
  the demotion policy too),
- refuse to dispatch `slow_promote` if M19.3 has already emitted a
  `PromotionLocked` event for the same `source_expectation_id` in the
  same M20.0 epoch.

M20.2 must NOT maintain its own slow-promotion history. The M19.3
promotion lock is the single source of truth.

## Acceptance Criteria

M20.2 is complete only if:

1. `GradedCorrection` enum, magnitude-to-level table, outcome
   override rules, and per-owner `graded_action_set` are all frozen.
2. The dispatcher is a pure function: same inputs -> same decision,
   no LLM call, no state mutation.
3. Routing to existing owner write paths works for every (level,
   owner_id) pair in the routing v1 table in §5, and the existing
   owner audit events fire on the existing owner write path.
4. `slow_promote` short-circuits with `CorrectionDeferred` and
   `reason_code = "m19_3_already_promoted"` when M19.3 has already
   promoted the source expectation.
5. `same_turn` writes are advisory only; any attempt to write a
   non-advisory field is rejected with `CorrectionRejected` and
   `reason_code = "same_turn_not_advisory"`.
6. M20.2 introduces no new long-term state bucket. All writes flow
   through existing owner write paths.
7. M20.2 does not duplicate M19.1 traction logic, M19.3 promotion
   logic, M9.0 control_guidance logic, M17.4 precision EMA logic,
   or M15.1 episode aggregation logic. Tests assert the absence
   of duplication.
8. `policy_state` corrections are observation-only; any non-`expire`
   correction routed there is rejected with `reason_code =
   "policy_source_no_correction"`.
9. The M20.2 acceptance diagnostic counters are exposed in the
   existing diagnose/UI observability surface.
10. The new tests pass.
11. Path A and M10 remain untouched.
12. The existing M20.0 / M20.1 audit events
    (`ActiveCommitmentCreated`, `ActiveCommitmentRejected`,
    `ActiveCommitmentSettled`, `NoSettlementMade`) remain unchanged.

## Verification Standard

The milestone is only accepted if a recorded Path B test turn can show:

```text
ActiveCommitmentCreated(T0)
  -> T0+1 turn: ActiveCommitmentSettled
  -> T0+2 turn: GradedCorrectionRouted (or CorrectionDeferred /
                CorrectionRejected) with the correct
                (correction_level, routed_owner_id, reason_codes)
  -> existing owner audit events fire on the existing owner
     write path
  -> no new long-term state buckets are created
  -> no settler / dispatcher / LLM prompt text appears in
     user-visible chat stream
```

with the recorded trace showing at most one
`GradedCorrectionRouted` per `commit_id`. A second
`GradedCorrectionRouted` on the same `commit_id` MUST NOT appear in
the trace. This proves the action half of the loop is bound to the
existing owner write paths and does not invent a parallel stack.

The same trace format, replayed against a M20.0 / M20.1 / M20.2
stack, MUST end with the same observable behavior as a hand-run
counterfactual: the existing owner state at the trace's end is the
same whether the correction was routed through M20.2 or applied
manually. (Equality is checked on the existing owner state, not on
the M20.2 audit log.)

## Engineering Phenomenology Boundary

M20.2 is a dispatcher. It may create the engineering preconditions for
"every commitment flows through the same graded correction" but it
must not claim that the unified commitment loop is closed in a way
that bypasses the conscious loop. `same_turn` corrections are
advisory only. Visible reply text still flows through the conscious
loop, the thinking stage, the reply validation, and the M19.x surface
consistency check.

M20.2 may create the conditions for "behavioral drift in matching
contexts" (M19.1 already does this) but it must not script visible
apology, self-blame, or "I was wrong" text. M19.1 / M19.3 own that
boundary; M20.2 must not expand it.
