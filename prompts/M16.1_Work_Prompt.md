# OpenFEP M16.1 Work Prompt

## Milestone

M16.1: Python Consciousness Runner Service And Gateway

## Goal

Implement the persistent Path B consciousness runner and a thin FastAPI/WebSocket
gateway defined in M16.0.

After M16.1:

```text
One persona+session runner process owns the self-loop.
User input enters through durable perception events.
Silence-period cognition ticks fire on runner schedule, not UI reruns.
Ready WebSocket clients count as a delivery surface for M13.3 outbox drain.
Streamlit is no longer an acceptance scheduler for proactive behavior.
```

The runner reuses existing cognition modules; it does not fork a second persona
stack.

## Architecture Position

```text
FastAPI gateway (m16_api.py)
  -> append perception events (M14.2 store)
  -> start/stop/status for runner subprocess or in-process task
  -> WS fan-out of durable actuation/audit events

ConsciousnessRunner (m16_runner.py)
  -> runner lock (extend M14.1/M14.2 patterns)
  -> loop:
       claim perception events
       if ClientInputCommittedEvent:
           MVPDialogueRuntime.run_turn
       else on timer/budget:
           M13.5 idle cognitive tick
           M14.0 idle introspection when structural + budget allow
           M14.1 background continuity slice
           M15.1 consolidation defer/check
           M15.2 / M15.3 detectors on existing entry points
       drain queued_outreach when delivery surface ready
       append actuation events and publish to gateway subscribers
       sleep bounded interval
```

Hard wiring rules:

- Gateway threads must not call `run_turn`, `run_idle_cognitive_tick`, or
  `run_proactive_turn` directly except in tests through the runner API.
- Gateway threads may validate, append, and notify only. If a request path can
  produce assistant text synchronously, the implementation is wrong.
- All durable state writes remain inside existing owners and `MVPStateStore`.
- Visible assistant text still comes only from M13.3 generation + assessor +
  reply validation.
- Semantic interpretation stays in LLM JSON stages; gateway validates and
  routes only.
- WS fan-out is not the durable source of truth. Restart and reconnect must
  recover from event logs, state store, and bounded snapshots.

## Dependencies

Hard:

- M16.0 protocol schemas and architecture contract
- M14.2 environment event bus and daemon lock patterns
- M14.1 background budgets and queued outreach
- `MVPDialogueRuntime`, `MVPStateStore`, `ChatInterface` facades
- M13.3 proactive pipeline
- M13.5, M14.0, M15.0–M15.3 existing entry points

Soft:

- M14.4 Streamlit implicit idle (leave in place but mark non-acceptance)

## Non-Goals

- Do not implement TypeScript clients (M16.2–M16.4).
- Do not remove Streamlit yet; only stop requiring it for acceptance tests.
- Do not merge Path A and Path B.
- Do not add hosted push/email/SMS.
- Do not bypass M13.3 safety, cooldown, or delivery assessor just because a WS
  client is connected or has sent `DeliverySurfaceReady`.
- Do not run unbounded LLM loops; M14.1 daily budgets still apply.

## Required Work

### 1. Runner Core

Add:

```text
segmentum/dialogue/runtime/m16_runner.py
```

Minimum public API:

```text
class ConsciousnessRunner:
    start() -> RunnerStatus
    stop(*, graceful_seconds=15) -> RunnerStatus
    status() -> RunnerStatus
    run_once_for_tests(*, now, max_steps=1) -> RunnerStepResult
```

Runner loop responsibilities:

- acquire persona+session lock; refuse second live runner,
- claim M14.2 events with leases and idempotency keys,
- translate `ClientInputCommittedEvent` into user turn execution,
- schedule silence ticks using internal timer + existing structural signals,
- never call full conscious loop with empty `conscious_plan` as a substitute
  for M14.0 when LLM is available and budgets allow,
- record `RunnerHealthEvent` each cycle with compact counters,
- honor opt-out flags from initiative state,
- recover leased-but-uncommitted events on restart without double-delivering
  visible assistant text.

Silence tick order must match Path B contract:

```text
environment claim
-> optional M13.5 idle cognitive refresh
-> optional M14.0 introspection
-> M15.2 detection hooks on those entry points
-> optional outbox drain
-> publish audits to WS + conversation_log
```

### 2. FastAPI Gateway

Add:

```text
segmentum/dialogue/runtime/m16_api.py
segmentum/dialogue/runtime/m16_ws_hub.py
```

Entry command:

```text
python -m segmentum.dialogue.runtime.m16_api \
  --host 127.0.0.1 --port 8765 \
  --persona 胡桃 --session <session_id>
```

Gateway responsibilities:

- implement M16.0 HTTP routes,
- authenticate locally by default (dev token or localhost-only bind),
- on `POST /input`, append perception event and nudge runner; return `202`,
- maintain WS subscriber registry per session,
- project durable runner actuation/audit events into WS server messages,
- emit `DeliverySurfaceConnectedEvent` / `DisconnectedEvent` on WS lifecycle,
- expose `/runner/status` reflecting lock owner, pid, last_health, budgets.

Use `uvicorn` programmatically; add dependency in project metadata if missing.

### 4. Delivery Surface Integration

When at least one WS client sends `DeliverySurfaceReady`:

- append `DeliverySurfaceReadyEvent` with freshness TTL,
- append `OutboxDeliverySurfaceAvailableEvent` (reuse M14.2 type),
- runner may drain `queued_outreach.jsonl` through existing M13.3 path,
- on successful proactive/normal assistant delivery, emit WS
  `AssistantMessageCommitted` or `ProactiveMessageCommitted`.

When no delivery surface is ready:

- runner may still think, audit, and queue; it must not invent a UI.
- queued messages must remain durable and idempotent until a ready delivery
  surface appears or existing suppression/expiry rules apply.

## Acceptance Criteria

M16.1 is complete when:

1. A standalone runner can process user input and silence ticks with Streamlit
   closed.
2. FastAPI HTTP + WS implement the M16.0 contract.
3. Gateway never executes cognition inline on request threads.
4. Fresh `DeliverySurfaceReady` over WS enables M13.3 outbox drain via existing
   assessor path.
5. Runner lock, budgets, opt-out, and M15.2 biases still apply.
6. All listed tests pass with stubs/fake clocks.
7. Streamlit path still works but is documented as legacy/non-acceptance for
   proactive scheduling.

## Roadmap Note

M16.2 should consume the stabilized WS/HTTP contract without changing message
kinds. Avoid breaking schema versions after M16.1 lands.
