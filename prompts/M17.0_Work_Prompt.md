# OpenFEP M17.0 Work Prompt

## Milestone

M17.0: Prediction Lock And Confidence Contract

## Goal

Turn the existing M11 `UserPredictionLedger` from a mostly post-hoc user-model
audit into a strict T0 prediction contract:

```text
before assistant response is generated
-> produce 3-5 bounded predictions about the next observable user/session outcome
-> normalize raw LLM confidence into committed_confidence
-> append immutable pending rows with created_before_response=true
-> expose those rows to the next-turn settlement path
```

This milestone does not implement surprise, memory-gate learning, or offline
ablation. It only makes the first half of the loop falsifiable: predictions must
exist before the observation that can confirm or violate them.

The intended architecture principle is:

```text
LLM may place forward bets.
Deterministic code owns committed confidence, immutability, and audit.
The same LLM must not assign its own post-hoc surprise.
```

## Architecture Position

M17 starts after M16.4. All work targets Path B through the M16 runner and
`MVPDialogueRuntime`; Streamlit remains legacy I/O only.

```text
MVPDialogueRuntime.run_turn
  -> read prior pending predictions for context
  -> conscious loop / M11 user-model extractor proposes next-turn predictions
  -> ConfidenceNormalizer clamps raw confidences
  -> PredictionLockOwner appends pending UserPredictionLedger rows
  -> assistant response generation continues
```

M17.0 should extend existing M11 structures, not create a second ledger:

```text
segmentum/user_model/prediction_ledger.py
segmentum/user_model/llm_extractor.py
segmentum/user_model/m11_runtime.py
segmentum/dialogue/runtime/mvp_loop.py
```

If the current `prediction_type` names remain verbose, keep them for
compatibility and add a normalized alias only in helper code:

```text
intent_prediction              -> intent
preference_prediction          -> preference
reaction_prediction            -> reaction
claim_reliability_prediction   -> policy_success or reliability
relationship_state_prediction  -> relationship
needed_memory_prediction       -> memory_need
```

Do not expand the ontology beyond these six types in this milestone.

## Dependencies

Hard:

- M11.0 `UserPredictionLedger`, `prediction_proposals`, and extractor schema
- M13.2 settlement assessor output shape, for future next-turn linkage
- M15.0 episode ledger, read-only for current turn ids and audit references
- M16 runner/gateway as the active Path B orchestration layer

Soft:

- M14.7 memory gate fields, read-only for evidence references
- Existing `pending_expectations`, for bridge references only

## Non-Goals

- Do not calculate prediction error or surprise in M17.0.
- Do not change MemoryGate write scoring in this milestone.
- Do not build the offline replay harness yet.
- Do not implement full active inference or continuous probability models.
- Do not let the LLM emit final committed confidence directly.
- Do not accept predictions without evidence references or creation ordering.
- Do not settle predictions in the same call that creates them unless the row
  was already pending before the current user observation.
- Do not touch Path A, M10, `conversation_loop.py`, or `SelfThoughtProducer`.

## Required Work

### 1. Extend prediction ledger rows

Update `segmentum/user_model/prediction_ledger.py` so pending prediction rows can
carry numeric confidence and T0 lock metadata while preserving legacy fields:

```text
PredictionEntry:
  prediction_id
  turn_id
  prediction_type
  predicted_value_summary
  confidence_band                    # legacy compatibility
  raw_confidence: float              # LLM proposal, clamped to [0, 1]
  committed_confidence: float        # deterministic final confidence
  confidence_cap_reason: str
  evidence_basis: list[str]
  evidence_refs
  expires_after_turns
  created_at_turn
  created_before_response: bool
  response_turn_id: int
  status: pending|confirmed|violated|uncertain|expired
  event_kind: prediction|judgment|expiration
```

Compatibility rules:

- Existing JSON payloads without numeric confidence must load successfully.
- If only `confidence_band` exists, map low/med/high to conservative numeric
  defaults: `0.55`, `0.65`, `0.75`.
- New rows must always write `raw_confidence` and `committed_confidence`.
- Pending prediction rows are append-only; later milestones append judgment rows
  instead of mutating the original row.

### 2. Add ConfidenceNormalizer

Add a deterministic helper, preferably in
`segmentum/user_model/prediction_ledger.py` or a small sibling module:

```text
normalize_prediction_confidence(
  raw_confidence,
  prediction_type,
  evidence_basis,
  type_precision=None,
) -> NormalizedConfidence
```

First-version caps:

```text
no evidence_basis                         -> max 0.55
current_user_question only                -> max 0.72
direct user statement evidence            -> max 0.80
repeated evidence or prior confirmation   -> max 0.85
explicit product/system invariant         -> max 0.90
```

Rules:

- Clamp input to `[0.50, 0.90]`; predictions below 0.50 are not useful bets.
- If type precision is supplied, shrink overconfident predictions toward the
  type precision estimate.
- Store both raw and committed confidence.
- Return a machine-readable cap reason.

This is not a semantic keyword parser. `evidence_basis` must come from bounded
structured extractor fields or known upstream evidence ids, not regex over raw
user text.

### 3. Update extractor schema

Update `segmentum/user_model/llm_extractor.py` so `prediction_proposals` accept:

```json
{
  "id": "next_turn_pref_impl_detail",
  "prediction_type": "preference_prediction",
  "claim": "User will prefer implementation-level guidance over theory-only response.",
  "raw_confidence": 0.76,
  "evidence_basis": ["current_user_request", "recent_topic_continuity"],
  "evidence_quote_ids": ["turn_123_user"]
}
```

Validation rules:

- Limit to 3-5 accepted proposals per assistant turn.
- `claim` / `predicted_value_summary` is capped to 200 characters.
- Invalid confidence becomes `0.50`, then normalizer applies caps.
- Invalid or missing evidence makes the proposal reject or cap at 0.55, based on
  existing M11 proposal-admission style.

### 4. Wire T0 lock into Path B

In `segmentum/user_model/m11_runtime.py` and `mvp_loop.py`, ensure prediction
creation happens after the system has observed the current user turn but before
the assistant response for that turn is committed.

Required audit event:

```json
{
  "type": "PredictionLockedEvent",
  "turn_index": 42,
  "prediction_ids": ["pred:..."],
  "prediction_count": 4,
  "created_before_response": true,
  "max_committed_confidence": 0.78,
  "engineering_proxy_label": "mvp_local_prediction_lock"
}
```

If no valid prediction can be made, emit:

```json
{
  "type": "PredictionLockSkippedEvent",
  "reason_code": "no_valid_evidence|proposal_quota_empty|extractor_unavailable"
}
```

Skipping is allowed, but silent absence is not.

### 5. State and diagnostics

Expose bounded diagnostics in existing debug surfaces:

```text
pending_prediction_count
latest_prediction_lock_turn
prediction_type_counts
confidence_cap_reason_counts
```

Do not expose raw prompt text or full ledger dumps to the default user-visible
chat stream.

## Acceptance Criteria

M17.0 is complete when:

1. Every accepted new prediction has numeric `committed_confidence`.
2. Accepted predictions carry evidence basis and are created before response
   commit.
3. Existing M11 ledger fixtures still load.
4. Missing prediction proposals produce an explicit skip audit event.
5. No post-observation surprise or error score is computed in this milestone.
6. New tests pass.
7. Path A and M10 remain untouched.

## Verification Standard

The milestone is only accepted if a recorded Path B test turn can show:

```text
PredictionLockedEvent.timestamp < AssistantMessageCommitted.timestamp
pending prediction row.created_before_response == true
pending prediction row.committed_confidence in [0.50, 0.90]
```

This is the foundation for later falsification. Without this ordering proof,
M17.1 and M17.2 must not proceed.
