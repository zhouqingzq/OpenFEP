# OpenFEP M17.10 Work Prompt

## Milestone

M17.10: Goal Priors And Adaptive Compute Control

## Goal

Make active goals shape prediction priors directly and make compute spend rise
or fall with uncertainty, conflict, and field structure.

Target contract:

```text
active goal state
  -> bounded prior shaping before action ranking
  -> local field / uncertainty diagnostics
  -> adaptive compute controller
  -> cheap reuse when confidence is high
  -> deeper retrieval / verification / counterfactual work when conflict is high
```

This milestone operationalizes two ideas:

- goals are not only reranking preferences; they are prior-shaping constraints
- low-error stable regions should be cheap, high-conflict regions should spend
  more compute

Adaptive compute keyed off field geometry is the cleanest available evidence
that the local field does something fixed top-k cannot: a top-k system always
does the same amount of work, so a system that spends less in low-Φ basins and
more on Φ ridges/saddles is expressing a behavior top-k cannot represent. Treat
this milestone as the primary non-decorative validation of the M17.9 field.

Scope note: the adjustable budgets here are the core survival runtime's analogue
of "skip vs escalate deliberation" — retrieval breadth, verification depth,
counterfactual/replay depth. This is not the Path B multi-agent chat
orchestrator; do not import a multi-agent bundle-escalation mechanism. The
escalation surface is the survival agent's own bounded budgets.

## Architecture Position

```text
GoalStack / active goal
  -> goal prior adapter
  -> world-model prediction
  -> local field diagnostics
  -> adaptive compute controller
  -> retrieval budget / verification budget / counterfactual budget
  -> final policy evaluation
```

Recommended landing points:

```text
segmentum/preferences.py
segmentum/agent.py
segmentum/world_model.py
segmentum/metacognitive.py
segmentum/meta_control.py
```

If helper modules are added, prefer:

```text
segmentum/goal_priors.py
segmentum/adaptive_compute.py
```

## Dependencies

Hard:

- M17.9 local field diagnostics
- Existing `GoalStack` and goal-alignment scoring
- Existing verification / inquiry / counterfactual hooks

Soft:

- Existing meta-control or cognitive-control state
- Existing retrieval-gain adjustment surfaces

Compatibility-sensitive:

- Existing `goal_alignment_score` and post-hoc reranking logic
- Existing fixed-budget retrieval or verification paths
- Existing traces that do not distinguish cheap stable decisions from escalated
  high-conflict decisions

## Non-Goals

- Do not build an unbounded planner.
- Do not let goals arbitrarily overwrite observed evidence.
- Do not spend more compute simply because more modules exist.
- Do not collapse goal priors back into a post-hoc `goal_alignment_score`
  rename.
- Do not touch Path A or M10.

## Required Work

### 1. Add an explicit goal-prior adapter and owner

Introduce a bounded adapter from active goals to predictive priors:

```text
GoalPriorAdjustment:
  active_goal
  prior_channel_shifts
  confidence
  reason_codes
```

Rules:

- Goal priors must act before final policy reranking.
- They must be bounded and auditable by channel.
- They must not erase strong contradictory observation.
- The adapter must name which channels were shifted and why.
- If multiple active goals exist, the implementation must specify how they are
  combined or prioritized.

Recommended channels:

```text
safety_prior_shift
energy_preservation_shift
exploration_shift
social_stability_shift
repair_or_seek_shift
```

### 2. Make prediction differ by active goal before final reranking

At least one predictive stage must differ under different active goals even
before final action ranking, for example:

```text
world-model priors
path/field weighting
expected outcome projection
```

If the only change remains `goal_alignment_score` at the end of ranking, the
milestone is not complete.

Requirements:

- the same observation under different active goals must be able to yield
  different predicted trajectories or path weighting
- the effect must be visible in structured diagnostics, not only inferred from
  different final actions

### 3. Add adaptive compute control and bounded regimes

Define a bounded control object such as:

```text
AdaptiveComputeDecision:
  retrieval_k
  verification_budget
  counterfactual_budget
  field_refinement_enabled
  escalation_reason_codes
confidence_regime: low|medium|high
```

Inputs may include:

```text
field_flatness
conflict_density
prediction_error_surrogate
verification pressure
goal urgency
```

Recommended first-version constants:

```text
LOW_CONFLICT_FLATNESS_MAX
HIGH_CONFLICT_DENSITY_MIN
LOW_ERROR_FE_MAX
HIGH_URGENCY_GOAL_MIN
```

If implementation chooses different thresholds, it must document them and make
them visible to tests or diagnostics.

### 4. Wire at least three adjustable budgets or depths

Adaptive control must affect at least three live bounded budgets, for example:

```text
retrieval top-N or path neighborhood size
verification target depth
counterfactual or replay depth
```

The controller must be able to do both:

```text
de-escalate compute in stable low-conflict regions
escalate compute in flat, conflicting, or high-error regions
```

First shipped version must prove both directions:

- compute can become cheaper in stable regimes
- compute can become more expensive in uncertain regimes

Both directions must be validated against the M17.5 FE surrogate outcome, not
just against spend:

- de-escalation in a low-Φ stable regime must not raise subsequent FE surrogate
  relative to the always-escalate baseline (cheap was safe)
- escalation in a flat/conflicted regime must reduce subsequent FE surrogate, or
  at least improve the field's `fe_advantage`, relative to the cheap baseline
  (spending bought something)

If escalation spends more without improving the surrogate, audit it as
`escalation_no_gain` rather than counting it as adaptive control.

### 5. Add decision audit and budget traceability

The runtime must be able to explain:

```text
which active goal shaped priors
how priors changed prediction
why compute stayed cheap or escalated
```

Recommended event family:

```text
GoalPriorAppliedEvent
AdaptiveComputeDecisionEvent
AdaptiveComputeSuppressedEvent
```

Minimum fields:

```text
active_goal_ids
prior_channel_shifts
field_flatness
conflict_density
prediction_error_surrogate
selected_budgets
escalation_reason_codes
```

### 6. Add bounded tests for cheap reuse vs costly uncertainty

There must be deterministic cases showing:

- same observation, different active goal, different predicted state
- stable low-conflict state, reduced compute spend
- flat or conflicting field, increased compute spend

- strong contradictory observation limits the effect of goal prior shaping

## Acceptance Criteria

M17.10 is complete when:

1. Active goals influence at least one predictive stage before final action
   reranking.
2. Goal priors are bounded, channel-auditable, and do not silently overwrite
   observation.
3. The runtime has a bounded adaptive compute owner.
4. At least three live budgets or depths are adjusted by adaptive compute.
5. Stable low-conflict states can run cheaper than ambiguous or conflicting
   states.
6. Cheap and escalated regimes are validated against the M17.5 FE surrogate
   outcome: de-escalation does not raise subsequent FE, and escalation reduces it
   or is audited as `escalation_no_gain`.
7. Decision traces can explain both goal-prior shaping and compute escalation
   or de-escalation.
8. The implementation remains deterministic and bounded.
9. Path A and M10 remain untouched.

## Verification Standard

Use one fixture where:

```text
the observation is the same
the active goal differs between energy-preservation and exploration
field structure is otherwise stable
```

Expected:

```text
GoalPriorAppliedEvent shows different prior_channel_shifts
the predictive stage changes before final action reranking
the difference is not explained only by goal_alignment_score
```

Use a second fixture where:

```text
the local field is flat or conflict-dense
prediction_error_surrogate is elevated
goal urgency is non-zero
```

Expected:

```text
AdaptiveComputeDecision selects higher retrieval and verification budgets
the same controller can choose a cheaper regime in a stable low-conflict fixture
decision traces explain both escalation and de-escalation
```
