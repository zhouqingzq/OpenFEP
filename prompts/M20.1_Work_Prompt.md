# OpenFEP M20.1 Work Prompt

## Milestone

M20.1: Settler Protocol And Observable Settlement Runtime

## Goal

Implement the settler runtime that turns an admitted `ActiveCommitment` (M20.0)
into a bounded settled value, using the four settler types frozen in
`Observable` v1 (`deterministic` / `llm_judge` / `hybrid` / `silent`). M20.1
closes the **observation half** of the unified-commitment loop without yet
deciding what to do with the settled value.

```text
M20.0 admitted ActiveCommitment (commit_id, observable, payload, evidence_refs)
        |
        v
+-------------------------------------------------------+
|        SettlerRuntime (M20.1)                        |
|  - route by observable -> settler type (hint)         |
|  - admit + bound inputs (no payload re-interpretation)|
|  - call settler: deterministic | llm_judge |          |
|                  hybrid (deterministic -> llm fallback)|
|                  silent (no settle, observations_tail)|
|  - emit ActiveCommitmentSettled or NoSettlementMade   |
+-------------------------------------------------------+
        |
        v
owner.observability surfaces read the settled value
(M20.2 will own the graded correction that mutates guidance)
```

M20.1 owns the **what happened** question. It does **not** own the **what to
do about it** question. Promotion, demotion, microadjust, same-turn repair,
slow promotion, and revocation are explicitly out of scope and belong to
M20.2.

## Why M20.1 Exists

M19.0 settled `self_expectation_outcome_results` with the conscious loop.
M19.1 added `self_repair_expectation` verify_on (`next_similar_turn` /
`natural_idle_shadow_eval`). M17.1 settled `prediction_error` deterministically.
M13.2 used a scalar band. M9.0 updated `repair_bias` floats. M15.0 writes
episodes. M18.5 has its own boundary-handling LLM judge.

Each of these settlers was a small private function with its own prompt
shape, return type, and audit event. They cannot easily share:

- a single audit envelope (`ActiveCommitmentSettled`),
- a single admission rule (must be in `Observable` v1),
- a single timing protocol (when is settlement attempted),
- a single confidence-and-band schema,
- a single failure-handling path (`NoSettlementMade` with reason code).

M20.1 builds the runtime that all of them can speak through, without yet
re-implementing the existing per-loop settlers. M20.1.1 (future) maps the
existing per-loop settlers onto the new runtime; M20.1 itself only
**adds** the runtime and a small number of reference settlers for the
cleanest observables.

## Architecture Position

M20.1 is MVP-local and lives as a sibling runtime to M20.0's
`ActiveCommitmentAdapter`:

```text
owner write path returns commit_id
   |
   v
SettlementScheduler (M20.1)
   |
   v
On eligible observation turn (T1):
   ActiveCommitment.commit_id
   -> route by observable -> settler
   -> bounded input (commitment + eligible state)
   -> settler returns SettledValue | NoSettlement
   -> emit ActiveCommitmentSettled or NoSettlementMade audit event
   -> owner.observability[commit_id] = SettledValue
```

The scheduler decides *when* to attempt settlement. The settler decides
*how* to interpret the observable payload into a settled value. The owner
decides *what to do* with it (which is empty in M20.1: owners just receive
and audit).

Hard:

- M20.0 frozen `ActiveCommitment`, `CommitmentRegistry` v1, `Observable` v1,

- M19.0 self_expectation_outcome_results shape (read-only; reference for

- M19.1 self_repair_expectation `verify_on` semantics (read-only;

- M13.2 `prediction_error_proxy` band shape (read-only; reference for
  deterministic band thresholds)
- M16.4 streamlit-deprecation boundary

Soft (read-only):

- M15.0 episode ledger shape (only for `episodic` source alignment)
- M11 legacy `prediction_judgments` (must remain unmigrated)

## Non-Goals

- Do not implement any promotion, demotion, microadjust, same-turn repair,
  slow promotion, revocation, or expiration logic. That is M20.2.
- Do not let the settler re-interpret or re-prompt the
  `observable_payload`. M20.0 freezes the payload schema; M20.1 only
  *reads* it. The LLM judge may only ask the LLM to bind the payload to a
  frozen outcome enum (`confirmed` / `violated` / `uncertain` /
  `ambiguous`).
- Do not let the settler recompute `confidence` or `priority`. Both were
  set at admission and remain immutable until M20.2 (which may add
  `magnitude` but not modify `confidence`).
- Do not write to `self_cognition`, `m13_drive_state`, `memory_dynamics`,
  `self_repair_expectation`, `mismatch_memory_fast`, or any long-term
  state bucket. M20.1 only writes to
  `owner.observability[commit_id]`, an audit-only artifact.
- Do not let an LLM judge settler call into a different LLM judge settler
  in the same settlement attempt (no nested judges).
- Do not refactor the existing per-loop settlers (M17.1, M19.0 outcome
  settlement, M13.2 band check, M15.0 episode aggregation, M18.5 boundary
  judgment). M20.1 builds a parallel runtime. A later M20.1.1 milestone
  migrates them.
- Do not let the settler attempt settlement on the same turn as
  admission (T0). Settlement attempts are T1 or later; see §4.
- Do not settle a commitment whose `due_at` is past — emit
  `NoSettlementMade` with `reason_code="due_at_passed"`.
- Do not let a hybrid settler fall back to a non-deterministic LLM judge
  more than once per attempt.
- Do not touch Path A, M10, `conversation_loop.py`, or
  `SelfThoughtProducer`.

## Required Work

### 1. Freeze the `SettledValue` schema

Define a frozen shape that all settlers return:

```text
SettledValue:
  commit_id: str                  # the commitment being settled
  outcome: str                    # bounded enum, see §2
  magnitude: float                # [0.0, 1.0], see §3
  evidence_refs: list[str]        # non-empty, subset of commitment's
                                  # evidence_refs + new observation refs
  reason_codes: list[str]         # bounded, see §4
  at: str                         # ISO 8601
  turn_index: int
  settler_type: str               # "deterministic" | "llm_judge" |
                                  # "hybrid" | "silent"
  engineering_proxy_label: str    # bounded, copied from commitment
```

Rules:

- `commit_id` MUST match a `commit_id` from a prior
  `ActiveCommitmentCreated` event.
- `outcome` MUST be one of the bounded enum values (§2).
- `magnitude` MUST be in `[0.0, 1.0]`. It is *not* confidence. It is the
  ε-magnitude the promoter (M20.2) reads to choose graded correction
  intensity. M20.1 freezes the field and emits it; the semantics are
  owned by M20.2.
- `evidence_refs` MUST be non-empty. A settler MUST NOT invent new
  evidence ids; it may only pick from the commitment's
  `evidence_refs` plus bounded turn-local observation handles
  (`turn_<n>_<slot>`).
- `reason_codes` MUST be a non-empty subset of M20.0's `reason_codes` v1.
- A commitment that cannot be settled (e.g., the settler was unavailable,
  the input was incomplete, the timing window was wrong) MUST emit
  `NoSettlementMade` instead of a `SettledValue`. See §6.

### 2. Freeze the `outcome` enum v1

```text
outcome:
  - "confirmed"        # the observable matched what the commitment
                        # expected
  - "violated"         # the observable contradicted the commitment
  - "uncertain"        # evidence was ambiguous but not contradictory
  - "ambiguous"        # multiple conflicting observations present
```

Mapping to Observable v1:

```text
expectation_outcome_match       -> "confirmed" | "violated" | "uncertain"
                                  (copies M19.0 outcome_results enum)
prediction_error_band           -> "confirmed" | "violated" | "uncertain"
                                  (band matched expected band)
repair_bias_band                -> "confirmed" | "violated" | "uncertain"
behavioral_pull_shift           -> "confirmed" | "violated" | "uncertain"
                                  (delta sign matched expectation)
mismatch_type_band              -> "confirmed" | "violated" | "uncertain"
pacing_match                    -> "confirmed" | "violated" | "ambiguous"
identity_voice_match            -> "confirmed" | "violated" | "ambiguous"
boundary_handled                -> "confirmed" | "violated" | "ambiguous"
initiative_timing_match         -> "confirmed" | "violated" | "uncertain"
silent_then_resolved            -> "confirmed" | "violated"
traction_delta_band             -> "confirmed" | "violated" | "uncertain"
```

Rules:

- M20.1 freezes the mapping per observable. A new outcome is a vocabulary
  version bump.
- Settlers MUST return one of the four outcomes. There is no "no result"
  return path; the only non-result is `NoSettlementMade` (see §6).

### 3. Compute `magnitude` deterministically

`magnitude` is the ε-size of the settlement. M20.1 emits a single,
deterministic, frozen formula:

```text
magnitude = |committed_value - expected_value| / max_observable_scale
```

where:

- `committed_value` is the value the observable payload actually carried
  (e.g., the band's high/low, the pull delta, the silence turn count).
- `expected_value` is the value the commitment expected (from
  `observable_payload` and the owner's stored priors, read-only).
- `max_observable_scale` is a frozen per-observable constant in §3a.

If the observable is binary (e.g., `boundary_handled` outcome
`preserved` vs `leaked`), magnitude is `1.0` on any settlement.

If the observable has no numeric value, magnitude is `0.5` and the
`reason_codes` MUST include `magnitude_defaulted`.

#### 3a. Frozen magnitude scales per observable

```text
expectation_outcome_match       -> 1.0    # binary
prediction_error_band           -> 1.0    # band delta is {0,1,2} -> /2
repair_bias_band                -> 1.0
behavioral_pull_shift           -> 0.5    # delta range [-1, 1] -> /2
mismatch_type_band              -> 1.0
pacing_match                    -> 1.0    # binary
identity_voice_match            -> 1.0    # binary
boundary_handled                -> 1.0    # binary
initiative_timing_match         -> 1.0    # categorical
silent_then_resolved            -> 1.0    # binary
traction_delta_band             -> 0.5
```

Rules:

- M20.1 freezes the per-observable scale constants. A change is a
  vocabulary version bump.
- All scales are non-zero. A scale of `0.0` is rejected.

### 4. Add reason codes for the settler side

Extend the existing `reason_codes` v1 (M20.0) with settler-side reasons
(frozen list v1):

```text
reason_codes (additive, M20.1):
  - "settler_deterministic"
  - "settler_llm_judge"
  - "settler_hybrid_fallback"
  - "settler_silent_carry_forward"
  - "magnitude_defaulted"
  - "evidence_ref_filtered"
  - "due_at_passed"               # also reused by NoSettlementMade
  - "settler_unavailable"         # also reused by NoSettlementMade
  - "no_eligible_observation"     # also reused by NoSettlementMade
```

Rules:

- A `SettledValue` MUST include at least one settler-side code.
- A `NoSettlementMade` MUST include at least one of `due_at_passed`,
  `settler_unavailable`, `no_eligible_observation`, or an
  M20.0-vocabulary code that the settler decided to surface.

### 5. Implement the four settler types

All four settler types implement the same interface:

```text
class Settler(Protocol):
    def settle(
        self,
        commitment: ActiveCommitment,
        observation_context: ObservationContext,
    ) -> SettledValue | NoSettlement:
        ...
```

#### 5a. `deterministic` settler

Pure function. Inputs:

- the `ActiveCommitment` (read-only),
- the `ObservationContext` (read-only, built by the scheduler from
  eligible evidence rows on the current turn).

Output: `SettledValue` with `settler_type = "deterministic"` and one of the
four outcomes from §2.

Required reference implementations for v1 (M20.1 ships these; later
milestones can add more):

- `ExpectationOutcomeMatchDeterministicSettler` — reads
  `M19.0 self_expectation_outcome_results` rows for the same
  `source_expectation_id` and `target_context`. If found, returns
  `confirmed` / `violated` / `uncertain` matching the LLM's outcome.
- `PredictionErrorBandDeterministicSettler` — reads the latest
  `M13.2 settlement_id` for the same `prediction_id`. Compares
  `prediction_error_band` band to the expected band in
  `observable_payload`. Returns `confirmed` if matched, `violated` if
  not, `uncertain` if the band is missing.

Both reference settlers MUST be deterministic, MUST NOT call an LLM, and
MUST be re-runnable with the same inputs and produce the same
`SettledValue`.

#### 5b. `llm_judge` settler

Bounded LLM call. Inputs:

- the `ActiveCommitment` (read-only),
- the `ObservationContext` (read-only, including bounded `excerpts`
  lists).

The settler calls a single LLM request with a frozen prompt template
that:

- instructs the LLM to return a bounded JSON object with `outcome` in
  `{confirmed, violated, uncertain, ambiguous}` plus bounded
  `evidence_span` and `reason` strings,
- forbids regex/keyword cues and free-form reasoning,
- caps `evidence_span` at 80 characters,
- caps `reason` at 200 characters.

Output: `SettledValue` with `settler_type = "llm_judge"`. If the LLM is
unavailable, the LLM times out, the response fails schema validation,
or the LLM returns a non-frozen outcome, the settler MUST return
`NoSettlement` with `reason_code = "settler_unavailable"` or
`settler_llm_invalid_response`.

Required reference implementations:

- `IdentityVoiceMatchLLMJudgeSettler` — wraps the existing
  `surface_consistency_verification` LLM call (M19.x). On a clean
  `surface_intent_outcome`, returns `confirmed`. On `drifted_self_id` or
  `drifted_voice`, returns `violated`. On `ambiguous`, returns
  `ambiguous`. Maps the LLM `confidence` to magnitude using §3
  (`binary` so `1.0`; the LLM `confidence` is not stored as magnitude).
- `BoundaryHandledLLMJudgeSettler` — produces a small new bounded
  LLM-judge call that mirrors the surface-consistency shape. It
  returns `confirmed` if `boundary_kind` is `preserved`, `violated` if
  `leaked`, `ambiguous` if `ambiguous`. The LLM prompt is a small
  addition to `build_surface_consistency_verification_prompt`-style
  builders; the LLM does not interpret free-form user text.

#### 5c. `hybrid` settler

Try deterministic first. If the deterministic leg produces
`uncertain` or `ambiguous` *and* the magnitude_defaulted flag is set
*and* the observable's `settler_hint` is `hybrid`, fall back to a single
LLM judge call.

Rules:

- The deterministic leg is required. There is no hybrid settler without
  a deterministic first leg.
- The LLM fallback may run at most once per settlement attempt.
- If both legs fail, return `NoSettlement` with `reason_code =
  "settler_hybrid_fallback_exhausted"`.

Required reference implementation:

- `InitiativeTimingMatchHybridSettler` — deterministic leg: if
  `expected_window` is `explicit_request` and the turn has a
  `user_explicit_request` evidence row, returns `confirmed` or
  `violated` based on whether `actual_window` is `explicit_request`. If
  not, deterministic returns `uncertain`. LLM fallback: bounded prompt
  asks the LLM to judge silence-window timing from a bounded
  observation excerpt.

#### 5d. `silent` settler

No settlement. Returns `NoSettlement` with `reason_code =
"settler_silent_carry_forward"`. The scheduler treats this as a valid
terminal state for that attempt and emits `NoSettlementMade`.

Required reference implementation:

- `BehavioralPullShiftSilentSettler` — the
  `behavioral_pull_shift` observable is one of the few that may carry
  the silent hint in v1, because the M13.0 traction update flow is its
  own concern. The M20.1 silent settler does not interpret the
  observable payload; it just records the absence of settlement in
  `owner.observability[commit_id] = {settler_type: "silent",
  reason_code: "settler_silent_carry_forward"}`.

### 7. Implement the `SettlementScheduler`

The scheduler decides when to attempt settlement. Rules:

- A commitment is **not** eligible for settlement on the same turn it was
  admitted (T0). The earliest eligible turn is T0+1.
- A commitment is eligible for settlement on any turn where the
  scheduler finds an `ObservationContext` matching the commitment's
  `observable` and at least one of its `evidence_refs`.
- The scheduler attempts at most one settlement per `(commit_id, turn_index)`.
  Multiple observations on the same turn produce at most one
  `SettledValue` (the first matching observation wins; later matches
  are recorded as `NoSettlementMade` with `reason_code =
  "observation_already_processed"`).
- After a commitment has been settled once, the scheduler does not
  attempt it again. Subsequent turns see
  `owner.observability[commit_id]` and skip.
- A commitment whose `due_at` is past and that has not been settled is
  emitted once as `NoSettlementMade` with `reason_code =
  "due_at_passed"`.

### 8. Route by `observable`

The scheduler uses `Observable` v1's `settler_hint` to route. A
commitment whose `observable` is unknown to the runtime is rejected at
admission (this is already enforced by M20.0's
`unknown_observable` rejection code). M20.1 also exposes a small
diagnostic for the case where the hint is present but the settler is
not yet implemented:

```text
settlement_attempts_total
settlement_attempts_by_settler_type
settlement_attempts_by_observable
no_settlement_total
no_settlement_by_reason_code
settled_value_magnitude_distribution
```

No raw payload or prompt text is exposed in the default user-visible
chat stream.

### 9. Wire owner observability

For each owner in `CommitmentRegistry` v1, add a read-only
`observability` map shape:

```text
owner.observability[commit_id] = {
  "settled_value": <SettledValue> | None,
  "settlement_attempts": int,
  "last_attempt_turn_index": int | None,
  "last_attempt_reason_code": str | None
}
```

`observability` is a diagnostic surface, not a state bucket. M20.2
will read it to drive graded correction. M20.1 only writes to it.

Owners MUST NOT lose their existing fields. The new `observability` map
is additive. Owners that already exist in code
(`policy_state`, `m13_drive_state`, etc.) get a new attribute
`_observability: dict[str, dict]` initialized empty on first read.

### 10. Emit the audit events

`SettledValue` and `NoSettlementMade` audit events go on the existing
`conversation_log.jsonl` and on the existing
`diagnose/UI observability` counters (not on the user chat stream).
Existing `ActiveCommitmentCreated` and `ActiveCommitmentRejected`
events remain unchanged.

A `commit_id` may appear in at most one `SettledValue` and any number
of `NoSettlementMade` events in chronological order.

## Acceptance Criteria

M20.1 is complete only if:

1. `SettledValue` schema, `outcome` enum v1, per-observable magnitude
   scales, and settler-side `reason_codes` v1 are all frozen.
2. The four settler types are implemented behind a single `Settler`
   protocol, and the five reference settlers from §5a–§5d all
   pass their dedicated tests.
3. `SettlementScheduler` enforces T0+1 minimum, single-attempt-per-turn,
   and `due_at_passed` emission.
4. Owner `observability` map is additive and read-only from M20.1's
   perspective (M20.1 only writes to it; M20.2 will read from it).
5. `ActiveCommitmentSettled` and `NoSettlementMade` audit events are
   emitted in chronological order, with the existing
   `ActiveCommitmentCreated` / `ActiveCommitmentRejected` events
   unchanged.
6. M20.1 makes **no** writes to `self_cognition`, `m13_drive_state`,
   `memory_dynamics`, `self_repair_expectation`, `mismatch_memory_fast`,
   or any long-term state bucket.
7. The LLM judge settler calls use a frozen prompt template that
   forbids regex/keyword cues and free-form reasoning, and fails
   closed (`NoSettlement`) on invalid LLM output.
8. The hybrid settler never retries the LLM leg more than once per
   attempt.
9. The M20.1 acceptance diagnostic counters are exposed in the
   existing diagnose/UI observability surface.
10. The new tests pass; promotion/revocation tests for M20.2 are
    explicitly absent (red) and the absence is documented in the
    test file headers.
11. Path A and M10 remain untouched.
12. The existing per-loop settlers (M17.1 prediction settlement,
    M19.0 outcome_results, M13.2 band check, M15.0 episode
    aggregation, M18.5 boundary judgment) are not refactored.
    A later M20.1.1 milestone migrates them.

## Verification Standard

The milestone is only accepted if a recorded Path B test turn can show:

```text
ActiveCommitmentCreated(T0)
  -> turn T0+1 settlement attempt:
       ActiveCommitmentSettled or NoSettlementMade
  -> owner.observability[commit_id] updated
  -> NO writes to self_cognition / m13_drive_state /
     memory_dynamics / self_repair_expectation /
     mismatch_memory_fast
```

with the recorded trace showing **at most one** `SettledValue` per
`commit_id`. A second settlement attempt on the same `commit_id` MUST
NOT appear in the trace. This proves the observation half of the loop
is bound but the action half is still empty. M20.2 then proves the
first graded correction against the same trace format.

## Engineering Phenomenology Boundary

M20.1 is a settler runtime. No new visible behavior is expected, and
no long-term state is mutated. The user must not see any change in
chat output, idle ticks, or proactive delivery as a result of M20.1
landing.

M20.1 may create the engineering preconditions for "every commitment
flows through the same settler", but it must not claim that settlement
has been unified with promotion. M20.2 owns that claim.
