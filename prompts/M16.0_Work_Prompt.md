# OpenFEP M16.0 Work Prompt

## Milestone

M16.0: Consciousness Runner Architecture And Wire Protocol

## Goal

Define the long-term control inversion for Path B:

```text
Consciousness runner (Python, persistent self-loop)
  owns scheduling, cognition ticks, state commits, and outbox preparation

FastAPI + WebSocket gateway
  exposes perception and actuation interfaces only

TypeScript clients (Web, TUI)
  subscribe, render, and publish user input; they never tick cognition
```

In this document, "consciousness runner" is an engineering label for the
Path B self-loop owner. It must not be used to claim subjective experience.

M16.0 does **not** ship a full UI or a production runner. It freezes the
contract that M16.1–M16.4 will implement:

- one persona+session consciousness runner is the local orchestrator,
- external input arrives only through durable perception events,
- visible assistant text leaves only through existing M13.3 delivery paths,
- Streamlit reruns and UI frame rate are **not** acceptance schedulers.

This milestone closes the architectural gap exposed by M14.4: implicit idle
and proactive delivery must not depend on Streamlit being open.

## Architecture Position

M16 sits after M15.3 and reuses Path B cognition unchanged in substance:

```text
Perception IF (HTTP/WS + M14.2 environment events)
  -> ConsciousnessRunner loop
     -> claim/consume perception events
     -> user turn: existing MVPDialogueRuntime.run_turn
     -> silence: existing M13.5 / M14.0 / M14.1 / M15.x machinery
     -> commit through named owners + MVPStateStore
     -> prepare/drain outbox through M13.3 assessor
  -> Actuation IF (WS push + optional REST poll)
     -> assistant messages, proactive messages, audit stream, health
```

M16.0 must explicitly preserve:

- M8.9 state ownership and `MemoryWriteIntent`
- M13.3 delivery assessor and reply validation
- M13.6 traceable-expectation discipline for proactive outreach
- M14.2 environment event store semantics
- M15.2 meta-control as engineering bias only, not autonomous agency

M16 does **not** revive Path A (`conversation_loop.py`) or M10 producers.

## Boundary Rules

These rules are binding for every M16 milestone:

- Perception is input only: HTTP/WS append durable events; they do not interpret
  user intent, choose proactive eligibility, or call cognition entry points.
- Orchestration is runner only: timers, leases, budgets, state commits, and
  outbox drain decisions live in `ConsciousnessRunner`.
- Actuation is output only: WS/REST expose bounded assistant/proactive/audit
  events prepared by existing Path B owners.
- UI clients are replaceable observers/controllers: losing all clients must not
  stop the runner self-loop, and adding a client must not create a second loop.
- Streamlit may remain as a legacy adapter during migration, but it must never
  be the acceptance scheduler once the M16 runner exists.

## Dependencies

Hard:

- M8.9 MVP architecture contract
- M13.0–M13.6 MVP-local drive and memory-EFE bridge
- M14.0–M14.3 conscious idle, background continuity, proactive alignment
- M14.2 environment event bus and standalone daemon patterns
- M15.0–M15.3 episode ledger, consolidation, meta-control, cleanup

Soft:

- M14.4 Streamlit implicit idle (legacy adapter only after M16.3/M16.4)
- M11.0, M12.0, M12.1, M12.2 read-only context

## Non-Goals

- Do not implement the full runner loop in M16.0.
- Do not implement Web or TUI clients in M16.0.
- Do not replace `MVPDialogueRuntime` cognition with Path A `CognitiveLoop`.
- Do not claim subjective consciousness beyond the existing M16 engineering
  label.
- Do not expose raw prompt text, full memory dumps, or internal patch payloads
  on the default client stream.
- Do not design a second message bus that interprets semantics. Perception
  events record facts; cognition interprets inside the runner.
- Do not let client presence, frame rate, browser focus, terminal repaint, or
  Streamlit rerun cadence determine whether cognition ticks occur.

### 2. Protocol Module And JSON Schemas

Add:

```text
segmentum/dialogue/runtime/m16_protocol.py
schemas/m16/
  http.openapi.yaml
  ws_client_messages.schema.json
  ws_server_messages.schema.json
  perception_events.schema.json
  actuation_events.schema.json
```

Minimum HTTP surface (versioned under `/v1`):

```text
GET    /health
POST   /v1/personas/{persona_id}/sessions
GET    /v1/personas/{persona_id}/sessions/{session_id}
POST   /v1/personas/{persona_id}/sessions/{session_id}/input
GET    /v1/personas/{persona_id}/sessions/{session_id}/snapshot
POST   /v1/personas/{persona_id}/sessions/{session_id}/runner/start
POST   /v1/personas/{persona_id}/sessions/{session_id}/runner/stop
GET    /v1/personas/{persona_id}/sessions/{session_id}/runner/status
```

Rules:

- `POST /input` appends a durable perception event and returns `202 Accepted`
  with `event_id`; it does **not** call `run_turn` inline in the gateway thread.
- Session snapshot returns bounded chat tail + compact runtime hints only.
- Runner start/stop manipulates the consciousness process lock, not cognition
  directly.
- HTTP mutating routes require `correlation_id` and bounded payload sizes.
- The gateway must be localhost-only by default or require a dev token; remote
  auth is out of scope but unauthenticated remote mutation is forbidden.

Minimum WebSocket surface:

```text
WS /v1/personas/{persona_id}/sessions/{session_id}/stream
```

Client → server message kinds:

```text
Subscribe
Ping
ClientInput
DeliverySurfaceReady
DeliveryAck
Unsubscribe
```

Server → client message kinds:

```text
Subscribed
SessionSnapshot
UserMessageAccepted
AssistantMessageCommitted
ProactiveMessageCommitted
AuditEvent
RunnerHealth
RunnerSuppression
Error
```

Every server message must include:

```text
schema_version
message_id
session_id
persona_id
at
kind
payload
```

Every client message must include:

```text
schema_version
message_id
session_id
persona_id
at
kind
correlation_id
payload
```

Actuation messages must never include forbidden internal fields from
`mvp_architecture_contract_2026-05-04.md` (raw prompts, full memory dumps,
full conscious markdown).

Delivery surface availability requires both an open WS subscription and a
fresh `DeliverySurfaceReady`; a TCP connection alone is not enough to drain
proactive outbox items.

## Acceptance Criteria

M16.0 is complete when:

1. `reports/m16_0_consciousness_runner_contract.md` documents runner ownership,
   perception/actuation boundaries, and Streamlit demotion plan.
2. OpenAPI and WS JSON schemas exist and validate example messages.
3. `m16_protocol.py` exposes typed helpers for message kind constants,
   forbidden-field checks, and schema version.
4. Perception/actuation vocabulary is closed and mapped to M14.2/M13.3 audit
   semantics.
5. TS package scaffold documents the future SDK boundary without implementing it.
6. All M16.0 protocol tests pass offline.
7. Path A and M10 remain untouched.
