# OpenFEP M13.6 Work Prompt

## Milestone

M13.6: Memory-Backed Expected Free Energy Bridge

## Goal

Add a Path B bridge that turns unresolved, memory-backed predictions into
bounded expected-free-energy policy guidance. M13.6 must support the pattern:

```text
traceable pending expectation / open item
+ missing or conflicting observation
+ recall / decay / relationship precision
-> memory-backed prediction tension
-> EFE over allowed policies
-> reply-angle bias or M13.3 outreach proposal input
```

This milestone is not a new emotion module and not a silence timer. It must not
make "silence_seconds" directly increase boredom or directly trigger outreach.
Silence only matters when it makes a concrete, memory-backed prediction due or
unresolved.

Target behaviors:

```text
User does not answer a traceable high-precision expectation
-> social prediction error rises
-> wait / reflect / outreach are compared during idle
-> outreach is allowed only if it is the lowest bounded EFE policy and M13.3
   accepts the proposal

User keeps chatting with low novelty / repeated path
-> repetition tension affects the current reply angle
-> no proactive outreach is triggered from repetition alone

User contradicts a prior expectation in the current turn
-> repair / clarify pressure applies to the current reply
-> no outreach policy is selected while the user is active
```

M13.6 outputs structural guidance only. It does not generate visible text and
does not write initiative, outbox, memory, or self-cognition state directly.

## Architecture Position

M13.6 is MVP-local and lives in the dialogue runtime layer:

```text
pending_expectations / open_items / scheduled intents
+ retrieved memories / memory_dynamics / M13.1 / M13.2
-> segmentum.dialogue.runtime.m13_memory_efe
-> memory_efe snapshot and audit events
-> current-turn reply_angle_bias OR M13.3 proactive proposal input
```

Recommended new file:

```text
segmentum/dialogue/runtime/m13_memory_efe.py
```

Do not move this logic into `segmentum/memory.py`. The lower memory core owns
episode prediction error and total surprise. M13.6 only adapts Path B runtime
state into an auditable expected-free-energy surrogate.

## Dependencies

M13.6 builds on:

- M13.0 behavioral pull and path precision
- M13.1 boredom / information gain / repetition pressure
- M13.2 reward proxy and pending settlement pattern
- M13.3 bounded initiative and `ProactiveTurnProposal`
- M13.4 idle tick / structural idle signals
- M14.0 idle introspection outputs
- M14.2 scheduled outreach intents and queued outreach suppression
- `pending_expectations`, `open_items`, `temporal_state`, and retrieved memory
  evidence cards

M13.6 may read memory-dynamics signals, but it must not require changes to the
core memory store for the first implementation.

## Non-Goals

- Do not implement a unified variational free-energy engine for all Path B.
- Do not create an always-running autonomous agent.
- Do not generate user-visible prose.
- Do not bypass M13.3 consent, cooldown, session caps, safety, or UI opt-in.
- Do not let repetition, boredom, or silence alone trigger proactive outreach.
- Do not clear prediction error merely because an outreach proposal was made.
- Do not duplicate `memory_dynamics.control_guidance.conflict_level`,
  `repair_bias`, or social-sharing FE.
- Do not introduce subjective claims such as loneliness, neediness, craving, or
  emotional punishment in diagnostics or prompt-safe output.

### 2. Normalize EFE-Eligible Expectations

Add a deterministic normalizer:

```text
normalize_expectations_for_efe(state, *, now, phase) -> NormalizedExpectationSet
```

It returns two lists:

```text
eligible_for_efe: expectations that may drive F_memory / outreach
diagnostic_only: expectations shown in diagnostics but not used for policy
```

Only these sources can be `eligible_for_efe` in P0/P1:

- `pending_expectations` with `verify_on = "next_user_turn"` during
  `phase = "in_turn"` when a current-turn user observation is available; these
  are used for confirm / violate settlement, not idle outreach
- `pending_expectations` with `verify_on = "next_user_turn"` during
  `phase = "idle"` when no newer user turn has arrived after the expectation
  was created and the elapsed time exceeds the expected response window; these
  count as missing-observation candidates
- `pending_expectations` with a parseable `due_at`, `due_at_epoch`, or bound
  `scheduled_intent_id`
- `open_items` with `status = "open"` and concrete `next_check`
- M14.2 scheduled-outreach linked open items with a durable `due_at`

These are diagnostic-only unless later milestones add schema:

- `verify_on = "later"` with no concrete date or scheduled intent
- vague open items whose `next_check` is empty, `"later"`, or
  `"next_user_turn"` during idle
- expectations with no id, no evidence reference, and no way to test an
  observation

Each normalized expectation should expose:

```text
expectation_id
source_kind
content_summary
status
confidence
precision
due_at
expected_window_seconds
elapsed_since_due_seconds
required_for_action
bound_memory_ids
evidence_refs
relationship_weight
boundary_cost_hint
scheduled_intent_id
eligible
ineligibility_reason
```

Default response-window handling:

```text
next_user_turn expected_window_seconds = 900
due_at expected_window_seconds = 3600
scheduled_outreach expected_window_seconds = due_window_seconds or 86400
```

Implicit due anchor for `verify_on = "next_user_turn"`:

```text
due_at_implicit = expectation.created_at + ACTIVE_GRACE_SECONDS
elapsed_since_due_seconds = max(0, now - due_at_implicit)
```

Missing fields must be handled conservatively. Unknown due windows do not
create high pressure. A later milestone may extend the thinking JSON with
optional `due_at_epoch`, `evidence_refs[]`, `bound_memory_ids[]`, and
`recall_keys[]`; P0 may instead read concrete due information only from
M14.2 scheduled intents and open items.

### 3. Define Precision And Prediction Error Components

Use bounded, weighted components. Follow the style of `M13PullWeights`.

Suggested structure:

```text
M13MemoryEfeWeights:
  confidence = 0.42
  recall_salience = 0.22
  future_prediction_value = 0.12
  stale_memory_penalty = 0.18
  epistemic = 0.35
  repetition = 0.20
  recall_failure = 0.55
```

Precision must be clamped:

```text
precision(e) = clamp(
    w_conf * confidence(e)
  + w_salience * recall_salience(e)
  + w_future * future_prediction_value(e)
  - w_stale * stale_memory_penalty(e),
  0,
  1
)
```

The implementation may approximate `recall_salience`,
`future_prediction_value`, and `stale_memory_penalty` from available fields in
P0. It must name the approximation in diagnostics. It must not merely cite
memory dynamics without reading any memory-backed field.

Relationship precision is applied once, outside `precision(e)`:

```text
relationship_weight(e) =
  clamp(0.75 + 0.25 * relation_precision(user), 0.75, 1.0)
```

Do not multiply relation precision into both `precision(e)` and
`relationship_weight(e)`.

Social prediction error:

```text
PE_social(e) =
  precision(e)
  * due_pressure(e)
  * unresolved_pressure(e)
  * relationship_weight(e)
  * observation_gap(e)
```

Deterministic pressure defaults:

```text
due_pressure(e) =
  clamp(elapsed_since_due_seconds / expected_window_seconds, 0, 1)

elapsed_since_due_seconds = 0 when not due yet

unresolved_pressure(e) =
  1.0 if status in {"pending", "open", "due"}
  0.0 if status in {"confirmed", "settled"}
  0.0 for violated during in_turn (handled as repair-only)
  1.0 for violated during idle/settle if still eligible and not user_active
```

Observation-gap defaults:

```text
confirmed                     -> 0.00
settled                       -> 0.00
pending and not due           -> 0.15
pending and due soon          -> 0.35
due with missing observation  -> 0.65
violated during user turn     -> repair_only, not outreach
violated during idle/settle   -> 0.90, if still eligible and not user_active
```

Epistemic prediction error:

```text
PE_epistemic(e) =
  precision(e) * required_for_action(e) * recall_failure_weight
```

P0 defaults:

```text
required_for_action(e) =
  1.0 if expectation has bound_memory_ids or evidence_refs
      and status in {"pending", "due", "open"}
  0.0 otherwise

recall_failure_weight = M13MemoryEfeWeights.recall_failure
```

P0/P1 may count recall failure only when an expectation has explicit
`evidence_refs`, `bound_memory_ids`, or expectation ids that were requested and
not retrieved. If there is no link field, do not fabricate recall failure.

Total memory tension:

```text
F_memory =
  min(
    F_MEMORY_CAP,
    sum(top K PE_social over eligible_for_efe)
  + lambda_epi * sum(top K PE_epistemic over eligible_for_efe)
  )

F_MEMORY_CAP = 1.5
K = 5
```

Sort eligible expectations by `PE_social` descending before applying top-K.
This prevents long soft expectation lists from overwhelming policy costs.

Repetition tension remains separate. It may affect `continue_reply`, but it
must not enter idle `outreach` EFE.

Repetition tension source:

```text
repetition_tension =
  m13_boredom_evaluation.repetition_pressure
  + optional small boost from M13.2 path_feels_stale_proxy
```

Do not create a third repetition metric in M13.6.

### 4. Split Policy Sets By Phase

The evaluator must accept:

```text
phase = "in_turn" | "idle"
```

`user_active` must be derived conservatively:

```text
user_active =
  phase == "in_turn"
  OR pending_user_message
  OR idle_seconds < ACTIVE_GRACE_SECONDS
  OR runtime/UI turn-in-progress flag is true
```

Default:

```text
ACTIVE_GRACE_SECONDS = 15
```

Allowed policies:

```text
in_turn:
  continue_reply

idle:
  wait
  reflect
  outreach
```

`continue_reply` must never appear as a valid idle policy. `outreach` must
never be selected while `user_active` is true.

Current-turn effects:

```text
selected_policy = "continue_reply"
reply_angle_bias =
  "none"
  | "new_angle"
  | "clarify_open_loop"
  | "repair_expectation"
  | "summarize_then_advance"
```

Idle effects:

```text
selected_policy = argmin(EFE(wait), EFE(reflect), EFE(outreach))
should_outreach = selected_policy == "outreach" plus hard gates
```

### 5. Close The EFE Equations

Do not use undefined "F after policy" terms. Define them explicitly and
conservatively.

Suggested shape:

```text
EFE(wait) =
  F_memory
+ wait_decay_risk
+ low_control_cost

EFE(reflect) =
  F_memory * (1 - expected_internal_resolution)
+ recall_cost
- expected_epistemic_gain

EFE(outreach) =
  F_memory * (1 - expected_outreach_resolution)
+ boundary_cost
+ relationship_cost
+ control_cost
- expected_information_gain
+ risk_penalty

EFE(continue_reply) =
  repetition_tension
+ low_expected_information_gain
+ repair_pressure_if_violated
- expected_reply_information_gain
```

Critical constraints:

- `EFE(continue_reply)` is computed only in `phase = "in_turn"`.
- `phase = "in_turn"` must always set `should_outreach = false`.
- `expected_outreach_resolution` must require a bound
  `traceable_expectation_id`.
- It must be capped; outreach cannot zero out F_memory in proposal stage.
- No PE is cleared when a proposal is created.
- No PE is cleared when a proposal is queued.
- PE can only be settled after delivery succeeds and a later user observation
  or TTL expiry is processed.

Outreach resolution prior:

```text
expected_outreach_resolution(e) =
  cap(
    base_resolution
    * traceable_binding(e)
    * evidence_strength(e)
    * boundary_allowance(e),
    max_outreach_resolution_prior
  )
```

Default cap should be conservative, for example `0.45`.

Default reflect terms:

```text
expected_internal_resolution = min(0.15, 0.04 * eligible_count)
expected_epistemic_gain = min(0.25, 0.08 * eligible_count)
recall_cost = 0.08
```

Default outreach margin:

```text
outreach_margin = EFE(wait) - EFE(outreach)
minimum_outreach_margin = 0.08
```

Default policy cost table:

```text
wait_decay_risk = 0.05
low_control_cost = 0.02
recall_cost = 0.08
control_cost = 0.10

boundary_cost =
  0.05 when boundary_strength in {"none", "", null}
  0.20 when boundary_strength == "soft"
  0.45 when boundary_strength == "hard"

relationship_cost = 0.10 + regret_bias
risk_penalty = 0.0 normally
risk_penalty >= 0.30 when safety, boundary, or identity-risk flags are present

boundary_cost_high = boundary_cost >= 0.30
relationship_cost_high = relationship_cost >= 0.30
```

Default current-turn terms:

```text
low_expected_information_gain = 1 - m13_boredom_evaluation.information_gain_proxy
repair_pressure_if_violated = memory_dynamics.control_guidance.repair_bias
  when expectation_results include violated, else 0
expected_reply_information_gain =
  0.18 for "new_angle"
  0.14 for "clarify_open_loop"
  0.12 for "repair_expectation"
  0.10 for "summarize_then_advance"
  0.00 for "none"
```

These are bounded proxy terms. M13.6 reads repair pressure but does not rewrite
`repair_bias` or `conflict_level`.

Current-turn `reply_angle_bias` selection:

```text
if expectation_results include violated:
  reply_angle_bias = "repair_expectation"
elif epistemic_prediction_error >= 0.20 and eligible recall failure exists:
  reply_angle_bias = "clarify_open_loop"
elif repetition_tension >= 0.35:
  reply_angle_bias = "new_angle"
elif progress_signal >= 0.35:
  reply_angle_bias = "summarize_then_advance"
else:
  reply_angle_bias = "none"
```

`expected_reply_information_gain` is the lookup value for the selected bias. It
is diagnostic support for `EFE(continue_reply)`, not a separate selector.

### 8. Suppression Rules

M13.6 must set `should_outreach = false` with a reason code when any hard gate
applies:

```text
phase_not_idle
user_active
not_opted_in
initiative_disabled
cooldown_active
session_limit_reached
no_efe_eligible_expectation
no_traceable_expectation
boundary_cost_high
relationship_cost_high
recently_outreached
scheduled_outreach_already_active
queued_outreach_already_pending
delivery_channel_unavailable
insufficient_expected_resolution
outreach_margin_too_small
safety_risk
```

Recently-outreached rule:

```text
M13_6_OUTREACH_RESETTLE_WINDOW_SECONDS = 3600
recently_outreached =
  now - last_memory_efe_outreach_at < M13_6_OUTREACH_RESETTLE_WINDOW_SECONDS
```

When a pending M13.6 outreach settlement exists for the same
`traceable_expectation_id`, suppress duplicate outreach until that settlement
is resolved or expired.

Scheduled-outreach rule:

```text
If an active M14.2 scheduled_outreach intent or queued outreach already covers
the same expectation / open item, M13.6 may report high PE but must not produce
another outreach recommendation.
```

M14.2 status matching:

```text
scheduled_outreach_already_active when scheduled_intents row has
  status in {"preparing", "prepared", "awaiting_delivery"}

queued_outreach_already_pending when queued_outreach row has
  status == "pending"

match key:
  traceable_expectation_id OR linked open_item_id OR scheduled_intent_id
```

Call M13.6 from the existing runtime, not from a separate background loop.

Recommended call sites:

```text

  after M13.1 boredom and M13.2 reward evaluation
  before final prompt-safe control guidance is assembled
  evaluate_memory_efe(phase="in_turn", user_active=True, ...)
```

## Function Sketch

Suggested public API:

```text
evaluate_memory_efe(
    state,
    *,
    phase,
    now,
    turn_index,
    user_active,
    memory_dynamics=None,
    retrieved_memories=None,
    m13_boredom_evaluation=None,
```

`now` must be an integer UTC epoch timestamp in seconds, consistent with
`_utc_timestamp()`.

If `m13_reward_evaluation` is absent, idle evaluation should read
`m13_drive_state.affective_reward_proxy` for `path_feels_stale_proxy` and

Result shape:

```text
M13MemoryEfeEvaluationResult:
  event_id
  phase
  eligible_for_efe
  diagnostic_only
  social_prediction_error
  epistemic_prediction_error
  repetition_tension

  should_outreach
  outreach_margin

  reason_codes
```

Traceable expectation selection:

```text
traceable_expectation_id = argmax PE_social over eligible_for_efe
tie-break 1: earliest due_at

```

```text

```

```text
build_memory_efe_outreach_proposal_input(evaluation) -> dict | None
```

## Testing / Acceptance Criteria

Add focused tests under `tests/test_m13_6_memory_efe.py`.

Required cases:

1. No open expectation during idle:
   - no EFE-eligible expectations,
   - `should_outreach = false`,
   - `suppression_reasons` contains `no_efe_eligible_expectation`.

2. Vague `verify_on = "later"` with no due:
   - item appears in `diagnostic_only`,
   - `eligible_for_efe` is empty,
   - no outreach recommendation.

3. High-confidence pending expectation with concrete overdue due time:
   - `social_prediction_error` rises,
   - `efe_by_policy` includes only `wait`, `reflect`, `outreach`,
   - outreach may win only if margin and boundary gates pass.

   Cover two fixtures:
   - overdue `open_item` or scheduled intent with concrete `due_at`,
   - idle `verify_on = "next_user_turn"` that exceeded the response window
     without a newer user turn.

4. User is active and expectation is violated:
   - phase is `in_turn`,
   - selected policy is `continue_reply`,
   - `reply_angle_bias` indicates repair or clarification,
   - `should_outreach = false`.

5. Idle phase never includes `continue_reply` as a valid policy.

6. Repetition tension with active user:
   - can set `reply_angle_bias = "new_angle"`,
   - must not set `should_outreach = true`.

7. Scheduled outreach already active:
   - PE may remain high,
   - `should_outreach = false`,
   - suppression includes `scheduled_outreach_already_active`.

8. Queued outreach already pending:
   - no duplicate M13.6 outreach proposal is produced.

9. Boundary cost high:
   - outreach is suppressed even with high PE.

10. Recall failure with explicit evidence refs:
    - `epistemic_prediction_error` rises,
    - reflect is preferred unless outreach has traceable, bounded resolution.

11. Outreach proposal not delivered:
    - PE is not cleared,
    - settlement observed resolution is zero or uncertain.

12. Delivery succeeds but no later user observation arrives before TTL:
    - settlement expires as unresolved or uncertain,
    - no fabricated confirmation.

13. M13.3 single-entry rule:
    - M13.6 does not write initiative or outbox directly,
    - proposal input goes through M13.3.
    - `memory_efe_outreach` is registered in the M13.3 trigger allowlist.
    - locked memory-EFE proposals outrank non-bound boredom targets.

14. Prompt safety:
    - prompt-safe guidance includes no raw equations, raw memory rows, or
      subjective wording.

15. Determinism:
    - same state and timestamp produce the same EFE values and reason codes.

16. Current-turn continue-reply EFE:
    - `EFE(continue_reply)` is present in `phase = "in_turn"`,
    - wait / reflect / outreach are absent from the valid in-turn policy set.

17. `user_active` race guard:
    - a daemon or idle tick inside `ACTIVE_GRACE_SECONDS` suppresses outreach.

18. F-memory cap and top-K:
    - more than five eligible expectations cannot push `F_memory` above
      `F_MEMORY_CAP`,
    - adding low-PE extra expectations does not change the selected policy.

19. Cost defaults and boundary threshold:
    - hard boundary maps to `boundary_cost = 0.45`,
    - `boundary_cost_high` suppresses outreach,
    - cost values are present in diagnostics.

20. Relationship precision is not double-counted:
    - increasing `relation_precision` changes `relationship_weight`,
    - `precision(e)` itself does not include relation precision.

21. Deterministic traceable expectation selection:
    - highest `PE_social` wins,
    - ties use earliest `due_at`,
    - remaining ties use lowest `expectation_id`.

22. M14.2 status matching:
    - scheduled intent statuses `preparing`, `prepared`, and
      `awaiting_delivery` suppress duplicate outreach,
    - queued outreach status `pending` suppresses duplicate outreach.

23. Store-lock write path:
    - `apply_memory_efe_state` updates `m13_drive_state.memory_efe` only
      through the existing state-store lock in integration tests.
