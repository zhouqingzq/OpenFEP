# OpenFEP M14.3 Work Prompt

## Milestone

M14.3: Traceable Proactive Delivery Alignment And Safety Diagnostics

## Goal

Close the product gap exposed after M13.6 and M14.2 land in a real Hu Tao session:

```text
User opt-in + implicit idle delivery + daemon running
-> one weak proactive message ("晚霞…") from vague open_item trigger
-> later proactive attempts blocked as safety_risk
-> dashboard shows pending environment events but no meaningful follow-up
-> user cannot tell whether the blocker is design, safety, or "no desire to talk"
```

M14.3 does not add a new emotion module or a second outreach stack. It **aligns**
the existing M13.3 delivery path, M13.6 memory-EFE gate, M14.0 idle reflector,
and M14.2 daemon/event bus so that:

```text
traceable unresolved expectation / open item / scheduled intent
+ idle or locked outbox proposal
+ recall on idle path before EFE
-> single proactive proposal source of truth
-> structured suppression taxonomy
-> delivery only when intent anchors to evidence
-> audit explains why outreach was allowed or blocked
```

Target behaviors:

```text
open_item with next_check="later" only
-> diagnostic_only in M13.6
-> MUST NOT create M13.3 open_item_next_check proposal

open_item with next_check="next_user_turn" + evidence_refs
-> eligible in M13.6 after observation gap
-> M13.3 proposal trigger = memory_efe_outreach with traceable_expectation_id
-> ordinary_language_intent cites the open loop content, not the raw next_check token

idle introspection with linked memory ids missing from retrieval
-> epistemic PE computed after retrieve
-> MemoryEfeSuppressionEvent may include recall_failure_active

proactive text generated but blocked
-> M13ProactiveSuppressionEvent.reason_code distinguishes:
   opponent_strength_pre_block | delivery_assessor_reject | reply_validation_fail
-> UI shows engineering reason, not only "safety_risk"

M14.2 environment events pending in UI
-> daemon claims and acks UserMessageCommittedEvent / ClockWakeEvent in the
   acceptance path; stale pending count drops after healthy daemon tick
```

Success means a developer (and the inner-world panel) can answer:

```text
Why did Hu Tao proactively speak?
Why did she not?
Was it safety, missing traceable expectation, cooldown, or weak dialogue tension?
```

without guessing from a single opaque `safety_risk` string.

## Architecture Position

M14.3 remains Path B and MVP-local. It refines integration; it does not replace
M13.6 or M14.2:

```text
M14.2 daemon / Streamlit idle tick
-> claim + ack environment events (reliability fix)
-> run_idle_introspection_turn
   -> retrieve_memories FIRST on idle path
   -> evaluate_memory_efe(..., retrieved_memories=...)
   -> M14.0 conscious_idle_plan + apply_idle_drive_rules
-> unified proactive target selection (M14.3 module)
   -> memory_efe_outreach | scheduled_outreach | correction_followup
   -> deprecate vague open_item_next_check
-> maybe_propose_proactive_turn / locked outbox drain
-> run_proactive_turn
   -> structured pre/post suppression codes
   -> proactive_delivered_text_is_safe with auditable assessment payload
-> conversation_log + inner-world diagnostics
```

M14.3 is the milestone where **proactive delivery becomes traceable end-to-end**,
not merely possible.

## Problem Diagnosis (from live session)

The following split guided this milestone. Percentages are engineering estimates,
not statistical measurements.


| Symptom                                                 | Primary cause                                                                                    | Approx. share         |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------- |
| Proactive sent but off-topic ("晚霞…")                    | M13.3 `open_item_next_check` accepts vague `next_check="later"`; weak `ordinary_language_intent` | ~80% system design    |
| Later attempt shows `safety_risk`, no chat text         | coarse `opponent_strength` pre-block and/or delivery assessor reject without sub-code            | ~75% system design    |
| M13.6 rarely `should_outreach`                          | open items not traceable eligible; idle EFE runs before retrieve                                 | ~60% system design    |
| User long_gap greeting; no strong follow-up on Li An'an | conscious plan correctly marks `exp_007` uncertain; low boredom                                  | ~40% dialogue quality |


M14.3 owns the **system-design** rows. It must not fake dialogue quality with
prompt-only outreach when memory tension is absent.

## Dependencies

Hard:

- M8.9 state ownership and evidence boundaries
- M13.3 initiative, delivery assessor, `run_proactive_turn`
- M13.6 memory EFE (`evaluate_memory_efe`, open-item normalization)
- M14.0 idle reflector and `apply_idle_drive_rules`
- M14.1 budgets and opt-in controls
- M14.2 event bus, daemon, scheduled intents, outbox drain

Soft (read-only):

- M11.0, M12.0, M12.1, M12.2

Path A and M10 remain out of scope.

## Non-Goals

- Do not add a variational free-energy engine for all Path B cognition.
- Do not create a second persona, second chat stack, or Path A bridge.
- Do not let boredom, silence, or repetition alone trigger proactive outreach.
- Do not weaken M13.3 user opt-in, cooldown, or session caps.
- Do not invent biography or promote unrecalled memory into proactive text.
- Do not use engineering audit text claiming subjective loneliness, craving, or
"she wanted to talk".
- Do not require the user to hand-edit JSON as the only migration path; provide
a deterministic migration helper, but do not auto-mutate live sessions silently
without an audited patch intent.
- Do not push notifications, email, or external delivery surfaces.

### 5. Safety Risk Decomposition

Split the opaque `safety_risk` into closed sub-codes. Update
`mvp_loop.run_proactive_turn`, `m13_initiative.evaluate_proactive_initiative`,
and `m13_memory_efe.evaluate_memory_efe` emitters.

Closed pre-generation codes:

```text
opponent_strength_pre_block          # affective_reward_proxy.opponent_strength >= threshold
context_assessment_unsafe            # assess_proactive_context_semantics.context_unsafe
memory_efe_safety_risk               # M13.6 risk_penalty >= 0.30
initiative_disabled / not_opted_in / cooldown_active / session_limit_reached
delivery_channel_unavailable         # implicit_idle_delivery false
idle_time_too_short
no_traceable_proactive_target
```

Closed post-generation codes:

```text
delivery_assessor_reject             # proactive_delivered_text_is_safe false
delivery_assessor_low_confidence
reply_validation_fail
empty_generation
```

Rules:

- `M13ProactiveSuppressionEvent` must include:
`reason` (legacy string), `reason_code`, `reason_stage` (`pre_proposal` |
`post_generation`), and compact `assessment` when LLM assessor ran.
- UI inner-world panel maps codes to short operational labels; chat bubble for
blocked proactive shows `reason_code`, not only `safety_risk`.
- M13.6 idle suppression `safety_risk` renamed in audit to
`memory_efe_opponent_risk` to avoid collision with delivery-stage codes.

Calibration task (bounded, hyperparam-driven):

- Document default `opponent_strength` threshold (currently 0.5) and add
`initiative.opponent_strength_block_threshold` with default unchanged.
- Add `initiative.delivery_assessor_min_confidence` explicit in state (already
exists as constant); log assessor score when reject happens.
- Do not remove delivery assessor; make it auditable.

## Acceptance Criteria

M14.3 is complete when:

1. Vague open items (`later`, `regular`, etc.) are **diagnostic-only** for M13.6
  and **cannot** produce M13.3 proactive proposals unless
   `legacy_vague_open_item_proactive=true`.
2. Idle introspection evaluates M13.6 **after** bounded memory retrieve; epistemic
  PE reflects recall failure on the idle path.
3. Proactive proposals use `memory_efe_outreach` (or scheduled/correction paths)
  with `traceable_expectation_id` and evidence-backed `ordinary_language_intent`.
4. Blocked proactive turns emit structured `reason_code` + `reason_stage`; UI
  and inner-world panel surface them; opaque-only `safety_risk` is no longer
   the sole diagnostic for new events.
5. M14.2 daemon reliably claims and acks environment events in the acceptance
  path; pending audit counts decrease after healthy ticks.
6. Open-item traceability audit/migration tooling exists with deterministic rules
  and audited apply path.
7. `reports/m14_3_proactive_alignment.md` documents the unified pipeline and
  suppression taxonomy.
8. M13.3 consent, cooldown, session caps, M14.1 budgets, and delivery assessor
  remain enforced.
9. M11/M12 ledgers, Path A, and M10 are untouched.
10. All listed M14.3 tests pass with deterministic stubs.
