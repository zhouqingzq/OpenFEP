## Milestone

M20.3: Policy Admission, Same-Turn Surface Horizon, Runtime Loop Invariants,
And Settler Migration

## Goal

Close the five gaps that M20.0–M20.2 alone do not close on the group-chat
identity and "every turn closes the loop" axes:

```text
M20.0  ActiveCommitment + Registry v1 + Observable v1
M20.1  Settler protocol (4 types, 5 reference settlers)
M20.2  Graded correction dispatcher (6 levels, route to existing owners)
                                |
                                v
+----------------------------------------------------------+
|  M20.3 (this milestone)                                   |
|  1. PolicyProducer           (gap A: policy admission)   |
|  2. AssistantIdentityMode    (gap A: writable mode owner)|
|  3. Same-turn surface horizon(gaps B+C: pre/post-send)   |
|  4. fast_chat minimum loop   (gap E: runtime invariant)   |
|  5. M20.1.1 settler migration(gap D: no double-tracks)    |
|  6. 6+1+1 step fixture       (acceptance: identity +      |
|                                fast_chat sub-scenarios)   |
+----------------------------------------------------------+
```

M20.3 is the *operational* layer above the M20.0–M20.2 *meta* layer. It does
not change the meta-contract frozen in M20.0, but it adds **a v2 bump** to
`CommitmentRegistry` (one new owner), **a v2 attribute** on
`ActiveCommitment` (`horizon`), and a runtime invariant module that the
existing `mvp_loop.run_turn` calls on every external turn.

M20.3 does **not** touch the conscious loop, the thinking stage, or the
reply validation semantics. It only adds:

- new admission paths (PolicyProducer),
- a new pre/post-send settler fast-path (same_turn_surface),
- a new runtime invariant (fast_chat minimum loop),
- a migration of existing per-loop settlers onto the M20.1 runtime.

## Why M20.3 Exists

The M20.0–M20.2 review identified five gaps. They are not three small fixes;
they are the difference between "the meta-loop exists" and "the meta-loop
runs in production on every turn, including fast_chat and identity
violations in the same turn they happen".

| Gap | Symptom | Why M20.0–M20.2 cannot fix it alone |
|---|---|---|
| A | Policy commitments have no producer and no writable owner | M20.0 §8 admits only LLM producers; M20.2 §2 forces `policy_source_no_correction` |
| B | Identity violation in turn T is settled in T+1 | M20.1 §7 enforces T+1 minimum for all settlements |
| C | `same_turn` corrections are advisory only; already-sent wrong-persona text stays | M20.2 §7 caps `same_turn` to advisory fields |
| D | M20.1 runtime exists but no per-loop settler uses it | M20.0–M20.2 do not migrate M17/M19/M13/M15/M18 |
| E | `fast_chat` skips admission, settlement, and dispatch | M20.0–M20.2 have no runtime invariant layer |

M20.3 closes all five.

## Architecture Position

M20.3 is MVP-local and lives as a sibling module to the M20.0–M20.2
runtime:

```text
external turn / fast_chat turn
   |
   v
run_turn (mvp_loop)
   |  1. PolicyProducer.evaluate(...)             (T0 admission, non-LLM,
   |                                                 runs first or in
   |                                                 parallel with conscious)
   |  2. (existing conscious loop)                 (T0 admission, LLM,
   |                                                 may emit
   |                                                 active_commitment_proposals)
   |  3. LoopInvariants.enforce_minimum_loop_coverage(...)
   |                                               (audit only, MUST run
   |                                                 after both admission
   |                                                 sources above)
   |  4. (existing thinking)
   |  5. (existing reply generation -> draft_reply)
   |  6. SameTurnSurfaceSettler.run_pre_send(draft_reply, ...)
   |                                               (can BLOCK only when
   |                                                 owner is runtime_mode_state)
   |  7. reply commit (or persona_boundary_fallback replacement)
   |  8. SameTurnSurfaceSettler.run_post_send(committed_reply, ...)
   |                                               (advisory only)
   |  9. validate_visible_reply                    (existing; M19.x
   |                                                 surface_consistency)
   |  10. m20.1.settle(...)                        (T+1+, on subsequent turns)
   |  11. m20.2.dispatch(...)                      (T+2+, on subsequent turns)
   |
   v
conversation_log + diagnose observability
```

The order matters. PolicyProducer runs **before or in parallel with**
the conscious loop so the runtime invariant at step 3 sees the union
of T0 admissions. The invariant module never blocks; it audits. The
same_turn_surface fast path runs both before (step 6) and after
(step 8) the visible reply. Steps 1, 3, 6, and 8 are the four new
M20.3 call sites. The existing M20.0 / M20.1 / M20.2 / M19.x code
runs on its existing schedule and is unchanged by M20.3 except for
the registry v2 exception table (see §3.5).

## Non-Goals

- Do not modify the M20.0 frozen schema fields. M20.3 may ADD `horizon`
  as a v2 attribute; it may NOT change `commit_id`, `owner_id`,
  `source_kind`, `observable`, `evidence_refs`, etc.
- Do not refactor `validate_visible_reply` to call M20.3 directly. The
  pre-send gate is a new settler that emits a new audit event; the
  existing `validate_visible_reply` is unchanged.
- Do not let the pre-send gate hard-replace a reply that the conscious
  loop has already emitted. The pre-send gate runs BEFORE the reply
  is committed; it cannot rewrite an already-committed reply.
- Do not let the post-send advisory write to visible reply text. Same
  rule as M20.2 §7's `same_turn_not_advisory` cap.
- Do not let the runtime invariant module block a turn. It only emits
  `MinimumLoopCoverageMissed` audit events; it does not refuse to run.
- Do not let PolicyProducer admit an `ActiveCommitment` whose
  `source_kind` is not `policy`. The producer is policy-only by name;
  `state` and `episodic` commitments still come from M20.0 §8 producers.
- Do not let `runtime_mode_state` owner be written by any path other
  than PolicyProducer admission followed by M20.2 graded correction.
  Direct writes from anywhere else are rejected.
- Do not let M20.1.1 alter the existing per-loop settlers' observable
  behavior. The migration is a thin adapter; the underlying settler
  logic is unchanged.
- Do not touch Path A, M10, `conversation_loop.py`, or
  `SelfThoughtProducer`.

## Required Work

### 1. PolicyProducer

A non-LLM admission path that produces `ActiveCommitment` rows with
`source_kind = "policy"`.

#### 1.1. Frozen producer surface

```text
class PolicyProducer:
    def evaluate(
        self,
        turn_context: TurnContext,
        runtime_mode_flags: RuntimeModeFlags,
        command_envelope: CommandEnvelope | None,
        user_correction_signal: UserCorrectionSignal | None,
    ) -> list[ActiveCommitment]:
        ...
```

Inputs:

- `turn_context`: existing per-turn context (existing field)
- `runtime_mode_flags`: existing group/chat mode flags (e.g.
  `surface_intent`, `conversation_mode`, `group_mode`)
- `command_envelope`: existing `envelope.platform_command` and
  `envelope.bot_command_args`, or `None` on non-command turns
- `user_correction_signal`: NEW bounded field
  `correcting_assistant_identity` from the conscious-loop JSON
  (v2 of conscious-loop structured output, see §3.1)

Outputs:

- zero or more `ActiveCommitment` rows with `source_kind = "policy"`,
  non-empty `evidence_refs`, and `commit_id` derived deterministically
  from `(owner_id, source_ref, layer, observable, created_turn)`.

#### 1.2. Producer policy-to-observable mapping v1

A frozen table mapping each producer input to an `ActiveCommitment`,
split into turn-scoped (advisory, no durable mutate) and durable
mutate (changes `runtime_mode_state.mode` after M20.2 dispatch):

```text
input                                          -> observable              -> owner_id             -> scope
envelope.platform_command == "/status"         -> "runtime_mode_state"   -> runtime_mode_state   -> turn-scoped
envelope.platform_command == "/mode X"         -> "runtime_mode_state"   -> runtime_mode_state   -> durable mutate
envelope.platform_command == "/persona X"      -> "runtime_mode_state"   -> runtime_mode_state   -> durable mutate
runtime_mode_flags.surface_intent == "bot"     -> "runtime_mode_state"   -> runtime_mode_state   -> turn-scoped
runtime_mode_flags.surface_intent == "chat"    -> "runtime_mode_state"   -> runtime_mode_state   -> turn-scoped
runtime_mode_flags.surface_intent == "abstain" -> "runtime_mode_state"   -> runtime_mode_state   -> turn-scoped
user_correction_signal == "wrong_persona"      -> "runtime_mode_state"   -> runtime_mode_state   -> durable mutate
user_correction_signal == "wrong_voice"        -> "runtime_mode_state"   -> runtime_mode_state   -> durable mutate
group_mode ingress change                       -> "runtime_mode_state"   -> runtime_mode_state   -> durable mutate
envelope.platform_command == "/quiet"           -> "outreach_intent_off"  -> outreach_intent_registry -> turn-scoped
envelope.platform_command == "/resume"          -> "outreach_intent_on"   -> outreach_intent_registry -> turn-scoped
```

Notes:

- `runtime_mode_state` is a NEW observable in `Observable` v2; the v1
  vocabulary is bumped in M20.3 (see §2).
- `outreach_intent_off` / `outreach_intent_on` are also new v2
  observables. They are observation-only in v1 (no settler; only
  `silent` carries forward).
- The mapping is deterministic. The same inputs always produce the
  same `ActiveCommitment` rows. PolicyProducer is not an LLM call.
- **Turn-scoped** rows admit an `ActiveCommitment` whose
  `observable_payload.expected_mode` is the requested mode; the
  pre-send gate uses this for `runtime_mode_state` but the
  `runtime_mode_state.mode` field is NOT mutated after M20.2
  dispatch. The user sees the requested mode for this turn only.
- **Durable mutate** rows are the only path that actually changes
  `runtime_mode_state.mode` (via M20.2 dispatch with
  `correction_level` ≥ `microadjust`).

#### 1.3. `/status` turn-scoped vs `/mode` durable split (DECIDED)

`/status` admits `expected_mode = bot_system` (turn-scoped). It does
NOT mutate `runtime_mode_state.mode`. Reply this turn uses the
bot-system persona (via pre-send gate), and the next turn reverts to
whatever the persistent mode is. Only `/mode X` and `/persona X` (and
`group_mode` ingress change, and `user_correction_signal` for
identity corrections) are durable mutate. This split is the v1
answer to "the user types `/status` and gets the wrong persona" —
the turn-scoped bot_system pre-send is enough to fix the surface for
this turn without contaminating the persistent mode state.

#### 1.4. Audit event

```json

  "type": "PolicyAdmitted",
  "turn_index": 42,
  "commit_id": "<deterministic sha1>",
  "owner_id": "<from registry>",
  "source_ref": "<command envelope id or mode flag change id>",
  "observable": "<from observable v2>",
  "evidence_refs": ["turn_<n>_command_envelope", "..."],
```

`PolicyAdmitted` is emitted ALONGSIDE `ActiveCommitmentCreated` (the

The v1→v2 registry bump is **additive**: v2 = v1 + `runtime_mode_state`

### 3. Same-turn surface horizon

Add a v2 attribute to `ActiveCommitment`:

```text
horizon: "same_turn_surface" | "next_turn" | "natural_context"
```

Default for all M20.0 / M20.1 / M20.2 producers: `"next_turn"`. M20.3
sets `"same_turn_surface"` only for:

- `runtime_mode_state` (always),
- `identity_voice_match` (only when `outcome = "violated"`),
- `boundary_handled` (only when `outcome = "violated"`),
- `pacing_match` (only when `outcome = "violated"`).

`horizon` is a v2 attribute and is rejected if its value is not in the
frozen enum. M20.0 admission validation is extended to allow
`horizon` as an optional field whose default is `"next_turn"`.

#### 3.1. Conscious-loop v2 attribute (DECIDED)

Extend `normalize_conscious_turn_plan` (existing) with one bounded
field:

```text
correcting_assistant_identity: "" | "wrong_persona" | "wrong_voice" | "right_persona_reaffirm"
```

`""` (empty) is the default. Non-empty values route to PolicyProducer
in §1.1. This is the user-side signal that triggers a same-turn
admission of `runtime_mode_state`.

`right_persona_reaffirm` is **confirm only** — it confirms the
current mode but does NOT write to slow layer or raise
`calibrated_tendencies`. The other two values (`wrong_persona` /
`wrong_voice`) trigger durable mutate (per §1.2) and follow the
M20.2 dispatch path through `runtime_mode_state`.

#### 3.1a. Correction-round semantics (v1 implementation, post-conscious)

**v1 implementation (2026-06-08)**: `correcting_assistant_identity`
is a v2 attribute of the **conscious loop** output. Per CLAUDE.md
"Semantic decisions must not be implemented as keyword/regex cue
lists", the LLM is the only legitimate source — engineering does
NOT parse user text for "你是X" / "我以为你是X" patterns. This means:

1. **Pre-conscious context cannot detect a correction round.**
   `correcting_assistant_identity` is not yet set when
   `_classify_turn_latency_mode` runs (the classify decision is
   made BEFORE the conscious loop). A "force full conscious based
   on pre-conscious detection" rule is therefore not implementable
   under the CLAUDE.md contract; the prompt language in earlier
   versions of this section was aspirational and is now aligned
   with the actual code path.

2. **Fast_chat fast path runs conscious in thin or full mode.**
   When `latency_mode == "fast_chat"`, the conscious loop still
   runs (`mvp_loop.run_turn` line ~7700+), but the LLM may
   prioritize other schema fields and emit
   `correcting_assistant_identity = ""` (the default-empty
   case). PolicyProducer's post-conscious call sees an empty
   `user_correction_signal` and emits no identity-correction
   row. The correction round on the current turn silently fails.

3. **Next-turn escalation via `_prior_surface_drift_observed`.**
   If the previous turn's `surface_consistency_audit_tail`
   recorded a `drifted_self_id` / `drifted_voice` outcome (the
   assistant's reply was in the wrong persona), then on the
   next turn `_classify_turn_latency_mode` returns
   `mode = "normal"` with `reason_codes =
   ["prior_surface_consistency_drift"]` (mvp_loop.py:5388).
   This forces the next turn's conscious loop to run in
   full mode, and the LLM has another chance to fill
   `correcting_assistant_identity`.

4. **Same-turn correction gap is real and accepted.** The v1
   path cannot block a wrong-persona reply on the same turn the
   user issues a short-sentence correction under fast_chat. The
   next turn re-evaluates. This is a deliberate trade-off:
   closing the same-turn gap would require a bounded
   pre-conscious extractor (M18.7.2-style minimal-prompt call
   for `correcting_assistant_identity`), which is a separate
   M20.3 / M18.7.2 follow-up milestone, not part of v1.

   **Out of scope (v1)**: a pre-conscious minimal extractor
   would itself be a new LLM call in fast_chat, which
   contradicts the v1 latency budget. Future work MAY
   revisit this if a low-cost signal source (e.g. an
   `ingress_evidence_band` flag from the platform connector
   that indicates "user is correcting a previous reply")
   becomes available.

Audit / diagnosability:

- The post-conscious call emits no bus event when
  `correcting_assistant_signal` is empty. The M18.7.2
  minimal call site emits `M18_7_2_MinimalDegraded` only
  on LLM failure, not on empty signal.
- The `_prior_surface_drift_observed` trigger emits a
  `LatencyModeClassifiedEvent` with
  `reason_codes = ["prior_surface_consistency_drift"]`
  in the next turn's bus.
- A future operator-visible counter
  `correction_round_no_op_total` could be added to
  `m18_5_attribution_diagnostics` to surface
  "the user issued a short correction; we missed
  same-turn; escalated next turn" — but that
  instrumentation is not in v1.

#### 3.2. Pre-send gate

A new settler path in M20.1 that runs **before the assistant reply is
committed**:

```text
class SameTurnSurfaceSettler:
    def run_pre_send(
        self,
        draft_reply: str,
        horizon_commitments: list[ActiveCommitment],
    ) -> SameTurnSurfaceVerdict:
        ...
```

The pre-send gate:

- takes the existing `draft_reply` (the conscious-loop + thinking
  output before `validate_visible_reply`),
- takes all `horizon_commitments` whose `horizon = "same_turn_surface"`,
- runs the corresponding settlers (`runtime_mode_state`,
  `identity_voice_match`, `boundary_handled`, `pacing_match`),
- returns one of:
  - `{"decision": "pass", "evidence_refs": [...]}`: no change
  - `{"decision": "advisory_guidance", "guidance": "...",
     "evidence_refs": [...]}`: reply is committed unchanged; guidance
    is added to `control_guidance` for the same-turn reply
  - `{"decision": "block", "replacement": "...",
     "evidence_refs": [...]}`: reply is replaced with `replacement` (a
     short, bounded fallback such as `persona_boundary_fallback` from
     the existing `validate_visible_reply`)

`block` is allowed only when the failing observable's owner is
`runtime_mode_state` AND the owner has `accepts_same_turn_block = true`.
For all other observables, the gate can only return `pass` or
`advisory_guidance`.

#### 3.3. Post-send advisory

After the reply is committed, the same settler runs `run_post_send`:

```text
def run_post_send(
    self,
    committed_reply: str,
    horizon_commitments: list[ActiveCommitment],
) -> PostSendAdvisory:
    ...
```

Post-send returns only `{"decision": "pass"}` or
`{"decision": "advisory_guidance", "guidance": "..."}`. It cannot
`block` because the reply is already committed.

The advisory is added to the existing `control_guidance` for the
**next** turn, not the current turn.

#### 3.4. Audit events

```json
{
  "type": "SameTurnSurfaceVerdict",
  "turn_index": 42,
  "horizon": "pre_send|post_send",
  "commit_ids": ["<sha1>", ...],
  "decision": "pass|advisory_guidance|block",
  "owner_id": "<from registry>",
  "evidence_refs": ["..."],
  "reason_codes": ["..."],
  "engineering_proxy_label": "mvp_local_same_turn_surface",
  "at": "<iso8601>"
}
```

A `commit_id` with `horizon = "same_turn_surface"` may appear in at
most one `SameTurnSurfaceVerdict` per turn (either pre-send or post-
send, not both).

#### 3.5. M20.2 §2 special case registry v2 exception table (NEW)

M20.2 §2 freezes the rule "`source_kind = policy` → `expire` for any
outcome". M20.3 does **not** modify that rule, but it adds a
**registry v2 exception table** that the M20.2 dispatcher reads at
runtime:

```text
exceptions:
  - when routed_owner_id == "runtime_mode_state":
      skip the "policy -> expire" rule
      apply the regular magnitude-to-level table instead
  - for all other owners:
      M20.2 §2 special case is unchanged
```

This is the only way the PolicyProducer-admitted policy commitment
(durable mutate in §1.2) can actually update `runtime_mode_state`
after M20.2 dispatch. Without this exception, M20.2 would expire
every policy commitment and `runtime_mode_state` would be read-only
in practice, defeating §2's `graded_action_set: ["microadjust",
"next_turn", "same_turn", "revoke"]`.

Implementation: the M20.2 dispatcher reads the `runtime_mode_state`
owner's `accepts_policy_correction: true` row in the registry and
short-circuits the §2 special case. M20.2's frozen rule remains
"policy → expire"; the registry column is the parameterization
point. This is a registry-driven exception, not a rule change.

### 4. fast_chat minimum loop invariant

A new runtime invariant module:

```text
segmentum/dialogue/runtime/loop_invariants.py

class LoopInvariants:
    def enforce_minimum_loop_coverage(
        self,
        turn_context: TurnContext,
        proposed_commitments: list[ActiveCommitment],
    ) -> LoopCoverageVerdict:
        ...
```

Rules:

- Every external turn (non-idle) MUST produce at least one
  `ActiveCommitment` with `source_kind = "policy"`. The
  `fast_chat_skip_admit` path (existing) MUST NOT skip PolicyProducer.
- Every external turn in `group_turn_binding.surface_intent == "chat"`
  or `"bot"` MUST produce at least one `ActiveCommitment` with
  `owner_id = "runtime_mode_state"`.
- If the minimum is not met, the invariant module emits
  `MinimumLoopCoverageMissed` (audit event) but does NOT block the
  turn.

```json
{
  "type": "MinimumLoopCoverageMissed",
  "turn_index": 42,
  "missing": [
    {"rule": "policy_source_required", "actual_count": 0},
    {"rule": "runtime_mode_state_required_for_chat_or_bot",
     "actual_count": 0}
  ],
  "engineering_proxy_label": "mvp_local_minimum_loop",
  "at": "<iso8601>"
}
```

#### 4.1. Wire into `run_turn` (DECIDED)

`mvp_loop.run_turn` call order is fixed:

```text
1. PolicyProducer.evaluate(...)         (T0 admission, runs FIRST
                                          or in parallel with
                                          conscious; MUST be reachable
                                          from the fast_chat path)
2. (existing conscious loop)             (T0 admission, may emit
                                          active_commitment_proposals
                                          and/or fill
                                          correcting_assistant_identity)
3. LoopInvariants.enforce_minimum_loop_coverage(...)
                                          (audit only, runs AFTER
                                          both admission sources above
                                          have produced their rows)
4. (existing thinking)
5. ... (rest of run_turn unchanged)
```

`enforce_minimum_loop_coverage` reads `proposed_commitments` =
union of PolicyProducer + M20.0 (LLM conscious) admissions for the
current turn. It does NOT retry the admission; if a rule is
violated, it emits `MinimumLoopCoverageMissed` and the turn
proceeds. The fast_chat path MUST call PolicyProducer even when
`fast_chat_skip_admit` is on for the conscious loop.

#### 4.2. Rule matrix (DECIDED)

The minimum is a **rule matrix**, not a single count N. Both rules
below are hard; miss on either rule → `MinimumLoopCoverageMissed`:

| Rule | Trigger | Required | Default state if no admission |
|---|---|---|---|
| A | every external turn (non-idle) | `ActiveCommitment` with `source_kind = "policy"` ≥ 1 | runtime_mode_state derived from surface_intent |
| B | `surface_intent ∈ {chat, bot}` | `ActiveCommitment` with `owner_id = "runtime_mode_state"` ≥ 1 | (no default; counted as miss) |

For group-chat fast_chat in `chat` / `bot` surface, the matrix
typically yields 2 admissions (one from `runtime_mode_state` per

## Acceptance Criteria

M20.3 is complete only if:

1. PolicyProducer is implemented as a deterministic, non-LLM admission
   path that emits `ActiveCommitment` rows with `source_kind = "policy"`.
2. The `runtime_mode_state` owner is added to `CommitmentRegistry` v2
   and the `Observable` v2 vocabulary; v1 rows are unchanged.
3. The `horizon` attribute is added to `ActiveCommitment` as a v2
   field; existing v1 commitments continue to default to
   `horizon = "next_turn"`.
4. The pre-send gate can `block` only when the failing observable's
   owner is `runtime_mode_state` and the owner has
   `accepts_same_turn_block = true`. For all other observables, the
   gate can only return `pass` or `advisory_guidance`.
5. The post-send advisory cannot `block` (reply is already committed)
   and writes only to next-turn `control_guidance`.
6. `LoopInvariants.enforce_minimum_loop_coverage` is called on every
   external turn; it emits `MinimumLoopCoverageMissed` but does not
   block the turn.
7. `fast_chat` does not skip PolicyProducer; the
   `fast_chat_skip_admit` path is verified to call PolicyProducer.
8. The 5 existing per-loop settlers (M17.1, M19.0, M13.2, M15.0,
   M18.5) are wired to the M20.1 runtime via thin adapters; the
   existing owner audit events and the new `ActiveCommitmentSettled`
   events agree on outcome in every test.
9. The 6+1+1 master acceptance fixture passes end-to-end.
10. All new tests pass; the existing M20.0 / M20.1 / M20.2 tests
    continue to pass without modification.
11. Path A and M10 remain untouched.
12. `prompts/README.md` M20.3 entry exists and lists the v2 registry
    bump, the horizon attribute, and the runtime invariant layer.

## Engineering Phenomenology Boundary

M20.3 may create visible behavioral change in three specific areas:

- `runtime_mode_state` becomes a real, writable mode container; a
  `/status` command now actually changes the persona, and the change
  is enforced on the same turn via the pre-send gate.
- The pre-send gate can BLOCK a reply whose persona / voice / boundary
  is violated; this is the first time the visible reply is hard-
  replaced by a runtime invariant. The replacement is bounded
  (`persona_boundary_fallback`); it is not free-form.
- The fast_chat minimum loop is a runtime invariant; if the rule is
  breached, an audit event is emitted. The user does not see the
  audit event directly.

M20.3 must NOT:

- script visible apology or self-blame text,
- treat user correction as the primary trigger for mode change (the
  PolicyProducer admits on bounded structured signal, not on raw text),
- claim subjective identity, mood, or persona feelings,
- unify Path A or M10.

M20.3 closes the loop on the engineering side. The conscious loop,
the thinking stage, the reply validation, and the M19.x surface
consistency check all still run. M20.3 adds an admission path, a
storage shape, a fast settler, a runtime invariant, and a migration.
It does not bypass anything.
