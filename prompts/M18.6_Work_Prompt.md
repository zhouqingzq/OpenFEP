# OpenFEP M18.6 Work Prompt

## Milestone

M18.6: Group Chat Acceptance Harness And Held-Out Validation

## Goal

Do not claim group-chat readiness until Path B passes real multi-party scripted
and held-out scenarios.

## Required Work

### 1. Build scripted multi-party acceptance scenarios

At minimum:

```text
Scenario A: turn-taking correction
Scenario B: ambiguous addressee clarification
Scenario C: cross-user memory/privacy boundary
```

Each scripted scenario should include both a positive success path and at least
one nearby failure probe, so the harness can distinguish true capability from
canned happy-path matching.

At minimum, the scripted suite should cover:

- three named participants in recent context
- one turn where reply-to or quote linkage is present
- one turn where current-speaker default would be wrong
- one turn where privacy policy changes the visible answer
- one turn where the correct action is intentional non-reply / wait-for-mention

### 2. Add restart/persistence checks

At least one scenario must include:

```text
talk -> save -> restart -> continue
```

### 3. Add held-out replay validation

Do not rely only on fixtures tuned during implementation.

Held-out validation should include at least:

- one replay set not used while iterating on prompts/tests
- one restart continuity continuation
- one ambiguity-heavy dialogue where the correct action is `clarify_addressee`

### 4. Define pass criteria and judge types

The harness must explicitly declare which checks are:

- structured field assertions
- deterministic replay assertions
- bounded rubric-based output judgments

Final pass must not depend only on free-form natural-language judging. Whenever
possible, speaker ownership, target choice, privacy decisions, thread state, and
non-reply decisions should be asserted from structured diagnostics or persisted
artifacts.

### 5. Report blocking failure classes

At minimum:

- speaker attribution error
- wrong addressee
- wrong third-party target
- privacy leak
- dropped unresolved thread
- restart drift
- deterministic policy replay mismatch
- false pass caused by missing structured input evidence

## Acceptance

This milestone is complete only if:

- the three scripted scenarios pass end-to-end
- at least one held-out replay set exists and contains a non-happy-path probe
- readiness is reported as pass/fail against the M18.0 checklist
- the report states which pass criteria were structured assertions versus
  rubric-based judgments
- the final report identifies the bounded operating envelope under which the
  pass claim is valid
- no claim of group readiness depends on Path A or Streamlit legacy mode
