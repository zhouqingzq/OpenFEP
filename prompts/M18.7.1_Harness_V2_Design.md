- status: design draft, not yet approved
- at: 2026-06-09
- branch: main

  not help; addressee 0.25→0.0, reaction ECE 0.258→0.417)

- out of scope: M18.7.2 prompt, M18.7 surface schema,

## 0. Why this design exists

The post-P0-step2 replay confirmed three things
(see section 0 of the post-P0 replay summary):

1. **Harness 打错靶 (m18_7_1_calibration.py:810-812)**.
   Reaction accuracy is judged by strict string
   equality on `reaction_to_turn_id`. The LLM emits
   `reaction_to_turn_id=""` 5/6 times. So
   `n_correct/n_present = 0/6` is forced by the
   scoring function, not by the LLM's semantics.

2. **Fixture GT 占位符不可解析**
   (m18_7_1_held_out_calibration.json:122-124).
   GT uses literal placeholder strings
   `"turn_<assistant_prior_turn_id>"`. Even if the
   LLM fills a real turn_id like `"turn_7"`, the
   strict-equality scoring can never match.

3. **P0-step2 prompt fix (commit 5ab3db4) was the
   wrong intervention**. It re-introduced v1
   semantic categories but the categories were
   not the missing information. The actual missing
   information is: the prompt does not enumerate
   available prior turn_ids (assistant + user) for
   the LLM to map "the prior claim" to a specific
   turn. P0-step2 commit message also wrote a fact
   error: pre-P0 reaction was already 0/6, so the
   commit's "fix reaction 0/6" framing is wrong.

This design fixes the **measurement layer** (1) and
(2) so that future prompt and threshold changes can
be evaluated against a trustworthy harness. Prompt
fixes are a separate milestone (out of scope here).

## 1. Goals

- G1. The harness measures what the LLM produces.
  Add a mode that scores the LLM's actual emitted
  fields (`reaction_to_participant_id` +
  `is_about_assistant_claim`) instead of only
  `reaction_to_turn_id`.

- G2. The harness handles fixture GT placeholders
  transparently. When the runner encounters a
  placeholder, it resolves it against the
  replay-time context (which assistant/user turn
  was the prior claim, etc.).

- G3. The harness handles participant id naming
  mismatches. The LLM emits
  `reaction_to_participant_id="assistant"`; the
  fixture GT has `"hutao"`. These are the same
  subject (the bot) under two different surface
  ids. A normalization map collapses equivalent
  ids before scoring.

- G4. v1 behavior is preserved. The current strict-
  equality scoring on `reaction_to_turn_id`
  remains available as one of several modes; the
  v1 report shape is unchanged. v2 modes are
  opt-in via runner arg.

- G5. No code change to M18.7.2, M20.4, M20.4.1,
  M18.5, M18.7, M18.7 prompt templates, or
  M18.7 normalize contract. v2 lives entirely
  inside `m18_7_1_calibration.py` and
  `scripts/run_m18_7_1_real_llm_calibration.py`.

## 2. Non-goals

- NG1. NOT changing M20.4 threshold constants
  (`M20_4_PRODUCER_ADMIT_MIN`,
  `M20_4_TIE_BREAKER_CONFIDENCE_MIN`, or the
  per-field split from P0-3 / commit 1e892b2).
- NG2. NOT changing the M18.7.2 minimal prompt to
  enumerate prior turn_ids. That is a separate
  M18.7.2 follow-up.
- NG3. NOT changing the M18.7 surface schema
  (`m18_7_attribution_hypotheses`).
- NG4. NOT changing the v1 `addressee_hypothesis`
  scoring on `addressed_to_assistant` bool
  (that field's strict-equality scoring is
  sensible; addressee accuracy is meaningful
  today; only reaction has the turn_id problem).
- NG5. NOT removing the v1 single-mode report.
  v2 adds modes; v1 stays as the default.

## 3. Scoring modes (v2)

The runner accepts a `scoring_mode` argument
that selects one of three reaction-side scoring
modes. Addressee-side scoring is unchanged (v1
strict-equality on `addressed_to_assistant`).

### 3.1 Mode A — `by_pid` (default for v2)

Score per-decidable-turn:
- `pid_correct` = (normalized
  `pred.reaction_to_participant_id` ==
  normalized `gt.reaction_to_participant_id`).
  Empty/None on either side is "unknown"-style
  skip; both empty is skip; one empty one not
  is incorrect.
- `is_about_correct` = (pred.is_about_assistant_claim
  == gt.is_about_assistant_claim). Same
  empty-skip rule.
- `joint_correct` = pid_correct AND is_about_correct.

Compute three accuracies:
- pid accuracy
- is_about accuracy
- joint accuracy (the most M20.4-relevant: a
  reaction is "correct" if it identifies the
  right participant AND the right is_about
  flag; turn_id is a soft identifier that
  the LLM doesn't have to fill)

This is the **primary v2 mode** and the one
that should be reported first.

### 3.2 Mode B — `by_turn_id_resolved`

Score on strict equality of
`reaction_to_turn_id`, but with **placeholder
resolution** (section 4) before scoring. If the GT
`reaction_to_turn_id` is `"turn_<assistant_prior_turn_id>"`
and the resolved value at replay time is
`"turn_5"`, then the LLM's
`reaction_to_turn_id="turn_5"` is correct; empty
is incorrect.

This mode is the closest to v1's intent but
fixes the placeholder bug. It is the secondary
v2 mode and is reported alongside Mode A so
reviewers can see "what v1 would have said
if the fixture was sane".

### 3.3 Mode C — `by_turn_id_v1` (legacy)

Strict equality on `reaction_to_turn_id` with
no placeholder resolution. Reproduces v1
behavior bit-for-bit. Useful as a control
to confirm v2 changes don't accidentally
shift v1 reports.

### 3.4 Mode selection

Runner arg: `scoring_mode: Literal["by_pid",
"by_turn_id_resolved", "by_turn_id_v1"] = "by_pid"`.
Default in v2 is `by_pid`; the CLI flag
`--scoring-mode` exposes it. Tests
(`test_m18_7_1_calibration.py`) get a fourth
mode `all` that runs all three and reports
all three in one `CalibrationHarnessReport`.

## 4. Placeholder resolution

### 4.1 The placeholder pattern

`reaction_to_turn_id` GT may use these
literals (case-sensitive):

- `"turn_<assistant_prior_turn_id>"` → resolve
  to the most recent assistant utterance's
  `turn_id` in the replay history at the time
  of the current turn.
- `"turn_<user_prior_turn_id>"` → resolve to
  the most recent user utterance's `turn_id`
  (any speaker other than the assistant) at
  the time of the current turn.
- `"turn_<carol_prior_turn_id>"` and other
  named-speaker placeholders → resolve to the
  most recent utterance by that participant
  in the replay history.
- `"turn_<any_unknown>"` → resolves to
  `"turn_<any_unknown>"` literal (deferred;
  the runner emits a `placeholder_unresolved`
  warning and treats it as "unknown" GT for
  scoring).

### 4.2 Resolution mechanism

The runner keeps a `replay_history: list[ReplayTurnRecord]`
where each record is
`(turn_id, participant_id, role, text)`.
The runner walks the fixture linearly
(one turn at a time); at each turn, the
`replay_history` is the list of all prior
turns (T+1, T+2, ..., T-1 already replayed).
Resolution is "most recent matching record".

If `replay_history` is empty (turn 0) or
no matching record exists, the runner emits
a `placeholder_unresolved` warning in the
report's `fixture_warnings` list and
treats the GT as "unknown" for that turn
(skips scoring per v1 rules).

### 4.3 What "turn_id" means here

In the existing fixture, each step has a
`turn_index` integer (0..11). The runner
should treat `turn_id = f"turn_{turn_index}"`
as the canonical form for resolved values.
This matches the M18.7 surface's
`evidence_refs` shape and the `commit_id`
hashing key.

## 5. Participant id normalization

### 5.1 The problem

The LLM emits these as `reaction_to_participant_id`:

- `"assistant"` (the bot role)
- `""` (empty, no attribution)
- `"hutao"` (the persona name when prompt
  uses the persona as speaker-of-the-claim)

The fixture GT uses:

- `"hutao"` (the persona, when reacting to
  the bot's claim)
- `"carol"` / `"dave"` / `"eve"` (other
  participants)
- `"unknown"` (when annotator can't tell)

There is also a third surface id in
production: `"clawdgroupchat_bot"`, the
internal bot id. The LLM is unlikely to
emit it (the prompt uses `assistant` and
the persona name), but the normalization
map should still cover it for safety.

### 5.2 The normalization table

Define a constant
`M18_7_1_PID_NORMALIZATION: dict[str, str]`
mapping every surface id to a canonical
form. The canonical forms are:

- `"bot"` for the assistant (any of
  `assistant`, `hutao`, `clawdgroupchat_bot`,
  `hutao_assistant`).
- The lowercase participant name for
  humans (`carol`, `dave`, `eve`, `bob`).
- `""` (empty) for the LLM's "I don't
  attribute this" signal.

The runner applies
`normalize_pid(pid, table=M18_7_1_PID_NORMALIZATION)`
to BOTH the prediction and the GT before
strict-equality comparison in Mode A and
Mode B.

### 5.3 Where the table lives

In `m18_7_1_calibration.py` as a frozen
v2 constant. v1 code does not import or
reference it. The table is opt-in: Mode A
uses it; Mode C does not (preserves v1
behavior bit-for-bit).

### 5.4 Extensibility

The table accepts new entries without code
changes via a runner arg
`--pid-normalization-override path/to/json.json`
(merges with the frozen default; runtime
override only). This lets future
fixtures (with different bot id
conventions) plug in their own
mappings without modifying the harness
source.

## 6. Report shape (v2)

### 6.1 `CalibrationHarnessReport` extension

Add a new field `scoring_mode: str` at the
top level. Existing fields unchanged. v1
`to_dict()` output is byte-identical when
`scoring_mode="by_turn_id_v1"`.

### 6.2 `CalibrationFieldReport` extension

Add a new field `n_joint_correct: int` and
`n_pid_correct: int` and `n_is_about_correct: int`
for reaction fields. v1 mode (`by_turn_id_v1`)
sets these to `None` (or omits the
key in `to_dict()` output to preserve
byte-identical v1 report).

### 6.3 Mode A report shape

For reaction in `by_pid` mode, the
`reliability_bins` are computed against
`joint_correct` (the strictest signal) by
default. The report also includes a
`pid_breakdown` and `is_about_breakdown`
section with separate bin tables for
each sub-axis. This is a bit verbose but
it makes the LLM's calibration
decomposable: a high-bin conf can be
correct on pid but wrong on is_about,
which is actionable info.

### 6.4 Mode B report shape

For reaction in `by_turn_id_resolved`
mode, the v1 report shape is reused
exactly, with a `fixture_warnings: list[str]`
field appended to flag any unresolved
placeholders.

### 6.5 Mode C report shape

Byte-identical to v1.

## 7. CLI / runner arg changes

`scripts/run_m18_7_1_real_llm_calibration.py`
adds:

- `--scoring-mode {by_pid,by_turn_id_resolved,by_turn_id_v1,all}`
  default: `by_pid` (v2 default; v1 was
  effectively `by_turn_id_v1`).
- `--pid-normalization-override PATH` optional.
- `--resolve-placeholders / --no-resolve-placeholders`
  default: `--resolve-placeholders`
  (only relevant in `by_turn_id_resolved`
  mode; ignored in other modes).

The final JSON summary printed by the
runner includes a top-level
`scoring_mode` field and, in `all` mode,
a `by_pid` + `by_turn_id_resolved` +
`by_turn_id_v1` triple.

## 9. Acceptance criteria

- AC1. All T1-T10 tests pass.
- AC2. The post-P0 replay (12-turn fixture)
  re-run with `--scoring-mode by_pid`
  produces a non-degenerate accuracy on
  the reaction field (target: ≥ 0.33 joint

  show that the LLM is doing meaningful

- AC3. Mode C report on the post-P0 fixture

  (reuses the same LLM calls, just
  re-scores).
- AC5. No changes outside
  `m18_7_1_calibration.py`,
  `scripts/run_m18_7_1_real_llm_calibration.py`,
  and `tests/test_m18_7_1_calibration.py`.
- AC6. Documentation: this design doc
  (the one you are reading) is referenced

## 10. Out of scope (still, after v2)

- OOS1. Prompt turn_id enumeration (M18.7.2
  follow-up). When the prompt gives the
  LLM a turn_id index table, Mode B
  accuracy will rise. That is a separate
  milestone.
- OOS2. Fixture GT placeholder
  replacement. With v2 placeholder
  resolution, the runtime can score Mode
  B correctly even with placeholder GTs.
  But a future fixture maintainer may
  want to replace the placeholders with
  real `turn_<N>` strings in the JSON
  directly. That's a content change to
  the fixture file, not a harness change.
- OOS3. Threshold revision. P0-3 (commit
  1e892b2) already split the v1 single
  0.85 threshold into per-field 0.9/0.7.
  Mode A's `joint_correct` accuracy may
  inform a future split of 0.7 further
  (e.g., a `pid-only` sub-threshold vs
  a `joint` sub-threshold), but that is
  M20.4's call, not M18.7.1's.
- OOS4. P0-step2 revert question. v2 makes
  P0-step2's prompt re-introduction
  even less impactful (because the
  real story is in the harness). Whether
  to revert 5ab3db4 is a separate
  decision; v2 is independent.

## 11. Open design questions

(These are not blockers for the design
doc; the user / M18.7.1 owner should
resolve before implementation.)

- Q1. **Should Mode A be the v2 default
  in the script, or should v1 stay the
  default and Mode A be opt-in?**
  Recommendation: Mode A default, because
  v1's 0/6 reaction accuracy is uninformative
  and the post-P0 report explicitly said v1
  understates the LLM. The risk is that
  downstream consumers (M20.4 threshold
  review) parse the report shape; v2 has a
  `scoring_mode` field so consumers can
  branch on it.

- Q2. **Should the pid normalization table
  be a Python constant or a JSON file
  shipped with the module?**
  Recommendation: Python constant for
  v2.0, JSON file for v2.1 if the
  table grows beyond ~10 entries. Right
  now the table has 4-5 entries; Python
  is fine.

- Q3. **Should `n_joint_correct` count a
  turn where pid is empty on both sides
  as correct?**
  Recommendation: NO. The empty-skip
  rule (v1 per-turn outcome rules)
  applies: if both pred and GT are empty
  on a sub-axis, the sub-axis is
  "unknown" and the joint count does
  not include it. The `n_correct` /
  `n_incorrect` denominators are
  decided per sub-axis independently
  and then the joint uses the AND
  of the per-axis denominators (or
  the intersection, whichever is
  larger).

- Q4. **When the runner cannot resolve
  a placeholder (no matching prior
  turn), should the GT be treated as
  "unknown" (skip) or as a hard
  "incorrect"?**
  Recommendation: "unknown" (skip).
  An unresolved placeholder is an
  annotation error, not a model error.
  The runner emits
  `placeholder_unresolved` in
  `fixture_warnings` so the report
  reader knows.

- Q5. **Does this design require M18.7.1
  to revisit the `MIN_PRESENT_FOR_DRIFT_SIGNAL = 5`**
  (frozen v1 constant)?
  Recommendation: NO. The drift-signal
  threshold applies to n_present, which
  is unchanged in v2. The pid_breakdown
  and is_about_breakdown each have their
  own n_present count and each runs the
  drift-signal logic independently. If
  a sub-axis has n_present < 5, the
  report shows
  `insufficient_data` for that sub-axis
  but still reports the aggregate
  joint n_present (which is usually
  higher).

## 12. Risk assessment

- R1. **Mode A might overstate accuracy**
  if the pid normalization is too loose
  (e.g., if `assistant` and `hutao` were
  not actually the same subject in some
  fixture). Mitigation: keep the
  normalization table minimal and
  document each entry; require a
  rationale comment on each entry.
  v2 review should explicitly walk
  the table.

- R2. **Mode B (resolved turn_id) might
  show much higher accuracy than Mode A
  on a future fixture where the LLM
  learns to fill turn_ids**. That's
  fine — it's a true positive. But
  it would mean M20.4's threshold
  review would benefit from looking at
  BOTH modes, not just Mode A. The
  report's `scoring_mode` field
  makes this explicit.

- R3. **The `all` mode could be slow**
  if it triggers re-runs. Mitigation:
  the runner reuses the same
  `predictions` and `ground_truth` lists
  across modes; only the scoring
  function is invoked three times. Cost
  is constant-factor 3 on the scoring
  step, not on the LLM step.

- R4. **Backwards compat for v1 report
  consumers**. The runner's printed
  JSON in Mode C is byte-identical to
  v1; the only addition is the
  `scoring_mode` field. Consumers that
  parse the JSON and ignore unknown
  fields are fine. Consumers that do
  `assert json.keys() == {"ok", "stage",
  ...}` will break. Mitigation: v1
  consumers should switch to
  `scoring_mode="by_turn_id_v1"` and
  use the `--scoring-mode` flag
  explicitly. The CLAUDE.md red line
  "no new fields without bump" is
  honored by the explicit
  `scoring_mode` field and the v1
  byte-identical Mode C.

## 15. Why v2 is the right next step

- The P0 prompt-fix path failed
  (post-P0 replay).
- The remaining unfixed problems are
  measurement (harness) and inputs
  (prompt turn table, fixture GT).
- Measurement is the cheaper, lower-
  risk, higher-information next step.
  Once v2 is in, every subsequent
  prompt change can be measured
  correctly. Prompt and fixture
  changes can be done in parallel
  after v2 lands.
- v2 does not require any LLM call
  during development (Mode A/B/C are
  pure functions; placeholder
  resolution is a pure function
  over `replay_history`). All tests
  can be deterministic with
  `FakeJSONLLM`.
- v2 is fully backward compatible
  (Mode C is byte-identical to v1).
