# OpenFEP M18.0 Work Prompt

## Milestone

M18.0: Group Chat Readiness Contract And Acceptance Boundary

## Goal

Define what it must mean for Hu Tao / Path B to be "ready for group chat"
without hand-waving, and freeze the acceptance boundary before any multi-party
runtime work begins.

This milestone is a contract milestone, not a feature milestone.

It must answer:

```text
What exact behaviors distinguish:
  "single-speaker chat with speaker_name switching"
from
  "real multi-party group-chat readiness"?
```

If this contract is not explicit, later milestones can fake progress by only
improving alias handling or by storing more names in memory.

## Readiness Checklist

Path B can be considered group-chat ready only when all of the following are
true:

### 1. Speaker Separation

```text
Different participants remain distinct durable agents in runtime state.
```

Measurable standard:

- Alice, Bob, and Carol must never collapse into one user bucket
- current speaker, quoted third party, and prior speaker must remain separable
- memory/model writes must preserve author identity

### 2. Addressing And Target Resolution

```text
The system must correctly resolve who is talking, who is being addressed,
and who is being talked about.
```

Measurable standard:

- direct mention, reply-to, quoted name, alias, and pronoun follow-up must not
  silently drift onto the wrong participant
- the system must support more than one candidate target in recent context,
  even if only one final reply target is chosen

### 3. Group Transcript Ownership

```text
The transcript must preserve speaker ownership and turn structure as
first-class data, not only raw text.
```

Measurable standard:

- replaying a transcript must recover who said each turn
- group context must survive restart/reload
- transcript storage must not flatten all human turns into one generic
  "interlocutor"

### 4. Group Memory And Privacy Boundaries

```text
What one participant said about another must remain properly scoped.
```

Measurable standard:

- cross-user memory may be reused only under explicit shareability rules
- private claims must not be re-attributed to the wrong participant
- gossip-like retrieval must remain auditable and bounded

### 5. Multi-Party Reply Selection

```text
Hu Tao must choose who she is replying to and what stance she is taking in a
multi-party turn.
```

Measurable standard:

- the runtime must decide whether the reply is addressed to current speaker,
  the whole group, or a named third party
- it must be able to ask for clarification when addressee ambiguity is high
- it must not answer a side thread as if it were the main thread

### 6. Cross-Turn Social Continuity

```text
The runtime must track unresolved tension, agreement, correction,
and pending follow-up across multiple participants.
```

Measurable standard:

- if Alice corrects Bob, the next turn must preserve that conflict structure
- if Hu Tao promised to answer Bob after finishing with Alice, that obligation
  must remain visible
- group state must survive settlement, consolidation, and restart

### 7. End-To-End Group Scenarios

```text
Readiness is not claimed from unit tests alone.
```

Measurable standard:

- at least three scripted multi-party scenarios must pass:
  - turn-taking correction
  - ambiguous addressee clarification
  - cross-user memory/privacy boundary
- at least one held-out replay set must exist for regression

## Input Contract Baseline

The acceptance boundary for M18 assumes a structured group-turn input contract.
`speaker_name` alone is not sufficient evidence of multi-party readiness.

At minimum, later milestones must either preserve or explicitly justify the
absence of:

```text
speaker_participant_id or equivalent stable speaker key
reply_to_turn_id when the client has it
visible_participants for the current turn
explicit_mentions parsed by the client or gateway when mechanically available
quoted_turn_refs when the surface supports quoting/reply
delivery surface / session thread id
```

If a surface cannot provide one of these fields, the runtime may operate with a
degraded confidence band, but it must not silently present guessed ownership or
addressee resolution as certain.

## Bounded Operating Envelope

This roadmap is for a bounded small-group chat capability, not arbitrary social
reasoning.

The contract should be evaluated against a configurable but explicit envelope,
for example:

- 3-5 simultaneously active participants in recent context
- bounded candidate-target lists
- bounded unresolved thread slots
- bounded replay window plus durable summarized carry-forward state

The exact numbers may be implementation-configured, but M18.0 must require that
they are declared and tested, not left implicit.

## Architecture Position

This roadmap extends Path B only:

```text
ui/web or ui/tui
-> m16_api gateway + runner
-> MVPDialogueRuntime
-> group-turn interpretation owner
-> speaker/target graph
-> group-safe recall / memory boundaries
-> reply planning / settlement
-> durable multi-party continuity
```

This roadmap does not revive Path A and does not replace Path B with
`SegmentAgent`.

## Dependencies

Hard:

- M16.0-M16.4 Path B runner / gateway / TUI-Web path
- M17.0-M17.4 prediction lock / settlement / anti-top-k bundle loop
- M17.5-M17.12 unified memory-field runtime on Path B

Soft:

- existing `speaker_name` support
- existing `entity_binding`
- existing cross-user shareability / evidence-judgment surfaces

## Non-Goals

- Do not implement a social-network simulator.
- Do not add open-ended NLP heuristics for addressee inference.
- Do not claim group readiness from alias storage alone.
- Do not make Streamlit the owner for group orchestration.
- Do not treat plain transcript text as sufficient group state.

## Required Work

### 1. Freeze the acceptance checklist

Convert the seven readiness items above into explicit acceptance criteria and
name the evidence artifact for each. Freeze the structured group-turn input
baseline at the same time so later milestones are not forced to infer all
group structure from raw text.

### 2. Define milestone boundaries from M18.1 onward

Each later milestone must own exactly one main layer:

```text
M18.1 speaker/participant contract
M18.2 target-resolution graph
M18.3 transcript ownership + persistence
M18.4 group-safe memory boundaries
M18.5 multi-party reply policy + continuity
M18.6 end-to-end validation harness
```

Boundary clarification:

- M18.1 owns participant identity objects and runtime ownership references
- M18.2 owns addressee/target interpretation on top of that identity layer
- M18.3 owns transcript row schema, persistence, replay, and migration
- M18.4 owns memory reuse policy under group audience conditions
- M18.5 owns reply-addressing policy and unresolved-thread continuity
- M18.6 owns scenario harnesses, held-out validation, and pass/fail reporting

### 3. Define "not ready" failure classes

At minimum, enumerate these as blocking failures:

- input-contract ambiguity masked as certainty
- wrong speaker attribution
- wrong target resolution
- privacy boundary leak
- thread-ownership drift
- restart losing group state
- fake readiness from canned scripts only

## Acceptance

M18.0 is complete only if:

- the seven readiness standards are frozen in the prompt itself
- later milestones M18.1-M18.6 are explicitly scoped
- no item depends on Path A or M10
- the contract distinguishes true group readiness from simple speaker switching
