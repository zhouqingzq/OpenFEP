# OpenFEP M14.2 Work Prompt

## Milestone

M14.2: Decoupled Environment Loop And Durable Overnight Outreach

## Goal

Close the product loop exposed by the "think overnight and leave me a message"
scenario.

M14.1 gave Path B a background self-continuity runner, persistent budgets, and a
cross-session outreach queue. The remaining gap is architectural: the first
implementation can still behave like a UI-assisted runner, and an explicit
user request such as "tonight think about this; tomorrow morning leave me a
message" can remain as natural-language follow-up text instead of becoming a
durable scheduled intent.

M14.2 refactors the runtime into three explicit responsibilities:

```text
Environment loop
  Observes external changes: user messages, UI pings, session lifecycle,
  clock wakeups, process start/stop, optional local file/runtime signals.
  It only appends events. It does not think, decide, or generate text.

Durable event store / message bus
  Records what happened, what has been claimed, and what has been acknowledged.
  It is deliberately simple: append, claim, ack, query. It is not a second
  cognition layer.

MVP self loop
  Runs independently of Streamlit. It consumes events and due intents, updates
  MVP state through existing owners, keeps M14.1 budgets, and creates durable
  outbox entries when outreach should later be delivered.

Delivery / outbox loop
  Drains queued outreach through the existing M13.3 delivery assessor when a
  delivery surface is available. It never bypasses M13.3 safety, cooldown, or
  reply validation.
```

The target product behavior:

```text
User: "Hu Tao, think about this tonight and leave me a message tomorrow morning."
-> user message event is appended
-> intent extractor creates a durable scheduled_outreach open item
-> independent MVP self loop wakes on clock/due-intent checks
-> M14.0/M14.1 reflection prepares a queued_outreach proposal
-> queued_outreach survives closed browser, app restart, and runner restart
-> next available delivery surface drains it through M13.3
-> the user sees one approved, short, in-character message
```

Success means Streamlit is no longer a life-support device for continuity. The
UI renders state, submits environment events, and delivers approved messages;
it does not own the self loop.

## Architecture Position

M14.2 remains Path B and MVP-local. It builds on M14.1 instead of replacing the
M13/M14 cognition stack:

```text
Streamlit / CLI / clock / local adapters
-> EnvironmentEventStore (append-only, durable)
-> M14.2 self-loop daemon
   -> claim environment events
   -> inspect due open_items / scheduled intents
   -> call existing M13.4 + M14.0 + M14.1 tick machinery
   -> commit state through M8.9/M14.0 owners
   -> append outbox proposals only
-> queued_outreach / outreach_outbox
-> M13.3 delivery assessor
-> chat UI or future local notification surface
```

M14.2 does not introduce a second LLM persona, a second prompt stack, or a new
generation path. The existing conscious idle reflector remains the planner; the
new work is lifecycle, event durability, intent scheduling, and outbox
discipline.

## Dependencies

Hard:

- M8.9 state ownership contract and `MemoryWriteIntent`
- M13.3 outreach pipeline (`maybe_propose_proactive_turn`,
  `run_proactive_turn`, delivery assessor)
- M13.4 idle tick and structural pre-filter
- M14.0 conscious idle reflector and named owners
- M14.1 background budgets, self-continuity state, runner locks, and
  `queued_outreach.jsonl`

Soft:

- M11.0, M12.0, M12.1, M12.2 read-only context

M14.2 must not write to M11 or M12.* ledgers. Path A and M10 remain out of
scope.

## Non-Goals

- Do not add hosted push notifications, email, SMS, or external services.
  M14.2 prepares and stores messages locally; delivery happens when an approved
  local surface is available.
- Do not make the message bus smart. It records and coordinates; it does not
  interpret user intent or decide outreach.
- Do not let the runner produce user-visible text directly. Visible text still
  comes only through M13.3 generation and delivery assessment.
- Do not rely on Streamlit session pings for the primary loop. Inline runner
  may remain as a development fallback, but the primary acceptance path is the
  standalone self-loop daemon.
- Do not introduce unbounded LLM calls. M14.1 daily budgets still apply.
- Do not create a second agent/persona/cognition stack.
- Do not mutate `self_basic_facts.json`.
- Do not weaken M14.1 engineering-language discipline. Engineering surfaces use
  operational wording; persona chat text remains out of scope for that lint.

### 2. Durable Environment Event Store

Add:

```text
segmentum/dialogue/runtime/m14_2_event_bus.py
```

The event store is MVP-local and persona+session scoped. It may use JSONL plus
file locks by default:

```text
environment_events.jsonl
environment_event_claims.jsonl
```

Minimum event schema:

```text
{
  event_id,
  event_type,
  source,                 # "streamlit" | "cli_runner" | "clock" | "test" | ...
  at,
  persona_id,
  session_id,
  correlation_id,
  payload,
  status: "pending" | "claimed" | "acked" | "failed" | "expired",
  claimed_by,
  claimed_at,
  acked_at,
  failure_reason
}
```

Required event types:

```text
UserMessageCommittedEvent
UIPingEvent
UISessionClosedEvent
RunnerStartedEvent
RunnerStoppedEvent
ClockWakeEvent
ScheduledIntentDueEvent
OutboxDeliverySurfaceAvailableEvent
```

API shape:

```text
append_event(event_type, payload, *, source, correlation_id=None) -> event_id
claim_events(consumer_id, *, limit, event_types=None, lease_seconds=60) -> list[Event]
ack_event(event_id, consumer_id, result=None) -> None
fail_event(event_id, consumer_id, reason, *, retryable=True) -> None
query_events(...) -> list[Event]
```

Rules:

- Append and claim operations must be file-locked.
- Claims use leases so a crashed runner does not permanently lose events.
- The event bus never calls LLMs and never mutates MVP state except its own
  event/claim ledgers.
- The event bus must be deterministic under fake-clock tests.
- Duplicate events with the same `correlation_id` and `event_type` are
  idempotent within a bounded window.

### 3. Environment Adapters

Refactor current UI-side lifecycle signals so they append environment events
instead of directly driving cognition.

Streamlit adapter responsibilities:

- append `UserMessageCommittedEvent` after a user message is committed,
- append `UIPingEvent` during normal renders,
- append `OutboxDeliverySurfaceAvailableEvent` when the chat surface is idle
  and allowed to display a proactive message,
- append `UISessionClosedEvent` when detectable; otherwise rely on ping expiry,
- render runner/outbox/event status read-only.

CLI/daemon adapter responsibilities:

- append `RunnerStartedEvent` / `RunnerStoppedEvent`,
- append periodic `ClockWakeEvent` or directly trigger the self-loop tick after
  recording the wake event,
- never require an active Streamlit process.

The UI may still call a lightweight queue drain on render, but that drain must
be modeled as delivery-surface availability, not as the thing that keeps the
self loop alive.

### 4. Independent MVP Self Loop Daemon

Add or refactor the M14.1 runner into a primary daemon:

```text
segmentum/dialogue/runtime/m14_2_self_loop.py
python -m segmentum.dialogue.runtime.m14_2_self_loop --persona <id> --session <id>
```

The daemon:

- is the primary acceptance path for overnight behavior,
- acquires the existing single-runner lock per persona+session,
- uses the M14.1 budget meter and daily rollover,
- periodically claims environment events,
- checks due scheduled intents and due open items,
- runs the existing M13.4/M14.0/M14.1 idle-reflection machinery when justified,
- appends queued outreach/outbox entries when reflection or explicit intent
  requires later delivery,
- writes audit events to `conversation_log.jsonl`,
- shuts down cleanly on `SIGTERM`, `SIGINT`, budget exhaustion, opt-out, or
  lock loss.

The daemon must not depend on Streamlit objects, Streamlit session state, or UI
callbacks. Inline background runner support may remain, but its status must be
reported as `runner_kind="inline_dev_fallback"` and it must not be used by
M14.2 acceptance tests for overnight continuity.

### 5. Explicit Overnight / Later Message Intent Extraction

Add a deterministic intent extraction layer for user messages committed to the
event store.

Preferred module:

```text
segmentum/dialogue/runtime/m14_2_scheduled_intents.py
```

It must detect explicit local-language requests such as:

```text
"think about this tonight and leave me a message tomorrow morning"
"sleep on it and tell me tomorrow"
"tonight mull it over; remember to say something when I come back"
"明早给我留言"
"今晚想想，明天早上告诉我"
"睡一晚，醒来给我留句话"
```

Output:

```text
scheduled_intent:
  intent_id
  kind: "scheduled_outreach" | "reminder" | "followup_reflection"
  created_at
  due_at
  due_window_seconds
  source_event_id
  source_turn_id
  user_request_excerpt
  ordinary_language_intent
  status: "pending" | "prepared" | "delivered" | "expired" | "cancelled"
  delivery_policy:
    require_m13_3_assessor: true
    max_visible_messages: 1
    no_direct_generation: true
  evidence_refs
```

Storage:

```text
scheduled_intents.jsonl
```

Integration with `open_items`:

- create or update a durable `open_items` entry with
  `type="scheduled_outreach"` and a concrete `next_check=due_at`,
- link it to `intent_id`,
- ensure the open item survives UI close and process restart,
- close or mark delivered only after queued outreach is delivered or expires.

Parsing rules:

- Use deterministic local parsing first for common English and Chinese phrases.
- Use an LLM classifier only behind M14.1 budgets and only when deterministic
  parsing finds a likely but ambiguous schedule.
- Resolve relative times using the local timezone configured for the session.
- "Tomorrow morning" defaults to 09:00 local time unless the user specified a
  time. The due window defaults to 4 hours.
- If the requested time is already past, schedule the next plausible future
  window and audit the adjustment.

### 6. Due-Intent Preparation

When the daemon sees a due `scheduled_outreach` intent:

1. Claim or mark the intent as preparing under a file lock.
2. Build a compact context from the original user request, relevant
   open_items, recent memory, self_continuity, and elapsed time.
3. Run the existing M14.0/M14.1 reflection machinery, not a new persona prompt.
4. Create exactly one `queued_outreach` / outbox proposal with:

```text
trigger = "scheduled_outreach"
source_intent_id
ordinary_language_intent
due_at
expires_at
evidence_refs
drive_snapshot_compact
status = "pending"
delivery_policy.require_m13_3_assessor = true
```

5. Mark the scheduled intent as `prepared`.

If there is insufficient evidence or budget is exhausted, the daemon must
record a suppression/block event and keep or expire the intent according to
policy. It must not silently drop the request.

### 7. Outbox Discipline

M14.1 `queued_outreach.jsonl` may be kept, or M14.2 may introduce a clearer
`outreach_outbox.jsonl`. Pick one canonical file and document the choice in
`reports/m14_2_runtime_lifecycle.md`.

The canonical outbox schema must include:

```text
proposal_id
source_intent_id
created_at
due_at
expires_at
trigger
ordinary_language_intent
evidence_refs
drive_snapshot_compact
status: "pending" | "delivered" | "expired" | "suppressed" | "cancelled"
delivery_attempts
last_delivery_attempt_at
last_suppression_reason
```

Drain rule:

- A delivery surface event allows at most one pending outbox entry to be
  considered.
- Delivery always calls `maybe_propose_proactive_turn` with the locked outbox
  proposal and then `run_proactive_turn` only if approved.
- Transient suppressions (`cooldown_active`, `user_active`,
  `delivery_surface_unavailable`) keep the outbox entry pending.
- Hard suppressions (`safety_risk`, `expired`, `user_opted_out`,
  `session_limit_reached`) mark the entry suppressed or expired.
- Successful delivery closes the linked scheduled intent and linked open item.

The runner never writes visible assistant chat content by itself.

### 8. State, Locks, And Crash Recovery

Required invariants:

- one self-loop daemon per persona+session,
- all state writes happen under the existing MVPStateStore lock or a documented
  narrower file lock,
- event claims have leases and can be reclaimed after a crash,
- intent preparation is idempotent by `intent_id`,
- outbox creation is idempotent by `source_intent_id`,
- delivery is idempotent by `proposal_id`,
- daily budgets survive restart and roll over only by local date,
- opt-out stops preparation and delivery but keeps audit history.

Crash recovery tests must cover:

- crash after event append before claim,
- crash after claim before ack,
- crash after scheduled intent creation before open item update,
- crash after intent marked preparing before outbox append,
- crash after outbox append before intent marked prepared,
- crash after delivery assessor approval before status update.

## Acceptance Criteria

M14.2 is complete when:

1. Environment observation, event storage, MVP self-loop execution, and outbox
   delivery are separate responsibilities with a documented lifecycle contract.
2. The primary overnight path is a standalone daemon that can run with
   Streamlit closed and can restart without losing pending work.
3. UI pings and Streamlit reruns no longer drive the self loop directly; they
   append environment events and expose delivery-surface availability.
4. Explicit "think overnight / message me tomorrow" requests create durable
   scheduled intents and linked open items with concrete `due_at`.
5. Due scheduled intents prepare exactly one durable outbox entry through the
   existing M14.0/M14.1 reflection stack.
6. Outbox entries are delivered only through the existing M13.3 assessor and
   generation path.
7. Crash/restart recovery is idempotent across event claim, intent creation,
   outbox creation, and delivery status update boundaries.
8. M14.1 budgets, opt-in controls, locks, and engineering-language discipline
   still apply.
9. M11/M12 ledgers, Path A, and M10 are not modified by the new loops.
10. All listed M14.2 tests pass with deterministic stubs and fake clocks.
